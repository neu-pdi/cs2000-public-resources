### Documenting Functions with Examples

On [Day 4](/days/4), we started each function from examples: for instance, we
wrote `moon_weight` from the expressions `100 * 1/6`, `150 * 1/6`, and
`90 * 1/6`. Now, what use are they? It's tempting to throw them away, but
_software evolves_: any useful program will change over time, and may end up
producing different values than it did at first, sometimes on purpose, and
sometimes by mistake (even one as silly as accidentally deleting some text). So
it's useful to keep the examples, to be alerted right away if the function stops
matching them.

In Python, we keep them in a _test function_, whose name starts with `test_`,
right after the function it checks. Each example is an `assert`, which checks
that the expression after it is `True`, using `==` to check that two values are
equal:

```python
def moon_weight(earth_weight: float) -> float:
    """Compute weight on moon from weight on earth"""
    return earth_weight * 1/6

def test_moon_weight():
    assert moon_weight(100) == 100 * 1/6
    assert moon_weight(150) == 150 * 1/6
    assert moon_weight(90) == 90 * 1/6
```

PLL runs the tests _every time you run the file_, and tells you if the function
no longer matches them. Check this! Change the body to
`return earth_weight * 1/3`, run the file, and pay attention to what PLL shows:
you should get used to recognizing it. Then fix the body, and instead change a
test, e.g. to `assert moon_weight(90) == 90 * 1/3`, and compare.

These examples are so similar to the body that they're unlikely to catch much.
But later, examples will be much simpler than the body, and then they are
invaluable for catching mistakes: professional programmers always write large
collections of examples, called _tests_. Examples are also part of _making sure
we understand the problem_: you work out the computation **on concrete values**
first, then worry about turning it into a function. If you can't write the
examples, chances are you won't be able to write the function either.

For `pen_cost`, from [Day 4](/days/4), we write the examples we started from as
tests, along with two more:

```python
def test_pen_cost():
    assert pen_cost(3, "wow") == 3 * (0.25 + len("wow")*0.02)
    assert pen_cost(10, "smile") == 10 * (0.25 + len("smile")*0.02)
    assert pen_cost(5, "") == 5 * 0.25
    assert pen_cost(0, "huskies") == 0
```

The last two tests are for special (yet valid) inputs: an empty message, and no
pens. Their right sides don't match the body: they only have to evaluate to the
answer we expect, and sometimes it's easiest to write the answer directly. What
goes on the right of `==` should summarize the computation, or the answer, in
some meaningful way. Most important? **Do not write the function, run it to find
the answer, and then put that answer on the right of the `==`!** Tests give the
design process some redundancy, so that you catch your mistakes: if the body is
wrong, and you use it to produce the answers, the tests can't catch it.

For now, we won't worry about nonsensical inputs, like a negative number of pens.
Try: we could have combined our two special cases into one, `pen_cost(0, "")`. Is
that a good idea? Why or why not?

### Motivating Example: Shipping Costs

On [Day 4](/days/4), we wrote `pen_cost`, to compute the cost of ordering pens.
Now we want `add_shipping`, to compute the total cost of an order including
shipping: an order of \$10 or less ships for \$4, while an order above \$10 ships
for \$8. As usual, we start with examples. Try writing a few: how are you choosing
the inputs? At random, or with some strategy? Here is a proposed set:

```python
def test_add_shipping():
    assert add_shipping(10) == 10 + 4
    assert add_shipping(3.95) == 3.95 + 4
    assert add_shipping(20) == 20 + 8
    assert add_shipping(10.01) == 10.01 + 8
```

They were chosen strategically: `10` is **at the boundary** between the charges,
`10.01` is **just over the boundary**, there are **both whole and decimal
numbers**, and there are examples that **result in each shipping charge**.

So far, we have made function bodies from examples by replacing the parts that
change with parameters. But here, `4` and `8` each appear in several examples,
and only in the answers, not the inputs: which one we use _depends_ on whether
the input is at most `10`. This calls for being able to _ask questions about
inputs_ in our programs.

### Conditionals: Computations with Decisions

To ask a question about our inputs, we use an `if` statement:

```python
def add_shipping(order_amt: float) -> float:
    """add shipping costs to order total"""
    if order_amt <= 10:
        return order_amt + 4
    else:
        return order_amt + 8
```

In an `if`, we ask a question whose answer is true or false (here,
`order_amt <= 10`), and give the code to run when the answer is true, and the
code for when it's false, after `else` (we call this the _else clause_). The
question line and the `else` line each end with a colon, and the code for each
case is indented under it.

### Booleans

So far, we have seen values of type `int`, `float`, `str`, and `Image`. What type
does a question like `order_amt <= 10` produce? Try `3.95 <= 10` and `20 <= 10`
at the prompt. `True` and `False` belong to a new type, `bool` (short for
_Boolean_, after George Boole), and they are its only two values. Try: what
happens if you enter `order_amt <= 10` at the prompt? Why?

#### Other Boolean Operations

Many other operations produce booleans, like checking whether two values are
equal, with `==` (unlike the single `=`, which associates a name with a value):

```python
1 == 1          # True
1 == 2          # False
"cat" == "dog"  # False
"cat" == "CAT"  # False
```

The last example shows that strings are _case-sensitive_: letters must match in
case for strings to be equal. We can also compare strings to put them in
alphabetical order:

```python
"a" < "b"         # True
"that" < "this"   # True
"alpha" < "beta"  # True
"a" >= "C"        # True
"a" >= "A"        # True
```

The last two need explaining: they follow a convention laid down long ago, in a
system called ASCII, in which every uppercase letter comes before every lowercase
one (letters outside of ASCII are far more complicated).

You can compare any two values for equality: `"a" == 1` is just `False`. Be
careful, though: that means comparing a number with a string by mistake doesn't
cause an error, and your program carries on with a nonsensical answer.

Just about every kind of data has some operations that produce booleans. For
example, `in` checks whether one string appears inside another:

```python
wm = "will.i.am"
"will" in wm  # True
"Will" in wm  # False (note the capital W)
```

#### Combining Booleans

Often, a decision depends on more than one boolean: you can vote if you're a
citizen _and_ above a certain age; you can board a bus if you have a ticket _or_
it's a free-ride day; you can drive if you are _not_ inebriated. For these,
Python has three operations, `and`, `or`, and `not`:

```python
(1 < 2) and (2 < 3)  # True
(1 < 2) and (3 < 2)  # False
(1 < 2) or (2 < 3)   # True
(3 < 2) or (1 < 2)   # True
not (1 < 2)          # False
```

Try: explain why numbers and strings are not good ways to express the answer to
a true/false question.

### Asking Multiple Questions

Shipping costs are rising, so we want a third level: orders between \$10 and \$30
ship for \$8, but orders over \$30 ship for \$12. So we need another question,
`order_amt <= 30`, with a charge of `12` if it fails. Where does it go? An
expanded `if`, using `elif` (short for "else if"), lets us ask several questions:

```python
def add_shipping(order_amt: float) -> float:
    """add shipping costs to order total"""
    if order_amt <= 10:
        return order_amt + 4
    elif order_amt <= 30:
        return order_amt + 8
    else:
        return order_amt + 12
```

Python evaluates the questions in order, starting with the one after `if`, and
runs the code for the first question that is `True` (and the `else` clause if
none are). An `if` can have any number of `elif`s.

How does this code capture orders _between_ `10` and `30`? Only implicitly: we
reach the second question only if the first, `order_amt <= 10`, was `False`, so
_in this context_, `order_amt <= 30` asks whether it's between the two. How
could you make "between" explicit? Remember `and`? (Python doesn't need the
parentheses here, since comparisons happen before `and`, but they make the order
clear.)

```python
def add_shipping(order_amt: float) -> float:
    """add shipping costs to order total"""
    if order_amt <= 10:
        return order_amt + 4
    elif (order_amt > 10) and (order_amt <= 30):
        return order_amt + 8
    else:
        return order_amt + 12
```

Either way, we should add tests for the new charge, like
`assert add_shipping(30) == 30 + 8` and `assert add_shipping(32) == 32 + 12`.
Both versions pass the tests, and both are correct. The `order_amt > 10` is
redundant, but conditions like it can help: they tell future readers (including
ourselves!) which condition covers a case, and they ensure that a mistake in an
earlier question, now or after someone later changes it, doesn't _silently_
produce surprising output.

Try: an online-advertising firm needs to decide whether to show an ad for a
skateboarding park. Write a function `show_ad` that takes a user's age and hair
color, and returns `True` if the user is between `9` and `18` and has either pink
or purple hair. Write it two ways: once with `if`, and once with just boolean
operations.

**Harms from reducing people to simple data.** Even this simple function encodes
a stereotype: many skateboarders aren't young, or don't have colored hair. Real
systems that decide who sees an ad, gets hired, is granted a loan, or is released
from jail also compare data about people with criteria in a program. So we
should ask _what data should represent people_ in our programs, and _what
stereotypes that data might encode_: decisions based on it can be inaccurate,
and harmful.

### Evaluating by Reducing Expressions

On [Day 4](/days/4), we saw how Python evaluates function calls by substitution.
Let's revisit that, now with `if`. Suppose a worker is paid \$10 per hour for up
to 40 hours, and \$15 for each extra hour:

```python
def wage(hours: float) -> float:
    """pay for hours worked: $10 an hour, and $15 an hour after 40"""
    if hours <= 40:
        return hours * 10
    elif hours > 40:
        return 40*10 + (hours-40)*15
```

Here is `wage(45)`, step by step, as in algebra: `45` is substituted for
`hours`; the first question is `False`, so its case is dropped, and the next
question is tried; it is `True`, so we are left with its case, and then it's just
arithmetic:

```
    wage(45)
=>  if 45 <= 40:
        return 45 * 10
    elif 45 > 40:
        return 40*10 + (45-40)*15
=>  if False:
        return 45 * 10
    elif 45 > 40:
        return 40*10 + (45-40)*15
=>  if 45 > 40:
        return 40*10 + (45-40)*15
=>  if True:
        return 40*10 + (45-40)*15
=>  return 40*10 + (45-40)*15
=>  return 400 + 5*15
=>  return 475
```

This is the best way to think about how Python evaluates expressions, and you
can use it to work through a program by hand (or in your head).

### Composing Functions

To compute the price of an order of pens including shipping, we need both
functions, sending the output of `pen_cost` to the input of `add_shipping`. Try:
write an expression for the total cost, with shipping, of `10` pens that say
`"bravo"`. We could pass the result of `pen_cost` directly to `add_shipping`, or
name it as an intermediate step:

```python
add_shipping(pen_cost(10, "bravo"))
```

```python
pens = pen_cost(10, "bravo")
add_shipping(pens)
```

#### How Function Compositions Evaluate

For the second version, Python evaluates `pen_cost(10, "bravo")` by
substitution, giving `3.5`, and stores that in the directory as `pens`; then, for
`add_shipping(pens)`, it looks up `pens`, and substitutes `3.5` for `order_amt` in
the body of `add_shipping`, giving `7.5`. For the first version, since the inputs
to a function are evaluated before it is called, Python evaluates
`pen_cost(10, "bravo")`, giving `3.5`, and substitutes that for `order_amt` in
the body of `add_shipping`, giving `7.5`.

Only the version that names `pens` uses the directory, but both get the same
result, since the same value is substituted into the body of `add_shipping`. That
version takes more steps, but some find it easier to read: use whichever makes
more sense to you.

#### Function Composition and the Directory

We could also use a name in the body of `pen_cost`, to make it more readable:

```python
def pen_cost(num_pens: int, message: str) -> float:
    """total cost for pens, each 25 cents
    plus 2 cents per message character"""
    message_cost = len(message) * 0.02
    return num_pens * (0.25+message_cost)
```

Try: write out the steps for `pens = pen_cost(10, "bravo")`, then
`add_shipping(pens)`, with this `pen_cost`. Hopefully, you made two directory
entries: `message_cost`, inside the body of `pen_cost`, and `pens`. Now, what do
you think happens here?

```python error
pens = pen_cost(10, "bravo")
cheap_message = message_cost > 0.5
add_shipping(pens)
```

`message_cost` isn't defined anywhere in this program, unless we peek inside
function bodies, which doesn't make sense (you might not even be able to see
inside a function from a library, say). So this should be an error, and it is: a
`NameError`. But if `message_cost` was in the directory, why?

Because _directory entries made inside a function are local (private) to the
function's body_. When you call a function, Python sets up a local directory
that other code can't see. The body can use names from its own local directory
(like `message_cost`) or from the overall (_global_) directory (like `len`), but
one function call can never look inside another's local directory. Once a call
finishes, its local directory disappears (since nothing else could use it
anyway).

## Intro (20 mins)

- Another common form of data, in addition to numbers, strings, and images, are
  "true/false" values. These values, called "booleans" (after an Irish
  mathematician George Boole who studied them, in obscurity), have only two possibilities. In Python, written as:

  ```python
  True
  False
  ```

- This form of data allows us to express options, or choices. For example, we
  might want to ask whether the temperature is at or above 80F/27C, and if so, wear a
  sun hat.

- This requires two things. First, to be able to compare numbers (a current
  temperature, in F for example, and 80); there are many operators on numbers
  (and strings, etc) to ask questions like that, and they return boolean values. Second, to use the result of
  that comparison (a boolean) and do different things in your program depending
  on the result; this is the `if` statement.

- Let's design that function, `choose_hat`.

- **Step 1 type annotation:** `def choose_hat(temp_in_f: float) -> str:`.
  Since the result should be the hat I'm wearing, I'll return a `str`.

- **Step 2 doc string:** `"""determines appropriate head gear, with above 80F a sun hat, below nothing"""`. Now we want to write our function. But how exactly
  should it work?

- **Step 3 of our design recipe for functions** is to **write down
  examples, in the form of tests cases, of how the function should behave**. In
  Python, we write these in a _test function_: a function whose name starts
  with `test_`, that we put right after the function it tests. Inside, each test
  is an `assert`, which checks that the expression after it is `True`; to check that two
  values are equal, we use `==`. So we end up with this partially written function:

  ```python skip
  def choose_hat(temp_in_f: float) -> str:
      """determines appropriate head gear, with above 80F a sun hat, below nothing"""
      # Missing body of function! That's the last step of the function design recipe.

  def test_choose_hat():
      assert choose_hat(50) == "no hat"
      assert choose_hat(85) == "sun hat"
  ```

- Is there another number we should check? Probably `80` as it's a boundary
  condition (i.e., right on the edge), which are common sources of bugs (what programmers
  call mistakes that cause programs not to behave as desired or expected!). Let's
  add another test for this:

  ```python skip
  def choose_hat(temp_in_f: float) -> str:
      """determines appropriate head gear, with above 80F a sun hat, below nothing"""

  def test_choose_hat():
      assert choose_hat(50) == "no hat"
      assert choose_hat(85) == "sun hat"
      assert choose_hat(80) == "sun hat"
  ```

- Now, we can proceed to **Step 4 of our design recipe**, which is to write code:

  ```python error
  def choose_hat(temp_in_f: float) -> str:
      """determines appropriate head gear, with above 80F a sun hat, below nothing"""
      if temp_in_f > 80:
          return "sun hat"
      else:
          return "no hat"

  def test_choose_hat():
      assert choose_hat(50) == "no hat"
      assert choose_hat(85) == "sun hat"
      assert choose_hat(80) == "sun hat"
  ```

- Note how each branch of the `if` is indented under it, and each has its own
  `return`.

- Now when we click **PLL: Run Python File**, PLL first runs the tests and reports the results.
  We can see our test fails. What went wrong? (Note that a test function stops at
  its first `assert` that fails, so if there were more `assert`s after that one,
  they wouldn't have been checked.)

- We can think about what happened to "debug" (i.e., the programmers term
  for finding & removing bugs!) our code, but we can also use another tool, called `print`, to help figure out the cause of the problem.
  This allows us to see values as code is running. Given any number of values, separated by commas, `print` shows them, with spaces between them.
  So we can print a label (a string), and then the value of an identifier, i.e.:

  ```python error
  def choose_hat(temp_in_f: float) -> str:
      """determines appropriate head gear, with above 80F a sun hat, below nothing"""
      print("temp_in_f:", temp_in_f)
      if temp_in_f > 80:
          return "sun hat"
      else:
          return "no hat"

  def test_choose_hat():
      assert choose_hat(50) == "no hat"
      assert choose_hat(85) == "sun hat"
      assert choose_hat(80) == "sun hat"
  ```

- Whatever is printed while a test runs is shown with that test's results.

- But probably we also want to know the value of _comparison_. We can either define a new name for that:

  ```python error
  def choose_hat(temp_in_f: float) -> str:
      """determines appropriate head gear, with above 80F a sun hat, below nothing"""
      comparison = temp_in_f > 80
      print("temp_in_f:", temp_in_f)
      print("comparison:", comparison)
      if comparison:
          return "sun hat"
      else:
          return "no hat"

  def test_choose_hat():
      assert choose_hat(50) == "no hat"
      assert choose_hat(85) == "sun hat"
      assert choose_hat(80) == "sun hat"
  ```

- Or, we can print the value of the expression directly, without giving it a name:

  ```python error
  def choose_hat(temp_in_f: float) -> str:
      """determines appropriate head gear, with above 80F a sun hat, below nothing"""
      print("temp_in_f:", temp_in_f)
      print("comparison:", temp_in_f > 80)
      if temp_in_f > 80:
          return "sun hat"
      else:
          return "no hat"

  def test_choose_hat():
      assert choose_hat(50) == "no hat"
      assert choose_hat(85) == "sun hat"
      assert choose_hat(80) == "sun hat"
  ```

- The difference between the last two is that in the former, `comparison` is
  added to the program directory inside `choose_hat`, but in the latter, 
  no new name is added: the comparison is only computed to be printed.

- Now if we run again, we can see what went wrong: our comparison is checking that `temp_in_f` is
  strictly greater than `80`, but our test shows what we want it to be greater
  than *or equal to* 80.

## Wrap-up (10 mins)

- There is a useful **order** we should carry out when defining new functions, and we
  can make this concrete as a Design Recipe for functions:

  - Step 1. **Type Annotation** - Once we have decided we need to write a function, the
    first thing we should think about, assuming we were not told it, is what
    type of inputs the function should take and what type of output it should
    produce. While we introduced type annotations as a way to get better error
    messages, and indeed they are, this use as part of a design process is
    indeed much more important: it helps us organize our thoughts!

  - Step 2. **Doc String** - After figuring out the types of data the function operates
    over, it is worth writing down what the function should do! This is written in
    English, and it doesn't need to include how the function works (and usually
    shouldn't); the purpose of the explanation is so that someone can
    understand how to **use** the function, not how it works internally. While
    this serves as useful documentation, it is even more useful as part of a
    design process, since like type annotations, it helps us organize our
    thoughts; in particular, it makes us think a little bit more concretely about
    how the code should work -- i.e., how is the output constructed from the input.

  - Step 3. **Tests:** The third step is writing tests in a test function (`test_...`) right after the function. These tests (or examples)
    serve as the most concrete step of our design process, as it's the point where we think through concrete cases of inputs, and exactly the output they should produce.
    It may be, as we write them, that we realize we did not think of something in the
    earlier steps, which is fine -- we go back and fix those and then continue forward.
    In addition to forming a useful step in the design process, these tests will also
    be used to check that our function works as expected!

  - Step 4. **Code** -- The last step, which we should only do **after** the first three, is writing
    down the code. There is a strong tendency for students, especially beginners, to want
    to jump ahead to this step, but the clarity that comes from doing the earlier steps will make
    writing the code easier, to the point that it is faster to not skip ahead.
