## Reading

In data analysis, we often work with datasets that someone else collected, and
that don't come in a form we can use right away: some data might be missing, or
entered incorrectly. As a concrete example, imagine you do data analysis for a
company that sells tickets to events. People buy tickets through an online
form, and the form software creates a spreadsheet with everything they entered.
Here it is, saved as a CSV file:

```
Name,Email,Num Tickets,Discount Code,Delivery,Zip Code
Josie Zhao,jo@mail.com,2,BIRTHDAY,email,90210
Sam Ochibe,s@sweb.com,1,,pickup,30301
Bart Simple,bart@simpson.org,5,STUDENT,yes,60614
Ernie O'Malley,ernie.mail.com,0,none,email,10001
Alvina Velasquez,alvie@schooledu,3,student,emall,73301
Zander,zandaman,10,,email,02115
Shweta Chowpatti,snc@this.org,three, ,pickup,02903
```

What do you notice that might affect using these data in an analysis, or for
managing an event? Some issues jump out quickly: the `three` in the
`Num Tickets` column, differences in capitalization in the `Discount Code`
column, and the use of both `none` and blank cells in that column (you may have
spotted more). Before we do any analysis, we need to clean up the data, so that
our analysis will be reliable.

### Cleaning Data Tables

#### Loading Data Tables

The first step in working with an outside data source is to load it into your
program. As we saw on [Day 7](/days/7), `load_table` does this, given either a
web address or the name of a file in the same folder as your program:

```python
event_data_orig = load_table("https://raw.githubusercontent.com/neu-pdi/cs2000-public-resources/refs/heads/main/static/support/dcic-events-orig.csv")
```

The names of the columns come from the first line of the CSV file. Every cell is
loaded as a string, even if it looks like a number, so `load_table` doesn't
report a problem with `"three"`: `"2"` and `"three"` are both strings. The
inconsistency will resurface, however, as soon as we try to use the column as
numbers.

#### Dealing with Columns with Multiple Types of Data

Well-formed data should not mix types of data within a single column. A small
program could correct some inconsistencies, for example by removing data that
don't have the expected type, but only after careful study of the data, to make
sure we aren't throwing out useful information that was simply entered
incorrectly (like `three`). So we recommend fixing this sort of error in the
source file, before loading the data into Python (or any other tool). If you got
the data from someone else (who might also send you updates to them), make a
copy and clean up the copy, so you still have the original if you need it. For
the events data, a copy with the `three` replaced by `3` is in
`dcic-events-data.csv`, which we'll use from here on.

#### Dealing with Missing Entries

When we create a table with `table(...)`, we have to give a value for every
cell, but in a spreadsheet, cells can be left empty. What happens when we load a
table with empty cells, like those in the `Discount Code` column?

```python
event_data_raw = load_table("https://raw.githubusercontent.com/neu-pdi/cs2000-public-resources/refs/heads/main/static/support/dcic-events-data.csv")

event_data_raw.row(1)["Discount Code"]  # -> ''
event_data_raw.row(6)["Discount Code"]  # -> ' '
```

Sam's cell (row 1) had no data at all, so it holds the empty string. Shweta's
(row 6) _appears_ empty, but it actually contained a space, and Python keeps the
actual content of the cell. What about Ernie's discount code, `"none"`: how is
that different from Sam's `""`?

The right way to address missing data (and conversion in general) is to convert
columns after loading, using `transform_column`. `int` (or `float`) converts
strings of digits to numbers, and causes an error (a `ValueError`) if a cell
cannot be interpreted as a number:

```python
event_data = event_data_raw.transform_column("Num Tickets", int)
```

Leave columns that should stay strings (like names, emails, discount codes, and
zip codes) unconverted. Aren't zip codes numbers, though? Try converting the
`Zip Code` column with `int`, and spot the difference. Zip codes are written
with digits, but aren't meant to be used numerically: what sense would it make
to multiply one by 3? And they can meaningfully start with 0 (`int("02115")` is
`2115`). Treating zip codes as strings treats them as identifiers more than
numbers (more on this on [Day 12](/days/12)).

**A note on default values:** no single default for missing or invalid cells
makes sense for all the ways numbers are used: `0` is plausible for a missing
number of tickets, but not for a missing age, and it could create outright
errors for a missing exam grade (later used to compute a course grade). That's
why `int` reports an error when a cell can't reliably be interpreted as a
number. When a default _is_ appropriate, a helper can choose it, using `try` /
`except` like `earnings_to_number` on [Day 9](/days/9):

```python
def string_to_int(s: str, default: int) -> int:
    """converts s to a whole number, or produces default if s does not represent one"""
    try:
        return int(s)
    except ValueError:
        return default

def test_string_to_int():
    assert string_to_int("3", 0) == 3
    assert string_to_int("three", 0) == 0
    assert string_to_int("", 0) == 0
```

To use it with `transform_column`, give it a `lambda` that supplies the default:
`lambda s: string_to_int(s, 0)`. Rule of thumb: when you load a table, convert
numeric columns with `transform_column`, so that missing or malformed data is
handled explicitly, rather than silently.

#### Normalizing Data

Next, the `Discount Code` column. We want to answer "How many orders were placed
under each discount code?" Looking in the [Tables](/pll/tables) documentation
for something that might help, we find `freq_bar_chart` (from
[Day 10](/days/10)): one bar for each different value in a column, as tall as
the number of rows that have that value.

Examples first! What chart do we _want_, for the data above? You can't answer
without deciding how to standardize the codes, and how to handle missing values.
_Normalization_ means making sure that a collection of data (such as a column)
shares structure and formatting. We'll aim for three bars: `BIRTHDAY` (height
1), `STUDENT` (height 2), and `none` (height 4), though you could have made
different choices. `freq_bar_chart` will produce that, as long as every cell in
the column has a value, and the only values are the ones we want bars for. So we
need to:

- put `"none"` in every cell that currently lacks a value
- convert all the codes that aren't `"none"` to upper case

Both are column transformations, which we can capture in one function:

```python
def cell_to_discount_code(s: str) -> str:
    """uppercases all strings other than none, and converts blank cells to none"""
    if s == "" or s == "none":
        return "none"
    else:
        return s.upper()

def test_cell_to_discount_code():
    assert cell_to_discount_code("") == "none"
    assert cell_to_discount_code("none") == "none"
    assert cell_to_discount_code("birthday") == "BIRTHDAY"
    assert cell_to_discount_code("Birthday") == "BIRTHDAY"
```

Is this a good set of examples, or are any key ones missing? They consider
different capitalizations of `"birthday"`, but not of `"none"`. Unless you are
confident that the data can't contain those, we should add one to the test
function:

```python error
    assert cell_to_discount_code("NoNe") == "none"
```

Oops! This test fails. Why? Since the `if` checks for the string `"none"`, we
need to normalize the input to match what it expects: with the condition
`s == "" or s.lower() == "none"`, all the examples pass. Using the function with
`transform_column` standardizes the discount codes, and then we can make our
chart:

```python
discount_fixed = event_data.transform_column("Discount Code", cell_to_discount_code)
discount_fixed.freq_bar_chart("Discount Code")
```

Try it yourself: normalize the `Delivery` column, so that all `"yes"` values are
converted to `"email"`.

Our chart has _four_ bars: the three we wanted, and one for `" "`. Where did

#### Normalization, Systematically

We need to think through potential normalizations systematically. When writing
examples, we think about the ways that inputs might vary; for loaded datasets,
that means thinking about _how the original data were collected_. Based on what
you know about websites, how might the discount codes have been entered, and
what mistakes does that make plausible?

A web form likely used either a drop-down menu or a text-entry box. A drop-down
menu automatically normalizes the data (which is why you should use one when
users select from a fixed collection of options), so let's assume a text-entry
box. Then any typical typing error could show up: swapped letters, missing
letters, leading spaces, capitalization, etc., or even something random, typed
just to see what the form would do.

Which of these can a program correct automatically? Swapped and missing letters
are the sorts of things a spell-checker might fix (especially if it knew all the
valid discount codes). Random junk, by definition, is random: you'd have to ask
the events company how they want it handled (convert it to `"none"`, reach out
to the customer, etc. -- these are questions of _policy_, not of programming).
But really, the moral is to use drop-downs or other means to prevent incorrect
data at the source whenever possible.

With experience, you'll learn to anticipate certain kinds of errors (like cells
that appear empty), which is one reason why good data scientists have to
understand the domain they work in. The takeaway is how we talked through what
to expect: where the data came from, and what errors are plausible there. A
clear _error model_ helps you write more robust programs (such _adversarial
thinking_ is also a core skill in security).

Try: modify `cell_to_discount_code` so that strings containing only spaces
(which look just like `""` in a spreadsheet) are also converted to `"none"`.
(Hint: `s.replace(" ", "")`, like the `s.replace(",", "")` in
`earnings_to_number`, removes all the spaces from `s`.)

#### Using Programs to Detect Data Errors

We can also look for errors by writing functions that check whether a table
contains unexpected values. For the `Email` column, let's say (in an admittedly
outdated, limited, and US-centric way) that a valid email address contains an
`@` sign, and ends in one of `.com`, `.edu`, or `.org`. Try writing a function
`is_email` that takes a string and checks both rules (`"@" in s` checks whether
`s` contains `"@"`, and `s.endswith(".com")` whether it ends with `".com"`). For
more of a challenge, also require some character between the `@` and the
ending. Then `event_data.filter(lambda r: not is_email(r["Email"]))` produces
all the rows whose email addresses need to be corrected: programs are often
helpful for finding data that need correcting, even if they can't do the fixing.

## Intro (20 mins)

- Data sources, especially if they are the result of manual entry by people,
  often have minor mistakes in them.
- Sometimes data is missing, othertimes it shows up in different ways.
- Today we'll work with this synthetic example data -- which models a subset of
  the type of data that is available to political campaigns (at least, in the United States) about voters.
- Let's start by loading it in as a table:
  ```python
  voter_data = load_table("https://raw.githubusercontent.com/neu-pdi/cs2000-public-resources/refs/heads/main/static/support/10-voters.csv")
  ```
- If we look at the data, we should notice a few things are off about the data.
- For example, the party affiliation, which is often used to target outreach,
  has one column empty (which is perhaps Independent?), but also, a couple rows
  have typos!
- So if we run `voter_data.filter(lambda r: r["Party"] == "Republican")`
  we see only _two_ rows, despite the original data seeming to have 3. If we
  look really closely we can see that one of the rows is `"Repbulican"` (note
  the typo).
- Let's create a new file in our `cs2000-scratch` repository, `voters.csv`, copy the contents of
  https://raw.githubusercontent.com/neu-pdi/cs2000-public-resources/refs/heads/main/static/support/10-voters.csv (open it in a new tab to copy) into it, and then fix this typo.
- Now we can change the above to load the file, by giving `load_table` its name rather than a URL (this works for any file in the same folder as your program):
  ```python
  voter_data = load_table("voters.csv")
  ```
- When we run the same `filter` expression now, we see the three rows we
  expect.
- Why did we change the source data, rather than trying to fix this in code?
  There are always two possible approaches -- we can normalize (remove
  distinctions between things that are "the same") in the original source, or we
  can do it in code. If there are _mistakes_ in the original data, like that
  typo, it may make sense to fix the data, rather than making our analysis more
  complicated.
- However, in other cases, like the empty Party being treated as Independent, we
  may want to do this in our analysis, but it would likely be a mistake to
  change the data, because it is possible that no party and Independent as a
  party are two different things, and later analysis would want to treat them
  separately. Let's do that.
  ```python
  def blank_to_indep(s: str) -> str:
      """replaces an empty string with Independent"""
      if s == "":
          return "Independent"
      else:
          return s

  def test_blank_to_indep():
      assert blank_to_indep("") == "Independent"
      assert blank_to_indep("blah") == "blah"

  voters_with_indep = voter_data.transform_column("Party", blank_to_indep)
  ```
- Now we can see our new table, where there are no blank party affiliations, but
  we have not removed the original blank from `voters.csv`.
- Even in cases of typos, it may make sense to automate corrections -- e.g., we
  can see several different forms of dates in our table. Manually correcting all
  of them is not wrong, but doing things manually always raises the possibly of introducing errors -- e.g., accidentally deleting a character that changes a date, and not realize it was done (and even without mistakes, it could be time
  consuming), whereas creating a `normalize_date` function would be more
  reliable.
