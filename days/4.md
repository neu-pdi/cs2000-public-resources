## Reading

### Example: Similar Flags

These two expressions draw the flags of Armenia and Austria, which have the same
shape, with different colors (`frame` draws a thin outline around an image):

```python
# Lines starting with # are comments, for human readers:
# Python ignores everything on a line after #.

# armenia
frame(above(rectangle(120, 30, "solid", "red"),
            above(rectangle(120, 30, "solid", "blue"),
                  rectangle(120, 30, "solid", "orange"))))

# austria
frame(above(rectangle(120, 30, "solid", "red"),
            above(rectangle(120, 30, "solid", "white"),
                  rectangle(120, 30, "solid", "red"))))
```

Rather than writing this twice, it would be nice to write the common part once,
and just change the colors for each flag, with a custom operation that we could
use like this:

```python
# armenia
three_stripe_flag("red", "blue", "orange")

# austria
three_stripe_flag("red", "white", "red")
```

Python has no such operation, since it is specific to our program, so we need to
add our own operations (from now on, called _functions_).

### Defining Functions

A _function_ takes one or more (configuration) _parameters_, and uses them to
produce a result. If we have several expressions that are identical except for a
few values, we create a function from them like this:

1. Write down at least two expressions showing the desired computation (here,
   the ones for the two flags).
2. Identify which parts are fixed (the `120` by `30` rectangles, stacked with
   `above`) and which are changing (the stripe colors).
3. Give each changing part a name (say, `top`, `middle`, and `bottom`): this is
   the parameter that stands for that part.
4. Rewrite the examples in terms of these parameters (e.g., replacing `"red"`,
   `"blue"`, and `"orange"` with `top`, `middle`, and `bottom`).
5. Name the function something suggestive, like `three_stripe_flag`.
6. Write the syntax for functions around the expression:

   ```
   def <function name>(<parameters>):
       return <the expression goes here>
   ```

   The indented lines after the `def` line are the function's _body_, and
   `return` says what value it produces. (The angle brackets mean "replace with
   something appropriate": they aren't part of the notation.)

Here's the result:

```python
def three_stripe_flag(top, middle, bottom):
    return frame(above(rectangle(120, 30, "solid", top),
                       above(rectangle(120, 30, "solid", middle),
                             rectangle(120, 30, "solid", bottom))))
```

This looks like a lot of work now, but with practice, the steps will become so
natural that you won't need to start from several similar expressions. Now, we
can make (and name) our flags:

```python
armenia = three_stripe_flag("red", "blue", "orange")
austria = three_stripe_flag("red", "white", "red")
```

When we provide values for a function's parameters to get a result, we are
_calling_ the function, and `three_stripe_flag("red", "blue", "orange")` is a
_call_. (If your file already defines `armenia` or `austria`, PLL will report a
reassignment: use a different name, like `austria2`, or turn the earlier
definition into a comment by putting `#` in front of it.)

#### How Functions Evaluate

So far, we know how Python evaluates expressions, definitions (adding an entry
to the directory), and names (looking them up in the directory). Now we need two
more rules:

- When Python reaches a function definition, it makes an entry in the directory
  associating the function's name with its code. The body is _not_ evaluated
  yet.
- When Python reaches a function call, it evaluates the function's body, with the
  values given in the call substituted for the parameters' names.

For example, for `three_stripe_flag("red", "blue", "orange")`, Python takes the
expression returned by the body, and substitutes the parameters' values into it:

```python
frame(above(rectangle(120, 30, "solid", "red"),
            above(rectangle(120, 30, "solid", "blue"),
                  rectangle(120, 30, "solid", "orange"))))
```

then evaluates that, producing the flag. This is exactly the expression we
started with for Armenia: substitution gets it back, while letting us write the
shorthand.

#### Type Annotations

What if we called `three_stripe_flag(50, "blue", "red")` by mistake? `50` isn't
a color, but Python substitutes it for `top`, giving
`rectangle(120, 30, "solid", 50)`. What happens then is up to `rectangle`: at
best, an error about that call to `rectangle`; at worst, a wrong picture, with no
error at all. Either way, someone using your function would be confused: they
didn't write anything about rectangles! It would be better to report a problem
with the call to `three_stripe_flag` itself.

You can make that happen by _annotating_ each parameter with the type of value it
expects (here, strings), and the function's output with its type, after the
`->`, changing the first line of the definition to:

```
def three_stripe_flag(top: str, middle: str, bottom: str) -> Image:
```

This is the notation we saw for contracts in the documentation: the parameter's
name, a colon, and a type (so far, `int`, `float`, `str`, or `Image`). Try the
mistaken call again with this definition: now PLL reports that
`three_stripe_flag` expects `top` to be a string. Python runs functions without
annotations, but we always write them: they let PLL report errors more
precisely, and tell human readers how to use the function.

#### Documentation

Would you remember, a couple of months from now, what `three_stripe_flag` does?
The name doesn't say that the stripes are stacked (not side by side), or that
they are the same height: names can't carry that much information. So
programmers also write a _docstring_, a short, human-language description of what
the function does. In Python, it's a string on the first line of the body, with
three double quotes on each side:

```python
def three_stripe_flag(top: str, middle: str, bottom: str) -> Image:
    """produce image of flag with three equal-height horizontal stripes"""
    return frame(above(rectangle(120, 30, "solid", top),
                       above(rectangle(120, 30, "solid", middle),
                             rectangle(120, 30, "solid", bottom))))
```

You should always write one: they are extremely helpful to anyone who reads your
program, whether a co-worker, a grader, or you, a couple of weeks from now.

### Functions Practice: Moon Weight

Suppose we're outfitting astronauts for lunar exploration, and need to know how
much each will weigh on the Moon, where objects weigh one-sixth of their weight
on Earth. Here are the expressions for a few astronauts (in pounds):

```python
100 * 1/6
150 * 1/6
90 * 1/6
```

This time, rather than _noticing_ repetition, we _expect_ to do this
computation many times (once per astronaut), and writing it over and over, we'd
sooner or later make a typo ("DRY": "don't repeat yourself"). Following our
steps, the fixed part is `* 1/6`, and the changing part is the weight on Earth,
which we name `earth_weight`. With a suggestive name, types, and a docstring, we
get:

```python
def moon_weight(earth_weight: float) -> float:
    """Compute weight on moon from weight on earth"""
    return earth_weight * 1/6
```

### Functions Practice: Cost of Pens

Let's make one more function: the total cost of an order of pens with slogans (or
messages) printed on them. Each pen costs 25 cents, plus 2 cents per character in
the message (counting spaces). We start with two concrete expressions:

```python
# ordering 3 pens that say "wow"
3 * (0.25 + len("wow")*0.02)

# ordering 10 pens that say "smile"
10 * (0.25 + len("smile")*0.02)
```

`len` takes a string and produces the number of characters in it (including
spaces and punctuation). This time, _two_ things differ between the examples:
the number of pens (a whole number, so an `int`) and the message, so our
function has two parameters. The cost can have cents, so it's a `float`
(written with a decimal _point_: `0,02` doesn't work). A docstring can continue
onto another line:

```python
def pen_cost(num_pens: int, message: str) -> float:
    """total cost for pens, each 25 cents
    plus 2 cents per message character"""
    return num_pens * (0.25 + len(message)*0.02)
```

### Recap: Defining Functions

Functions let us write a computation once, and configure it with different
concrete values each time we use it: `pen_cost(10, "Welcome")`, then
`pen_cost(100, "Go Huskies!")`. A function has a _name_, _parameters_ (names for
the values we configure it with), and a _body_, which `return`s what it
produces; we annotate its parameters and its result with their types, and
describe what it does in a docstring. Running a function definition adds it to
the directory (showing nothing); calling it evaluates its body, with the values
we gave substituted for its parameters.

## Intro (10 mins)

- Functions allow us to express repeated expressions that differ in some way.

- e.g., I can write a function that says "Welcome to class, " and then someone's
  name, and then use it for many different people.

  ```python
  def welcome(name):
      return "Welcome to class, " + name
  ```

- The function starts with `def`, then its name, then the names of its
  arguments in parentheses, and then a colon. The _body_ of the function is the
  lines after that, which are indented (by four spaces), and `return` says what
  value the function produces.

- Just like definitions, functions are added to the program directory. When you
  use a function: `welcome("some-name")` (ask for a name from the room)
  the expression evaluates to what the body of the function returns, with the
  arguments added to a **_local_ version of the program directory used just while the function is running**.

- i.e., in the above example, at the start of the program, the program directory
  is empty. (DRAW A DIAGRAM) After evaluating the `def`, the program
  directory now has a single entry, which associates `welcome` to a function
  value. Evaluating `welcome("some-name")` next turns into `"Welcome to class, " + name`, but with `name -> "some name"` added to the program directory
  temporarily. Now when we evaluate the expression, `name` will be replaced with
  "some-name" and then the two strings will be put together. After that string
  is produced, as a value, the body of the function has ended, and thus `name` is
  removed from the program directory. This means that if you try to use `name`
  after, it won't work.

- Observe what happens if you call `welcome` with a number. You get an error,
  but where is the error pointing to?

- The issue is that since `welcome` doesn't indicate anything about the
  type of argument it expects, the error that Python reports is from inside --
  in a call to `+` -- when really, the problem is the call to
  `welcome`.

- To fix this, we should put **type annotations** on all functions we write --
  both to clarify to ourselves (and other people reading the code) what type of values we expect, but
  also to allow PLL to report better errors in case of mistakes. We should also
  indicate the type of value we are going to return!

  ```python
  def welcome(name: str) -> str:
      return "Welcome to class, " + name
  ```

- Now if we call `welcome` with a number, PLL reports that the problem is the
  call to `welcome`, since the argument didn't match the annotation.

- This is another example of Design -- and is the **first step of our actual
  design recipe for functions**. All **functions should have type annotations, and
  they should actually be the _first_ thing that we figure out**, as until we
  understand the type of data that we are working with, trying to do anything
  else is likely not going to go well.

- Another thing that all functions should have, and the **second step in our
  design recipe, is a "documentation string" (or docstring)** -- this is a
  concise, English explanation of what the purpose of the function is. Not
  necessarily how it works (though the distinction is subtle), but what someone
  who wants to use it needs to know.

- In Python, the docstring is a string written as the first line of the body of the
  function, with three double quotes on each side. Further refining our example:

  ```python
  def welcome(name: str) -> str:
      """Returns a greeting addressed to the given person"""
      return "Welcome to class, " + name
  ```

## Wrap-up (10 mins)

- Functions allow us to not repeat ourselves; more importantly, **they are our first, and in this class, primary, example of a mechanism for abstraction** -- i.e., building a re-usable piece of a program, that has internals that are not visible to other parts of the program. **Abstraction is one of, if not the most, important ideas in computer science.**
- Type annotations allow us to clarify and communicate what kind of input each parameter expects and the kind of output the function will return.
- Docstrings communicate what the function does in a clear, simple way.
- These serve both as a guide to others, but more importantly, as a guide to
  YOU! As thinking through the inputs / outputs **before** writing the function,
  and describing what the function should do, helps you figure out how to
  implement it.
