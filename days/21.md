## Reading

On [Day 19](/days/19), we used `match` to tell apart the variants of
conditional data, and on [Day 20](/days/20), to tell apart empty and non-empty
lists. This suggests that lists are also conditional data, just built into
Python. Indeed, this is the case.

To see this, let's define a new type `NumList`, for lists of numbers, with two
variants: `NlEmpty`, for the empty list, and `NlLink`, for a non-empty one. Try,
before reading on: what fields should `NlLink` have, and what are their types?

A non-empty list has two parts: its first element, and the rest of the list, so
`NlLink` needs two fields, `first` and `rest`. Since we're making a list of
numbers, `first` should be a `float`. What about `rest`? It needs to be a list
of numbers, so its type should be `NumList`:

```python
from dataclasses import dataclass

@dataclass
class NlEmpty:
    pass

@dataclass
class NlLink:
    first: float
    rest: "NumList"

NumList = NlEmpty | NlLink
```

(Since `NumList` isn't defined until after the two classes, we write its name
in quotes inside them.) Notice something new here: the type of the `rest` field
is the very type, `NumList`, that we are defining. Does that actually work?
Yes. To build a list of 2, 7, and 3 (in that order), we start with `NlEmpty()`,
which is a valid `NumList`, and use `NlLink` to add the numbers onto it:

```python
NlEmpty()
NlLink(3, NlEmpty())
NlLink(7, NlLink(3, NlEmpty()))
NlLink(2, NlLink(7, NlLink(3, NlEmpty())))
```

Each `rest` is itself a valid `NumList`. Defining data in terms of itself
works because, to build actual data, we have to start with `NlEmpty()`, which
doesn't refer to `NumList`.

Data definitions with fields of the same type are called _recursive data_.
They are powerful because they let us create data that is _arbitrarily sized_:
given a `NumList`, we can always make a larger one with `NlLink`. So we have to
handle larger lists, like:

```python
NlLink(1,
  NlLink(2,
    NlLink(3,
      NlLink(4,
        NlLink(5,
          NlLink(6,
            NlLink(7,
              NlLink(8,
                NlEmpty()))))))))
```

### Functions to Process Recursive Data

Let's write a function `contains_3`, which returns `True` if a `NumList`
contains `3`, and `False` otherwise. First, the header and some tests:

```python
def contains_3(nl: NumList) -> bool:
    """returns True if nl contains 3, False otherwise"""
    ...

def test_contains_3():
    assert not contains_3(NlEmpty())
    assert contains_3(NlLink(3, NlEmpty()))
    assert contains_3(NlLink(1, NlLink(3, NlEmpty())))
    assert contains_3(NlLink(1, NlLink(2, NlLink(3, NlLink(4, NlEmpty())))))
    assert not contains_3(NlLink(1, NlLink(2, NlLink(5, NlLink(4, NlEmpty())))))
```

We use `match` to tell the variants apart, and since we will need the fields
of `NlLink` to compute a result in that case, we list them in the initial
outline (it isn't code that can run yet, so we write it in comments):

```python
# def contains_3(nl: NumList) -> bool:
#     match nl:
#         case NlEmpty():
#             ...
#         case NlLink(first, rest):
#             ... first ...
#             ... rest ...
```

Following our examples, the answer must be `False` in the `NlEmpty` case. In
the `NlLink` case, if `first` is `3`, the answer is `True`. That only leaves
the case where the argument is an `NlLink` whose first element isn't `3`:

```python
def contains_3(nl: NumList) -> bool:
    """returns True if nl contains 3, False otherwise"""
    match nl:
        case NlEmpty():
            return False
        case NlLink(first, rest):
            if first == 3:
                return True
            else:
                ...  # handle rest here
```

Since `rest` is a `NumList` (from the data definition), we could use another
`match` on it, just like the first one:

```python
            else:
                match rest:
                    case NlEmpty():
                        return False
                    case NlLink(first_of_rest, rest_of_rest):
                        if first_of_rest == 3:
                            return True
                        else:
                            ...  # handle rest_of_rest here
```

And `rest_of_rest` is a `NumList` too, so we could write a `match` for it... See
where this is going? Not anywhere good. We can copy this `match` as many times
as we want, but we can never answer the question for a list that is just one
element longer than the number of copies.

So let's go back to where the problem began, at `# handle rest here`. We need
to know whether `rest`, a perfectly valid `NumList`, contains `3`. And we have a
function (or, most of one) whose job is to figure out exactly that:
`contains_3`! We ought to be able to call it with `rest`:

```python
def contains_3(nl: NumList) -> bool:
    """returns True if nl contains 3, False otherwise"""
    match nl:
        case NlEmpty():
            return False
        case NlLink(first, rest):
            if first == 3:
                return True
            else:
                return contains_3(rest)
```

And lo and behold, all of the tests pass. It's useful to step through a call,
like `contains_3(NlLink(1, NlLink(3, NlEmpty())))`. As with any function call,
we substitute the argument for `nl`. The `NlLink` case matches, so we
substitute its parts for `first` (`1`) and `rest` (`NlLink(3, NlEmpty())`), and
run:

```python
if 1 == 3:
    return True
else:
    return contains_3(NlLink(3, NlEmpty()))
```

Since `1 == 3` is `False`, we run the `else` part, another call:
`contains_3(NlLink(3, NlEmpty()))`, on the `rest` of the original input. Again
the `NlLink` case matches, this time with `first` being `3`:

```python
if 3 == 3:
    return True
else:
    return contains_3(NlEmpty())
```

This time `3 == 3` is `True`, so this call returns `True`, and so does the
original call, which returns whatever this call returns.

Notice that the trace reached `contains_3(NlLink(3, NlEmpty()))`, a normal call
to `contains_3` that could even be a test on its own. The function works by
doing something (checking for `3`) with the non-recursive part of the data, and
combining that with the result of the same function on the recursive part.

### A Template for Processing Recursive Data

Stepping back, we have derived a new way to write functions over recursive
data. On [Day 20](/days/20), we used substitution across a sequence of examples
to get a function that calls itself on the rest of the list. Here, we got that
structure _from the shape of the data itself_: we break the data into its
variants (with `match`), pull out the fields of each variant, and call the
function itself on any recursive fields (fields of the same type). For
`NumList`, this gives:

```python
# def num_list_fun(nl: NumList) -> ...:
#     match nl:
#         case NlEmpty():
#             ...
#         case NlLink(first, rest):
#             ... first ...
#             ... num_list_fun(rest) ...
```

The generic name `num_list_fun` shows that this outline is for _any_ function
that processes a `NumList`. We call it a _template_. Every data definition has
one, capturing how to break a value into cases, pull out the fields, and use
the same function on any recursive fields.

**Strategy: Writing a Template for Recursive Data.** Given a recursive data
definition:

1. Create a function header (using a general-purpose placeholder name if you
   aren't yet writing a specific function).
2. Use `match` to break the recursive-data input into its variants.
3. In each case, list each of its fields in the answer portion of the case.
4. Call the function itself on any recursive fields.

The power of the template is its universality: to write a specific function
(like `contains_3`), copy the template, replace the generic name with your
function's, and fill in the `...`s. When you see a recursive data definition
(there will be _many_ in this course), start thinking about what the recursive
calls will return, and how to combine their results with the non-recursive
parts of the data. Working out a sequence of examples and filling in the
template both get you to the same function, but the template scales to more
complicated data definitions, where writing examples by hand would be tedious.

### The Design Recipe

We've shown you many techniques for designing programs: developing examples,
writing tests, and now writing and using templates. Putting them together gives
a _design recipe_ (adapted from the one in
[_How to Design Programs_](https://htdp.org/)) for designing recursive
functions. Given a programming problem over recursive data:

1. Write the function header: its name, its contract (the types of its inputs
   and output, as annotations), and a docstring. The name is needed for
   recursive calls, while the contract guides the design of the body.
2. Guided by the contract, write several examples of inputs and outputs, as
   tests, using _concrete_ data. Include examples where the input of one
   extends the input of another.
3. From the definition of the input's data type, write out its template.
4. Adapt the template to this problem, using your examples (you should have one
   for each case) to fill in each case. Where one example's input extends
   another's, the difference in the outputs becomes the function body, as on
   [Day 20](/days/20).
5. Run your examples to make sure your function behaves as you expect.
6. Write more fine-grained tests: the examples (written before the body) focus
   on input-output behavior, but now that you have an implementation, write
   tests that focus on its details.

## Intro (15 mins)

- We can define our own list definitions, specialized to numbers, as (since
  `NumList` isn't defined until after the two classes, we write its name in quotes where we use it inside of them):
  ```python
  from dataclasses import dataclass

  @dataclass
  class NlEmpty:
      pass

  @dataclass
  class NlLink:
      first: float
      rest: "NumList"

  NumList = NlEmpty | NlLink
  ```
- And use it as:
  ```python
  NlEmpty()
  NlLink(3, NlEmpty())
  NlLink(7, NlLink(3, NlEmpty()))
  NlLink(2, NlLink(7, NlLink(3, NlEmpty())))
  ```
- When defining functions over `NumList`s, writing a series of examples (as we
  did last time) leads us to a general pattern (or template) of a solution (the template isn't code that can run, so we write it in comments):
  ```python
  # def num_list_fun(nl: NumList) -> ...:
  #     match nl:
  #         case NlEmpty():
  #             ...
  #         case NlLink(first, rest):
  #             ... first ...
  #             ... num_list_fun(rest) ...
  ```
- i.e., a function over a `NumList` will proceed by cases on whether the
  `NumList` is an `NlEmpty` or an `NlLink`, and in the case that it is an
  `NlLink`, we may use the `first` field, but on the `rest` we will likely call
  the function recursively.
- **Any data definition can have a similar function template written for it**:
  1. Create a function header (using a general-purpose placeholder name if you aren’t yet writing a specific function).
  2. Use `match` to break the recursive-data input into its variants.
  3. In each case, list each of its fields in the answer portion of the case.
  4. Call the function itself on any recursive fields.
- For example, we can use the template to write a function that counts the number of `7`s in a `NumList`:
  ```python
  def num_7s(nl: NumList) -> int:
      match nl:
          case NlEmpty():
              return 0
          case NlLink(first, rest):
              if first == 7:
                  return num_7s(rest) + 1
              else:
                  return num_7s(rest)

  def test_num_7s():
      assert num_7s(NlEmpty()) == 0
      assert num_7s(NlLink(0, NlEmpty())) == 0
      assert num_7s(NlLink(7, NlEmpty())) == 1
      assert num_7s(NlLink(0, NlLink(7, NlEmpty()))) == 1
      assert num_7s(NlLink(0, NlLink(7, NlLink(7, NlEmpty())))) == 2
  ```

## Wrap-up (5 mins)

- Data has structure, which can be used to guide how we implement functions.
- We can write function templates based on that structure, which is a helpful
  starting point.
