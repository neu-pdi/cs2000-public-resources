### Naming Values

The expressions that create images involve a bit of typing: it would be nice to
"name" images, and refer to them by their names. Put this in your file, click
**PLL: Run Python File**, and then enter `red_circ` at the prompt:

```python
red_circ = circle(30, "solid", "red")
```

You should see the red circle. In general, `NAME = EXPRESSION` associates the
value of `EXPRESSION` with `NAME`, and anytime you then write `NAME`, Python
replaces it with that _value_: if you write `x = 5 + 4`, then `x`, you get `9`
(not `5 + 4`).

What if you enter a name that you haven't associated with a value, like
`puppy`? Try it: Python reports a `NameError`, since `puppy` hasn't been
associated with (or _bound_ to) a value.

#### Names Versus Strings

We have now seen words used in two very different ways: as data, in strings, and
as names for values (also called _identifiers_).

- We tell them apart by the double quotes: `puppy` is a name, `"puppy"` a string.
- Strings can contain spaces, but names can't: `"hot pink"` is a valid piece of
  data, but `hot pink` is not a single name. To make one name from several
  words, we separate them with underscores, as in `red_circ`.
- Entering `puppy` asks Python to look up the value stored under that name,
  while entering `"puppy"` just writes down a piece of data (like typing `3`).
- A name you haven't defined causes an error, but a string you've never used
  before is fine: strings are just data.

#### Expressions versus Statements

Definitions tell Python to associate names with values; expressions tell Python
to perform a computation and give back the result. Enter each of these at the
prompt:

```python
5 + 8
x = 14 + 16
triangle(20, "solid", "purple")
blue_circ = circle(x, "solid", "blue")
```

The first and third are expressions, and Python shows their values; the second
and fourth are definitions, and it shows nothing. We distinguish _expressions_,
which produce values, from _statements_, which instead give some other kind of
instruction. So far, definitions are the only statements we've seen.

Now enter `blue_circ`. It produces a value, so a name on its own is also an
expression. But something must _happen_ when you run a definition: otherwise, how
could you use the name later?

### The Program Directory

When you write a definition, Python makes an entry in an internal _directory_,
which associates names with values. If you write:

```python
width = 30
height = width * 3
```

Python records that `width` has the value `30`. Then, for `height`, it evaluates
`width * 3`: since `width` is a name (not a string), Python looks up its value
in the directory, and substitutes it, giving `30 * 3`, which is `90`. It stores
that in the directory alongside `height`: the _result_ of `width * 3`, not the
expression (this will matter when we use names to avoid doing the same
computation twice). You can't see the directory, so to figure out how a program
works, it can help to write it down on paper. Try it: if your file contains these
two lines, what appears in the interactions panel when you run it, and how does
each line interact with the directory?

```python
name = "Matthias"
"name"
```

What if you then add another definition of a name that's already in the
directory, such as `width = 50`? Giving a name that already has a value a new one
is called _reassignment_. Python allows it, but at the `beginner` level, PLL
rules it out (reporting that `width` is already assigned, and not running the
code), since it is a common cause of bugs. So a name keeps its first value. Later
in the semester, we'll see how, and when, to change the value of a name.

#### Understanding the Run Button

When you click **PLL: Run Python File**, PLL first clears out the directory,
except for the functions that come with Python and PLL. It then runs your file
line by line, starting at the top. If your file contains the definitions of
`width` and `height` above, followed by
`blue_rect = rectangle(width, height, "solid", "blue")`, then afterward, the
directory looks like:

| Name | Value |
| --- | --- |
| `circle`, `rectangle`, ... | PLL's functions |
| `width` | `30` |
| `height` | `90` |
| `blue_rect` | the blue rectangle image |

Any name you then use at the prompt is looked up in the directory: for
`beside(blue_rect, rectangle(20, 20, "solid", "purple"))`, Python looks up
`blue_rect`. Is the purple rectangle in the directory? What about the image with
both rectangles? Neither is: we didn't give them names. If we instead wrote:

<!-- python setup
blue_rect = rectangle(width, height, "solid", "blue")
-->

```python
two_rects = beside(blue_rect, rectangle(20, 20, "solid", "purple"))
```

the image with both rectangles would be in the directory, under `two_rects`
(but the purple rectangle on its own still wouldn't be). Try it: if you did this
at the prompt, then ran your file again, and typed `two_rects`, what would
happen, and why?

### Using Names to Streamline Building Images

Naming values can make it easier to build up complex expressions. Here's a
rotated purple triangle inside a green square:

```python
overlay(rotate(45, triangle(30, "solid", "purple")),
        rectangle(60, 60, "solid", "green"))
```

This can get hard to read. Instead, we can name the shapes first (and here, we
also add another purple triangle on top):

```python
purple_tri = triangle(30, "solid", "purple")
green_sqr = rectangle(60, 60, "solid", "green")

above(purple_tri,
      overlay(rotate(45, purple_tri), green_sqr))
```

This is quicker to read, because the shapes have descriptive names, and we can
use `purple_tri` twice without writing out the `triangle` expression twice. Try
it: how many images appear in the interactions panel when you run this file? Do
you see the triangle and square on their own, or only combined? Why? Then,
rewrite your Armenian flag from [Day 2](/days/2), giving a name to each stripe.

In practice, programmers don't name every image or result: they name the ones
that will be used more than once, or that are important for understanding the
program.

## Intro (15 mins)

- Review the file in the editor for permanent work, the "interactions" panel for testing it, trying things out, etc.
- While we've been using our file to write down expressions, and see them printed out when we click **PLL: Run Python File**, the primary use is actually to write *named* definitions, like:
  ```python
  blue_square = rectangle(40, 40, "solid", "blue")
  ```
- When we run the file, initially, nothing seems to happen, but now if we type `blue_square` in the interactions, we see a blue square image.
- Running caused everything in the file to evaluate, including the `rectangle` expression above, which evaluated to a blue square. The definition statement `blue_square = ...` caused the resulting value to be stored under that name so we can refer to it later.
- Names in Python can contain letters, digits, and underscores (`_`), but no spaces or dashes, so we use underscores to separate words: `blue_square`.
- IMPORTANT: names & strings are different! `"blue_square"` is not the same as `blue_square`.
  - What do you think will happen if you type `puppy` versus `"puppy"` at the prompt?
- We can understand how our programs work, and how definitions work, by understanding how the **program directory** works.
- Every definition statement, written `name = expression` causes `expression` to be evaluated and `name` to be added to the **program directory**, so it can be used later, including in other expressions for other definitions.
- e.g., you can write `radius = 10` and then `area = 3.14 * radius * radius`. If you do those in the other order (TRY IT), it won't work, since the directory won't have the `radius` entry yet -- since the definitions are added in order, the order we define things matters.

## Wrap-up (5 mins)

- Definitions involve the first aspect of program *design*. **Notice how there
  were often many different ways of writing the same program**, some of which were
  easier to understand, easier to modify, and even possibly easier to write.
- One of the main lessons of this class, and indeed this whole curriculum, is
  that **well designed code is something much more important, and often more
  challenging, than just getting code to work**. Of course code has to work, but
  for it to work in real systems, at the scale that we are building them, messy,
  convoluted, or confusing code can make it so hard for people to understand
  what is going on that even getting it to work, as the programs get bigger,
  becomes impossible.
- By focusing on design, from the very beginning, you'll develop skills that will
  help you all the way through, as programs get bigger and bigger!
