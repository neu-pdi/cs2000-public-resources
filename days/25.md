## Reading

We will now study a new kind of data, and the programming style that goes with
it. This will give us both great power and great responsibility.

### Example: Bank Accounts

Imagine that we want to represent bank accounts, where each account has a
(unique) id number and a balance:

```python
from dataclasses import dataclass

@dataclass
class Account:
    id: int
    balance: float

acct1 = Account(8404, 500)
```

Now let's say the account has just earned another 200. We could write
`Account(acct1.id, acct1.balance + 200)`, but this creates a _new_ account: the
balance of `acct1` (`acct1.balance`) is still `500`. If this were our account,
we would be quite sad! Rather, we want to _change_ the balance in the _existing_
account. Data that can be changed are called _mutable_; until now, we have
worked with _immutable_ data, which cannot be altered.

In Python, the fields of a dataclass can always be changed, so `Account` stays
the same. (This also means every programmer has to make sure they don't
accidentally change a field that shouldn't change, like the id number.) To
change a field, we put the field access on the left side of an `=`: for example,
`acct1.balance = 0` sets the balance to zero. Try to figure out how to set it to
`200` more than its previous value. Here's how we combine the pieces, accessing
the value and then setting it:

```python
acct1.balance = acct1.balance + 200
```

We hadn't written any tests above. Suppose we had written one right after making
the account:

```python error
acct1 = Account(8404, 500)

def test_balance():
    assert acct1.balance == 500

acct1.balance = acct1.balance + 200
```

When PLL runs the tests, it first runs the whole file, and only then calls the
test functions. So even though `test_balance` is written before the update, it
fails. If we change it to expect `700`, it passes, but not if we comment out the
update.

We see a new phenomenon: tests that are only _sometimes_ true. This is called
_state_: there is a "state" (a collection of values for the defined names) in
which the balance is `500`, and another in which it is `700`. This is not
limited to testing, which just reflects what is going on as the program runs.
From now on, every instruction runs in some state, and if the values in it
change, the same piece of program text may produce different answers. This
makes programming much harder, and we will have to get used to its subtleties.

### Testing Functions that Mutate Structures

Adding funds to an account is making a deposit. Let's turn our balance-updating
code into a function, `deposit`, that takes the deposit amount as input:

```python
def deposit(ac: Account, amt: float) -> None:
    """adds amt to the account's balance"""
    ac.balance = ac.balance + amt
```

How do we test this? The function doesn't return anything (its return type is
`None`), so there is no result to compare with an expected answer. In general,
tests for functions that use mutation have three or four parts:

1. _Setup_: set up the values to give the function.
2. _Call_: call the function.
3. _Check_: check that the function had the desired effect.
4. _Teardown_: restore data to their expected state.

```python
def test_deposit():
    # Setup
    acct = Account(8200, 150)

    # Call
    deposit(acct, 100)

    # Check
    assert acct.balance == 250
```

Here we don't need a Teardown step, because we created data just for this test;
if we had changed data whose values matter elsewhere, we would need to undo the
changes. Similarly, since other mutations may have changed existing data, Setup
may need to not only create data, but also set existing data to the values the
test expects.

Try writing a test for this function (remember `pytest.approx`):

```python
def add_interest(ac: Account) -> None:
    """increases the account's balance by 2 percent"""
    ac.balance = ac.balance * 1.02
```

### Aliasing

Now suppose our bank allows accounts to be shared by several customers. We
should then separate the information about customers from that of the accounts:

```python
@dataclass
class Customer:
    name: str
    acct: Account
```

Continuing our program (where `acct1` now has a balance of `700`), suppose we
have a second account, and that `acct1` is owned jointly by Elena and Jorge:

```python
acct2 = Account(8405, 350)
elena = Customer("Elena", acct1)
jorge = Customer("Jorge", acct1)
```

Now Elena earns an additional 150. To update the account, we first access it,
with `elena.acct`, and then update it as before:

```python
a = elena.acct
a.balance = a.balance + 150
```

Sure enough, `elena.acct.balance` is now `850` (the original `500`, the `200`
from before, and now the extra `150`). The key question is: _what is Jorge's
balance?_ That is, what is the value of `jorge.acct.balance`? There are two very
reasonable answers:

1. Going by our prose, Jorge's account should also have `850`, because that's
   what it means to "share" an account.
2. Going by the visible code, Jorge's account should still have `700`, because
   the update was made through `elena.acct`, _not_ `jorge.acct`.

Run the code, and see which you get. You'll find that Jorge's account also has
`850`: `elena.acct` and `jorge.acct` are _aliases_, two different "names" for
the exact same datum. We have had shared data before, but until now it didn't
_matter_. With mutation, aliases matter: the balance in `jorge.acct` changed
even though we never made a change using that name, as if `elena.acct`
exhibited spooky action at a distance. Since every field in Python can be
changed, you always have to be on the alert for this.

### Structure Mutation and the Directory

Now that we can mutate data, we need to revise our notion of the program
directory. Here are our definitions again, starting over in a new file (after
the two dataclasses):

```python
acct1 = Account(8404, 500)
acct2 = Account(8405, 350)
elena = Customer("Elena", acct1)
jorge = Customer("Jorge", acct1)
```

What does the directory contain after running them? We might be tempted to
write `Customer("Elena", acct1)` for `elena`, but values in the directory can't
refer to names in the directory, since Python replaces names with their values
when evaluating expressions. So the directory is (which is also what you would
see if you evaluated each name):

```
acct1  Account(8404, 500)
acct2  Account(8405, 350)
elena  Customer("Elena", Account(8404, 500))
jorge  Customer("Jorge", Account(8404, 500))
```

Now, let's add funds to Elena's account:

```python
elena.acct.balance = elena.acct.balance + 150
```

Following the code precisely, we might expect only Elena's version of the
account to change. But we know from running the code that the account is
aliased, so the balances seen through all three names change:

```
acct1  Account(8404, 650)
acct2  Account(8405, 350)
elena  Customer("Elena", Account(8404, 650))
jorge  Customer("Jorge", Account(8404, 650))
```

But this is also weird. What in the directory indicates that those three
balances should change, but not the balance of `acct2`? _Nothing!_ Mapping names
to values works fine for programs without mutation, but once we have both
mutation and aliasing, it breaks down, because _it doesn't capture the aliases_.

#### Introducing the Heap

The tempting version, with `acct1` inside the `Customer`s, did reflect the
sharing. Names still can't appear in values, but the idea of _a single term that
can be reused to reflect sharing_ is a good one, and it reflects what happens
inside your computer.

Every time you use a constructor to create data, Python stores it in your
computer's _memory_, which consists of a (large) number of slots. Each slot is
labeled with an _address_: just as a street address refers to a specific
building, a memory address refers to a specific slot. Python gets a portion of
the memory to store its data in, called the _heap_. When you write

```python
acct1 = Account(8404, 500)
```

Python puts the new `Account` into a slot in the heap, then puts the _address_
of that slot, not the value itself, in the directory. So our picture now has two
parts: the directory, mapping names to addresses, and the heap, showing the
values stored at the addresses:

```
Directory       Heap
acct1  @1001    @1001  Account(8404, 500)
```

We write addresses as four-digit numbers after an `@`. The first address (here
1001) is arbitrary, and later data use the next addresses, in order, so `acct2`
gets `@1002`. What happens when we then run `elena = Customer("Elena", acct1)`?
As before, we look up what `acct1` refers to in the directory, and use that in
the `Customer`. But now, `acct1` refers to an _address_, `@1001`, so the
`Customer` in the heap contains an address. After making `jorge` the same way,
the directory and heap look like this:

```
Directory       Heap
acct1  @1001    @1001  Account(8404, 500)
acct2  @1002    @1002  Account(8405, 350)
elena  @1003    @1003  Customer("Elena", @1001)
jorge  @1004    @1004  Customer("Jorge", @1001)
```

Now we can see the relationship between the `acct` fields of the two customers
and the name `acct1`: they _refer to the same address_, and so to the same value.
In contrast, `acct2`, which was not aliased, refers to an address that is not
referenced anywhere else. This is the heart of aliasing: it's why changes made
through one name also affect values seen through another.

Try writing three different expressions, each using a different name from the
directory, that produce the balance of the account at `@1001`. Would
`elena.acct.balance = jorge.acct.balance - 50` work to update Elena and Jorge's
shared account? Is it a good way to write it? And how would the directory and
heap change if we ran `acct3 = acct1`?

Three rules guide how running a program affects the directory and the heap:

1. If the code constructs a new piece of structured data, put it at the next
   address in the heap.
2. If the code associates a name with a piece of structured data, the directory
   maps the name to the address of that data in the heap.
3. If the code modifies a field within structured data, modify the data in the
   heap.

So Elena's deposit (rule 3) changes only the `Account` at `@1001`, which is why
all three names see the new balance. And `acct3 = acct1` doesn't change the heap
at all: it only adds `acct3` to the directory, with the address `@1001`, making
`acct3` and `acct1` aliases.

#### Basic Data and the Heap

Do basic data, such as numbers or strings, get addresses in the heap too? They
do not. We need the heap so that updates to fields of shared data affect all
their aliases, but basic data don't have fields. For example, continuing our
program, suppose we also had a dataclass for offices, with a professor's name
and a room number:

```python
@dataclass
class Office:
    name: str
    room: int

x = 4
prof = "Dr. Kumar"
office1 = Office("Dr. Lakshmi", 311)
office2 = Office(prof, 310 + x)
```

This adds these entries to the directory and heap:

```
Directory              Heap
x        4             @1005  Office("Dr. Lakshmi", 311)
prof     "Dr. Kumar"   @1006  Office("Dr. Kumar", 314)
office1  @1005
office2  @1006
```

Though real implementations vary, it is enough to think of basic data as living
in the directory: the point of structured data is that they have both their own
identity and several components, which the heap gives us, while basic data
can't be broken down. But don't strings have components, their characters?
Technically, yes, but Python has no operations that change the characters in a
string (`+` and the like produce new strings), so we can treat them as basic
data.

### Equality of Data

Now that we can mutate data, it's worth asking what it means for two pieces of
data to be equal. Consider, in a new file:

```python
a1 = Account(8603, 500)
a2 = Account(8603, 500)
a3 = Account(8603, 250)
```

Which of these accounts do you consider "equal"? The third has a different
balance, so it can't be equal to either of the others. The first two have the
same contents, so arguably they are equal. But each account ends up at its own
address in the heap, so the first two do not have the same address. Is that
relevant? To explore this, let's add another name, `a4`, for the same address
as `a2`, then change the balance in `a2`:

```python
a4 = a2
# checkpoint 1
a2.balance = 800
# checkpoint 2
```

At checkpoint 1, the directory and heap are:

```
Directory     Heap
a1  @1001     @1001  Account(8603, 500)
a2  @1002     @1002  Account(8603, 500)
a3  @1003     @1003  Account(8603, 250)
a4  @1002
```

`a1` and `a2` refer to two different `Account`s with the same contents. At
checkpoint 2, their contents are different: the only change is that the heap at
`@1002` now holds `Account(8603, 800)`. In contrast, `a2` and `a4` are aliases
for the same `Account`, so their values change in lockstep: displaying either
one would now show a balance of `800`. What do you think now: are the first two
accounts equal?

### Equality in Python

These examples point to two notions of equality: whether two values have the
same contents (_structural equality_: when displayed, do they look the same?),
and whether they live at the same address, so there is really only one value in
memory (_reference equality_: are the names aliases?). Each is useful in
different situations, so Python has an operation for each. The `==` operator
checks for structural equality, regardless of addresses, while `is` checks for
aliasing:

```python
a1 == a2  # True at checkpoint 1, but False at checkpoint 2
a2 == a4  # True at both
a1 is a2  # False at both
a2 is a4  # True at both
```

This explains why `a2 == a4` was true both before and after the mutation, but
`a1 == a2` was not true after it, which seems to violate a very basic meaning of
"equality": the problem is caused by mutation. `==` is more accepting, so it is
usually the right default; if you actually need to know whether two expressions
evaluate to the same address, use `is`.

## Intro (15 mins)

- Today we look at how mutable data structures work in Python, and how the "heap" model helps us understand mutation and aliasing.
- In Python, all fields in structured values (like those created with `@dataclass`) are mutable by default. Assignment with `=` both creates and updates variables and fields. **There is no _syntactic_ difference between changing variables and fields inside data in Python, as both use `=`, but these have significant _semantic_ differences.**
  ```python
  from dataclasses import dataclass

  @dataclass
  class LibraryBook:
      id: int
      title: str
      copies: int

  book1 = LibraryBook(101, "The Curious Incident", 5)
  book2 = book1
  book1.copies = book1.copies - 1
  # book2.copies is now 4, because book2 is an alias for book1
  ```
- The **program directory maps names to addresses in the heap, where the actual data lives**. If two names refer to the same address, **mutating through one changes the value for both**.
- In Python `==` checks for structural equality (same contents), while `is` checks for reference equality (same address in the heap). Be careful: two values that are `==` now may not be later, if one of them is changed!
- For example:
  ```python
  book3 = LibraryBook(101, "The Curious Incident", 5)
  print(book1 == book3)  # False: book1 now has 4 copies, but book3 has 5
  print(book1 is book3)  # False, different objects
  print(book1 is book2)  # True, same object (alias)
  ```

## Wrap-up (5 mins)

- In Python, mutable data structures live in the heap and can be aliased.
- Mutating through one alias affects all.
- Structural equality checks contents; reference equality checks identity.
- Understanding these concepts is key to writing correct code and avoiding bugs related to aliasing and mutation.
