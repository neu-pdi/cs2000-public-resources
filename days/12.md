### Task Plans

Our process for the discount chart in the reading for [Day 11](/days/11) --
start from a concrete example, check the documentation for a function that might
help, then manipulate the data to work with it -- is an instance of what we'll
call _task planning_. A _task plan_ is a sequence of steps (tasks) that
decompose a problem into smaller steps (sub-tasks) that you know how to
implement, with a built-in function or one you write. It can be a bulleted list,
a diagram of how the data are transformed, or both: the goal is a programming
to-do list.

**Strategy: Creating a Task Plan**

1. Develop a concrete example of the desired output on an input you pick: large
   enough to show different features of your inputs, but small enough to work
   with by hand (for tables, 4-6 rows usually works well).
2. Identify functions that you know (or find in the documentation) that might
   help transform the input to the output.
3. Develop a sequence of steps that could solve the problem. If you draw
   pictures, show the intermediate data values from your example, and note the
   operations that get from one to the next.
4. Repeat step 3, breaking down sub-tasks until you could write code for each
   step.

Here is a plan for the discount chart, of the sort we'd draw on paper:

```
 Name       Num Tickets   Discount Code
 "Jaime"    2             "BIRTHDAY"
 "Darren"   4             "birthday"
 "Nya"      3             " "
 "Luis"     5             "Student"
               |
               |  using transform_column
               v
 Name       Num Tickets   Discount Code
 "Jaime"    2             "BIRTHDAY"
 "Darren"   4             "BIRTHDAY"
 "Nya"      3             "none"
 "Luis"     5             "STUDENT"
               |
               |  using freq_bar_chart
               v
 bars: BIRTHDAY 2, none 1, STUDENT 1
```

To turn a plan into a program, write code for each step, passing the output of
one step as the input of the next.

Try: write a task plan for finding the student with the largest improvement from

Some plans transform the same table in different ways, then combine the results.
For example, to compute the difference between the largest and lowest midterm
scores:

```

     "Rania"    86        82
     "Bernd"    82        90
     "Annika"   93        85
     "Cole"     78        89
         |                     |
         |  sort, look up      |  sort, look up
         v                     v
         93                    78
           \                  /
            '--->  93 - 78  <'
```

Try: given a table of weather data, with columns for the date, precipitation,
and highest temperature, write a task plan to compute whether there were more
snowy days (below freezing, with precipitation more than zero) in January than
in February.

The takeaway: **If you aren't sure how to approach a problem, don't start by
trying to write code. Plan until you understand the problem.** Newer programmers
often assume that starting to write code is the fastest way to working code;
experienced programmers know that it takes much longer than first stepping back
to understand the problem, using concrete examples to find the intermediate
computations you need.

### Preparing Data Tables

Sometimes our data are clean, but not in the form our analysis needs. To chart
the distribution of small, medium, and large ticket orders, we need labels for
the scale of each order, which our table doesn't have.

#### Creating Bins

Reducing a set of values (like numbers of tickets) into a smaller set of
categories (small/medium/large, or morning/afternoon/evening for times) is
_binning_: the categories are the bins. We write a function that computes the
bin for a value, then add a column of bin labels (`cleaned_event_data` is the
cleaned events table, which we'll make below):

```python
def order_scale_label(num_tickets: int) -> str:
    """categorizes a number of tickets as small, medium, or large"""
    if num_tickets >= 10:
        return "large"
    elif num_tickets >= 5:
        return "medium"
    else:
        return "small"

def test_order_scale_label():
    assert order_scale_label(2) == "small"
    assert order_scale_label(5) == "medium"
    assert order_scale_label(9) == "medium"
    assert order_scale_label(10) == "large"

order_bin_data = cleaned_event_data.add_column("order-scale", lambda r: order_scale_label(r["Num Tickets"]))
```

#### Splitting Columns

Each name in the events table is a single string, which doesn't help if we want
to sort by last name, so we might split the column into two. Python's `split`
method splits a string around a separator: `"Josie Zhao".split(" ")` is
`["Josie", "Zhao"]`, a _list_ of the pieces (more on lists on
[Day 13](/days/13)). You get a piece by writing its position, starting from 0, in
square brackets: `"Josie Zhao".split(" ")[1]` is `"Zhao"`.

Try: write a task plan (just the plan) for replacing the `Name` column with
`last-name` and `first-name` columns, and some name strings to test it on.

Did you notice `"Zander"`, whose whole name is one string? What about middle
names? Names that include the last names of both parents? Cultures that put the
family name first, or don't use the Latin alphabet? Representing names is
heavily context- and culture-dependent. It's okay for a table structure to
exclude names outside the population you're representing; the headache comes
from realizing later that your program excludes data it needs to support. So
_examine your table structure for assumptions it makes about your data_, and
_choose it after thinking about which individuals it needs to represent_. (For
more, search for "falsehoods programmers believe about names".)

Try: filter a table to the rows whose name is _not_ two strings separated by a

`"first-name last-name"` format with `last-name` and `first-name` columns (use
`add_column`, then `select_columns` to leave out `Name`).

### Managing and Naming Data Tables

We now have several versions of the events table: the original, the corrected
copy, and ones with normalized discount codes, normalized delivery modes, and
order scales. Which should get names? We keep both the original file and the
corrected copy, in case we need to look at the original again (to see what
errors people made, or to apply different fixes), and we keep the cleaned data
separate from what we loaded (table operations make new tables, so this is
easy). But we don't need a name for every intermediate table: as a rule, we
name the loaded table, the cleaned table, and significant variations for
analysis:

```python
event_data_raw = load_table("https://raw.githubusercontent.com/neu-pdi/cs2000-public-resources/refs/heads/main/static/support/dcic-events-data.csv")

cleaned_event_data = (
    event_data_raw.transform_column("Num Tickets", int)
    .transform_column("Discount Code", cell_to_discount_code)
    .transform_column("Delivery", yes_to_email)
)

order_bin_data = cleaned_event_data.add_column("order-scale", lambda r: order_scale_label(r["Num Tickets"]))
```

(`cell_to_discount_code` and `yes_to_email` are from the [Day 11](/days/11)
reading.) Since `transform_column` produces a table, we can call it directly on
its own result (the parentheses around the whole expression let us put each step
on its own line), naming only the final table. With a very large dataset, you
might save the cleaned table to a file (with the **Save CSV** button on a table
in the interactions panel), and load only that. A few consistently chosen names
will reduce your confusion as you switch between projects.

### Visualizations and Plots

Now we can analyze the data: which discount code was used most often? Does the
time of purchase correlate with the number of tickets? Which plot to use
depends on the question, and on the kinds of variables (columns) involved:

- _quantitative_: numeric values, ordered with a consistent interval between
  them, that are meaningful to compute with.
- _categorical_: a fixed set of values, with no meaningful computations beyond
  (perhaps) ordering. These usually describe characteristics of your samples.

Which kind are last names? Course grades? Zip codes?

Common plots (all table methods: see [Tables](/pll/tables)) include
_scatter plots_ (`scatter_plot`), relating two quantitative variables;
_frequency bar charts_ (`freq_bar_chart`), showing how often each categorical
value appears; _histograms_ (`histogram`), showing how quantitative values are
distributed across equal-size intervals; and _pie charts_ (`pie_chart`), showing
the share of a total belonging to each categorical value.

Try: which chart type would answer each question? Which discount code has been
used most often? Is there a relationship between the number of tickets in an
order and the time of purchase? How many orders have been made for each
delivery option?

For the last one, a frequency bar chart:

```python
cleaned_event_data.freq_bar_chart("Delivery")
```

It has bars for `email` (4), `pickup` (2), and... `emall` (1)? Look closely at
Alvina's row: a typo (drop-down menus, anyone?). Plots are valuable not only
for analysis, but also early on, to sanity-check that the data are clean: _good
data scientists **never** trust a dataset without first making sure that the
values make sense_. In large datasets, which you can't inspect by hand, plots
and other summaries help find errors.

### Summary: Managing a Data Analysis

When doing any data analysis, a good data practitioner:

1. Thinks about the data in each column: what values are plausible, and what
   errors are likely, given how the data were collected?
2. Checks for errors, by looking at the table, making plots, and using `filter`
   to find unexpected values, then normalizes or corrects the data, at the
   source (if they control it) or with small programs.
3. Stores the cleaned table, as a name in the program or in a new file, leaving
   the raw data intact.
4. Prepares the data for their questions: computing new columns, binning
   existing ones, or combining data from different tables, and naming either
   one final table, or one for each question.
5. At last, performs the analysis, with the statistics, visualizations, and
   interpretations that suit the question and the kinds of variables. When
   reporting, they keep notes about which file holds the analysis code, and
   which parts of it produced each graph or interpretation.

There is much more to managing and analyzing data: entire books, degrees, and
careers. For example, _machine learning_ uses programs (that others have
written) to make predictions from datasets, and the skills here are
prerequisites for using it effectively and responsibly. Predicting from data
raises many issues: from the data themselves (are the samples representative?
do correlations between variables lead to discrimination, as in the algorithmic
hiring case on [Day 6](/days/6)?), from data collected for one purpose being
misused for another, and from how results are interpreted.

## Intro (25 mins)

- Often, what you want to do is big enough that jumping right into code is a mistake.

- Instead, good idea to develop a task plan -- as text, pictures, etc.

- A plan has concrete inputs & outputs, notes about what functions you might use, and a concrete sequence
  of steps and how the data is transformed through them.

- You might repeat this process at a smaller level if one of the steps still seems complex.

- Let's say we had the following table of weather data:

  ```python
  weather_data = table(
      ["date", "temperature", "precipitation"],
      [
          ["2025-01-01", 62, 0.1],
          ["2025-01-02", "45", 3],
          ["2025-01-03", 28, 0.2],
          ["2025-01-04", 55, -1],
          ["2025-01-05", 90, 0],
      ],
  )
  ```

  And we wanted to visualize the number of cold, mild, and hot days.

- The output is going to be a chart, which has bars for counts of cold, mild,
  and hot days. Let's say cold is below 40F, mild is 40F to 60F, and hot is
  above 60F.

- Our task plan, the steps we need to do are:

  1. Normalize the data -- in particular, the temperature column needs to be all
     numbers! While the precipitation column seems to have problems (a negative
     number) since our task doesn't have anything to do with precipitation, we
     don't need to deal with that.
  2. Create a new column with the three different bins -- cold, mild, or hot.
  3. Chart that new column.

- For the first step, we can use `isinstance`, which checks whether a value has a given type (`isinstance(v, str)` is `True` if `v` is a string), and `float` to convert the errant values. But `float` causes an error (a `ValueError`) if the string doesn't represent a number, and we don't want our program to stop in that case, so we use a helper that, as we saw on [Day 9](/days/9), uses `try` / `except` to produce a default value instead:

  ```python
  def string_to_number(s: str, default: float) -> float:
      """converts s to a number, or produces default if s does not represent a number"""
      try:
          return float(s)
      except ValueError:
          return default
  ```

  Then we can define a helper that does the conversion. Its input is either a number or a string, which we write as `float | str` (the `|` means "or"):

  ```python
  def normalize_temp(v: float | str) -> float:
      """given a number or a string that represents a number, converts to a number"""
      if isinstance(v, str):
          return string_to_number(v, 0)
      else:
          return v

  def test_normalize_temp():
      assert normalize_temp(10) == 10
      assert normalize_temp("13") == 13
  ```

  Then we can use that to transform the column:

  ```python
  fixed_data = weather_data.transform_column("temperature", normalize_temp)
  ```

- For the second column, we can define a helper function that does the bucket conversion:

  ```python
  def bucket_temp(t: float) -> str:
      """numbers < 40 turn into 'cold', >=40 and < 60 to 'mild' and >=60 to 'hot'"""
      if t < 40:
          return "cold"
      elif t < 60:
          return "mild"
      else:
          return "hot"

  def test_bucket_temp():
      assert bucket_temp(-10) == "cold"
      assert bucket_temp(0) == "cold"
      assert bucket_temp(39.9) == "cold"
      assert bucket_temp(40) == "mild"
      assert bucket_temp(58) == "mild"
      assert bucket_temp(60) == "hot"
      assert bucket_temp(100) == "hot"
  ```

  Now we can use that to add a new column:

  ```python
  with_buckets = fixed_data.add_column("temp-category", lambda r: bucket_temp(r["temperature"]))
  ```

  Note how I made my helper function `bucket_temp` just take a number, so it was easy to test, and then used a `lambda` to
  pass a function from a row to a string to `add_column`, which handled extracting the column value and passing it to the helper. I could have
  had `bucket_temp` take in a row, but it would have made testing more complex.

- Now, our last task is to visualize the results. We can do this with `freq_bar_chart`:

  ```python
  with_buckets.freq_bar_chart("temp-category")
  ```
