## Reading

### Examples for Table-Producing Functions

How do we test functions that produce tables? We check that we got the table we
expected, but writing out a table is more work than writing a number or a
string. How might you write the tests for `give_raises`, from the
[Day 9](/days/9) reading? Some ideas that help:

- _Simplify the input table._ Rather than a large table with all of its
  columns, create a small one, with enough variety in just the columns the
  function uses:

  ```python
  wages_test = table(["hourly-wage"], [[15], [20], [18], [18]])
  ```

  Would any table with a column of numbers work here? The only constraint is
  that it has the columns your function uses.

- _Write computations in the code that constructs a table_, rather than doing
  them by hand:

  ```python
  def test_give_raises():
      assert give_raises(wages_test) == table(
          ["hourly-wage"], [[15 * 1.1], [20], [18 * 1.1], [18 * 1.1]]
      )
  ```

  The expected table is written directly in the test: it doesn't need a name.

- _Create a new table from rows of an existing one._ For example, a function
  that filters `employees` to those working exactly 40 hours should produce its
  first and fourth rows. Rather than typing them again, we can write:

  ```python
  emps_at_40 = table(employees.columns(), [employees.row(0), employees.row(3)])
  ```

  `employees.columns()` is the list of `employees`' column names, and `table`
  also accepts rows that are `dict`s, like the ones `row` gives us.

### Lambda: Anonymous Functions

Let's revisit our program from the [Day 8](/days/8) reading for finding the
months with fewer than 1000 riders, `shuttle.filter(below_1k)`. Do we really
need a helper function for something this simple? Wouldn't it be easier to
write this?

```python
shuttle.filter(r["riders"] < 1000)
```

What will Python do if you run it? It reports a `NameError`: it doesn't know
what `r` is. We mean `r` to be each row in turn, but a function's (or method's)
arguments are evaluated _before_ it runs, so Python evaluates
`r["riders"] < 1000` before `filter` has started. The point of `below_1k` is to
make `r` a parameter of a function, whose body is only evaluated once `r` has a
value.

So we need a way to make a temporary function, which gets its input once
`filter` is running. `lambda` does this:

```python
shuttle.filter(lambda r: r["riders"] < 1000)
```

`lambda r:` says "make a temporary function that takes `r` as its input", and
the expression after the colon is what it returns. (Many, though not all,
languages have `lambda`.)

The main difference from `below_1k` is in the program directory: only
`below_1k` has an entry there. But `filter` calls the function it is given
through the name of its own parameter (say, `keep(row)`), and whichever we pass,
`keep` refers to a function with the same parameter and body, so it doesn't
matter whether that function had a name of its own.

In practice, we use `lambda` to pass simple functions, whose body is a single
expression, to methods like `filter`, `transform_column`, and `add_column`, but
you can always write a named helper function instead. Try adding 10 riders to
each row of `shuttle`, using `lambda` rather than a named helper function.

## Intro (15 mins)

### Lambda functions
- In the last few classes, we've shown table operations that take functions as
  arguments; some of those are complex, and benefit from being written with our
  full design process (e.g., `calc_distance`, or the function to obfuscate item
  names), but others, like `subtract_1` seem a bit unnecessary. It would be nice
  if we could write:

  ```python
  t = table(
      ["x-coord", "y-coord"],
      [
          [1, 2],
          [3, 4],
      ],
  )
  t.transform_column("x-coord", n - 1)
  ```

- But if we try to run this, we get an error -- `n` is not defined. What we
  want, instead of `n`, is a way of referring to the column value that is being
  transformed. When we defined a function, this is the argument:

  ```python
  def subtract_1(n: float) -> float:
      """subtracts 1 from input"""
      return n - 1

  def test_subtract_1():
      assert subtract_1(10) == 9
      assert subtract_1(0) == -1
      assert subtract_1(-3.5) == -4.5
  ```

- For simple functions, we can do this with `lambda`, which creates an unnamed function. After `lambda` come the names of the arguments, then a colon, and then a single expression, which is what the function returns (there is no `return`, and there can't be type annotations):

  ```python
  t.transform_column("x-coord", lambda n: n - 1)
  ```

- The body of a `lambda` can only be a single expression, so it can't contain, for example, an `if` statement. For anything more complicated than that, we should write a named function, following our full design process.

### Testing tables
- Another oddity about the last few classes is that while we've followed our
  design process for _helper_ functions, we haven't actually written functions
  that take tables and produce tables, and (for the most part), haven't written
  tests on tables.

- For example, let's design a function that transforms a table, modifying a
  `"price"` column by discounting it by 20%, but only for prices that are below
  100\. Since this needs an `if`, we write a named helper function for the
  discount, and use it with `transform_column` (the type annotation for tables is `Table`):

  ```python
  def discount_price(price: float) -> float:
      """reduces price by 20%, if it is below 100"""
      if price < 100:
          return price * 0.8
      else:
          return price

  def test_discount_price():
      assert discount_price(50) == 50 * 0.8
      assert discount_price(120) == 120

  def apply_discounts(t: Table) -> Table:
      """transforms 'price' column by reducing 20%, if value is below 100"""
      return t.transform_column("price", discount_price)

  def test_apply_discounts():
      test_table = table(
          ["price"],
          [
              [50],
              [120],
              [80],
              [40],
          ],
      )
      assert apply_discounts(test_table) == table(
          ["price"],
          [
              [50 * 0.8],
              [120],
              [80 * 0.8],
              [40 * 0.8],
          ],
      )
  ```

- Note how we created an example table within our test function, and in the
  test, rather than computing the actual numbers, wrote the expressions for the
  rows that should have changed. This makes it easier to understand the behavior.

### Visualizing data
- It's often helpful to _see_ the data, using visualizations. There are many methods
  that allow us to make charts. For example, we can make a frequency bar chart, which has a bar for each different value in a column, with a height showing how many times that value appears, using `freq_bar_chart`:

  ```python
  prices = table(
      ["price"],
      [
          [50],
          [120],
          [80],
          [40],
          [50],
          [80],
          [80],
      ],
  )
  prices.freq_bar_chart("price")
  ```

## Wrap-up (5 mins)

- `lambda` allows us to more concisely use operations that expect functions as
  inputs, like `transform_column`, `add_column`, or `filter`, when the function is simple.
- Table functions should follow the same design process, and include tests, just
  like other functions!
