## Reading

### Testing and variables that can change

We have intentionally changed variables in only one pattern (the one from
[Day 15](/days/15)), mainly because code that changes them in other ways is
hard to test, and so hard to understand. In particular, the pattern never
changes a variable defined _outside_ a function: each time the function runs, a
new variable is created, changed in the `for` loop, and its value returned; then
its entry in the program directory is removed, so it is never shared by
different calls.

Consider what happens if we don't follow the pattern, for this problem:

> Given a list of numbers, return the prefix of the list (i.e., all elements,
> starting from the beginning) that sums to less than 100.

You might keep the running sum in a variable `cnt` defined outside the function
(a function that changes such a variable has to say so with `global`, which PLL
only allows at `#level advanced`):

```python
#level advanced

cnt = 0

def prefix_under_100(lst: list[float]) -> list[float]:
    """returns the elements at the start of lst that sum to less than 100"""
    global cnt
    output = []
    for elt in lst:
        cnt = cnt + elt
        if cnt < 100:
            output = output + [elt]
    return output
```

This might seem reasonable. But what happens when we test it?

```python error
def test_prefix_under_100():
    assert prefix_under_100([1, 2, 3]) == [1, 2, 3]
    assert prefix_under_100([20, 30, 40]) == [20, 30, 40]
    assert prefix_under_100([80, 20, 10]) == [80]
```

The first two `assert`s pass, but the last one doesn't. Why? Even more
confusing: if we move the last `assert` to the top of the test function, it
passes, and now the one for `[1, 2, 3]`, which passed before, fails!

Since `cnt` is outside the function, it is _shared_ across calls: it is added
to the program directory once, and each call changes that entry, but never
resets it. So to understand what a call does, we need to know not only the code
in the function, but also the current value of `cnt`, which we can't figure out
just by looking at the code!

Functions like this are said to have _side effects_, which make them much
harder to test and to understand, and so more likely to have bugs -- often
subtle ones, that only happen when functions are called in particular orders
that may only arise in rare situations. While sometimes necessary, almost all
code can be written without side effects, and will be much more reliable.

Try tracing `cnt` through the three calls in the test, to see why the last one
returns `[]`. Then fix `prefix_under_100` by following the pattern.

## Intro (15 mins)

- All our uses of variables that change have intentionally followed the same pattern:
  ```python skip
  def func(lst: list) -> ...:
      result = ...  # what to return if the input list is empty
      for item in lst:
          # combine item with the result so far
          result = ... item ... result
      return result
  ```
- In particular, **we only change variables inside of functions** (and `#level intermediate` only allows that). Why?
- Consider we wanted to implement a function `every_third_element` that took a
  list, and returned the first, fourth, seventh, etc, elements.
- We might try to keep track of the position we are at in a variable, `count`,
  defined outside of the function. In Python, a function that changes a variable
  defined outside of it has to say so, by writing `global` and then the name of the
  variable at the beginning of the function (without it, assigning to `count` inside the function
  would create a new variable, local to the function, instead). PLL only allows
  `global` at `#level advanced`, which doesn't do any of the extra checks of the
  levels we've used so far, so to try this, the first line of your file should be `#level advanced`. If we wrote it as:
  ```python
  #level advanced

  count = 0

  def every_third_element(lst: list) -> list:
      global count
      output = []
      for elt in lst:
          if count % 3 == 0:
              output = output + [elt]
          count = count + 1
      return output

  def test_every_third_element():
      assert every_third_element([]) == []
      assert every_third_element([1, 3, 5]) == [1]
      assert every_third_element([1, 3, 5, 7, 11]) == [1, 7]
  ```
- It seems to work. But when we actually use it, adding
  `every_third_element([1, 3])` somewhere in our code, then suddenly our
  test is now failing. Why is this happening?
- Since `count` is defined outside of `every_third_element`, it is put into the
  top-level program directory. This means that there is only ever one `count`,
  and separate calls to `every_third_element` share the same `count`.
- This means two things, both of which are very bad:
  1. The function no longer returns the same output depending on the same input.
     Instead, the output depends on the input **and the current state of count**.
  2. This means, more confusingly, that to understand what a given call of
     `every_third_element` does, we need to know all the calls that have
     happened before, as the program _ran_, which may not be obvious from
     reading the program (since with looping, with one function calling others,
     etc, the order and how many times a function is called can be tricky to
     figure out).

## Class Exercises (40 mins)

For these exercises, use `#level advanced`, since they all use `global`.

1. What does each call return? (Trace very carefully through the execution order):
    ```python
    score = 10

    def bonus_points(amt: int) -> int:
        global score
        score = score + amt
        return penalty_check()

    def penalty_check() -> int:
        global score
        if score > 15:
            score = score - 3
        return score

    bonus_points(2)
    bonus_points(4)
    bonus_points(1)
    ```
1. Trace through these function calls. What does `process_data` return each time?

    ```python
    dta = [1, 2, 3]
    position = 0

    def advance() -> int:
        global dta, position
        result = dta[position]
        position = position + 1
        if position >= len(dta):
            position = 0
            dta = [0] + dta
        return result

    def process_data() -> int:
        first = advance()
        second = advance()
        return first + second

    process_data()
    process_data()
    process_data()
    ```

1. Trace execution. What does `calculate` return for each call?

    ```python
    multiplier = 1
    base = 5

    def update_multiplier(n: int) -> int:
        global multiplier, base
        multiplier = multiplier + n
        if multiplier % 3 == 0:
            base = base - 1
            multiplier = 1
        return multiplier

    def calculate(x: int) -> int:
        update_multiplier(x)
        return x*multiplier + base

    calculate(2)
    calculate(1)
    calculate(4)
    calculate(2)
    ```

1. Now, pick one of the examples above, and try to write tests for it using a test function. What goes wrong?
1. Try using `print` to inspect the values of appropriate variables and the effect the changes to the variables have across function calls.

## Wrap-up (5 mins)

- While mutation can be very useful, it also can make programs much, much harder to understand.
- Ease of testing is often a good way of approximating ease of understanding -- if it is very hard (or impossible) to set up test cases, that's an indication to try to figure out a different way of organizing the program.
