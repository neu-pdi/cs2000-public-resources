## Notes (review before class)
### Functions from Similar Expressions

Two pines from the [Class 1](/class/1) picture, and the spruce:

```python
# Lines starting with # are comments, for human readers:
# Python ignores everything on a line after #.

# the big pine
above(triangle(120, "solid", "darkgreen"),
      rectangle(20, 40, "solid", "brown"))

# the small pine
above(triangle(60, "solid", "darkgreen"),
      rectangle(10, 20, "solid", "brown"))

# the spruce
above(triangle(96, "solid", "teal"),
      rectangle(16, 32, "solid", "brown"))
```

We'd like to write what they share once, and give only what changes. But
Python has no `pine` operation: it's specific to our program.

```python error
pine(120, "darkgreen")
pine(60, "darkgreen")
pine(96, "teal")
```

A **function** is an operation we add ourselves: it takes **parameters**, and
uses them to produce a result.

### Defining Functions

To make a function from expressions that are alike except for a few values:

1. Write down at least two examples (the three trees).
2. Mark what is the same in all of them (a `"solid"` triangle `above` a brown
   rectangle), and what changes.
3. For each change, ask whether it is a separate choice, or follows from
   another. The triangle's size and color are choices. The trunk's numbers
   change too, but the width is always the size divided by 6, and the height the
   size divided by 3: they follow from the size.
4. Name each choice: these are the parameters (`size`, `color`).
5. Rewrite the expression with the parameters in place of the choices, and
   computations from them in place of what follows: `size / 6`, `size / 3`.
6. Pick a name that says what the result is: `pine`.
7. Wrap it in the syntax for functions (`<...>` means "fill in"):

   ```
   def <function name>(<parameters>):
       return <the expression goes here>
   ```

```python
def pine(size, color):
    return above(triangle(size, "solid", color),
                 rectangle(size / 6, size / 3, "solid", "brown"))
```

- The indented lines after `def` are the function's **body**; `return` says
  what value it produces.
- With practice, you won't need to start from several examples.

Giving values for the parameters is **calling** the function;
`pine(120, "darkgreen")` is a **call**:

```python
big_pine = pine(120, "darkgreen")
small_pine = pine(60, "darkgreen")
spruce = pine(96, "teal")
```

- If your file already defines `big_pine`, PLL reports a reassignment: use
  another name, or comment out the earlier definition with `#`.

### Whitespace Matters

**Indentation** (pushing lines in from the left edge) is how Python knows which
lines belong to the body: in Python, **whitespace** (spaces, tabs, new lines)
carries meaning, where many languages use braces or `end`:

```python
def double(n):
    return n * 2
```

```python error
def double(n):
return n * 2
```

- The second is an error: after the `def` line, Python finds no indented body.
- Indent by **four spaces** (the editor does this when you press Enter after
  the `:`).
- Be **consistent**: lines in the same body need the same indentation. A tab
  (copied in from elsewhere) can look just like spaces, but isn't: let the
  editor insert spaces.
- For an indentation error, read down the left edge first: the _shape_ of the
  code is wrong.
- This applies to everything with a body: conditionals, loops, and more.

### How Functions Evaluate

- A function **definition** adds an entry to the directory, from the function's
  name to its code (and shows nothing). The body is _not_ evaluated yet.
- A **call** evaluates the body, with the call's values in place of the
  parameters: `pine(60, "darkgreen")` becomes
  `above(triangle(60, "solid", "darkgreen"), rectangle(60 / 6, 60 / 3, "solid", "brown"))`,
  which is the small pine.
- Equivalently, the call adds `size` and `color` to a **local** directory, used
  only while the body runs and then removed: they can't be used outside the
  function (more on [Class 5](/class/5)).

### Signatures and Docstrings

`pine("darkgreen", 120)`, with its inputs swapped, puts `"darkgreen"` in place
of `size`. PLL then reports that `triangle`'s `side` must be a number, which is
confusing, since the caller wrote no triangle. Worse would be a mistake that
gives a wrong picture and no error at all. The complete definition fixes this,
and explains the function:

```python
def pine(size: float, color: str) -> Image:
    """a pine tree: a triangle of needles, size on each side and of the given
    color, on a brown trunk in proportion to it"""
    return above(triangle(size, "solid", color),
                 rectangle(size / 6, size / 3, "solid", "brown"))
```

- The **signature** is the `def` line, now with **type annotations**: each
  parameter gets a colon and its type (so far: `int`, `float`, `str`, or
  `Image`), and the result's type goes after `->`, as in the documentation's
  contracts. Now PLL reports that `pine` expects `size` to be a number.
- Python runs functions without annotations, but our signatures always have
  them: errors are reported more precisely, and readers know how to use the
  function.
- A **docstring** is a short, human-language description of what the function
  does (not necessarily how): a string with three double quotes on each side,
  on the first line of the body, which can continue onto more lines. A name
  can't say everything (is `size` the height? does the trunk change?), so always
  write one, for any reader, including you in a few weeks.
- These are two steps of the **design recipe**: the order in which we design
  every function, from now on. For each function, first the **Signature**, with
  its types (work them out _first_: the rest of the function depends on them),
  then the **Docstring**. Two steps come before them, about the kind of data
  rather than one function (its **Data definition**, and its **Template**), and
  the rest come in the next few classes:

### Example: Celsius to Fahrenheit

A weather display gets temperatures in degrees Celsius, and shows them in
Fahrenheit: multiply by 9/5, then add 32. We _expect_ to convert many readings
(`0 * 9/5 + 32`, `100 * 9/5 + 32`, `37 * 9/5 + 32`, ...), and repeating the
formula invites typos, so we write a function right away ("DRY": "don't repeat
yourself"), with fixed part `* 9/5 + 32` and the Celsius temperature as
parameter. Step by step:

- **Data definition**: a Celsius temperature is a number of degrees (a `float`),
  possibly negative. Until [Class 19](/class/19), data definitions are written
  in words, like this.

- **Template**: the outline that the kind of data gives the body of any function
  on it, written once, right after the data definition. A template is a function
  named for its kind of data, with `_` in front (it's an outline, not a function
  to call), and the signature ends with `-> ...`, since its result could be
  anything. A temperature is a number, which has just one part, so the template
  has a line for it, with `...` before and after it, since the body's code can
  go around it, and then `return ...` (templates have more to them from
  [Class 5](/class/5)):

```python
def _celsius_temp(celsius: float) -> ...:
    ...
    celsius
    ...
    return ...
```

- **Signature** and **Docstring** of this function, with `...` as the body.
  The result can have a fraction (37 degrees Celsius is 98.6 Fahrenheit), so
  its type is `float`, written with a decimal _point_: `98,6` doesn't work. The
  file already runs: if you try to use the function, though, PLL says `c_to_f`
  isn't written yet.

```python
def c_to_f(celsius: float) -> float:
    """the temperature celsius (in degrees Celsius), in degrees Fahrenheit"""
    ...
```

- **Examples**: the calculations above say what the function should give:
  `c_to_f(0)` should be `0 * 9/5 + 32`, and `c_to_f(100)` should be
  `100 * 9/5 + 32`. (From [Class 5](/class/5), we write examples as tests.)
  For now, we can write them as comments:

```
# c_to_f(0) should be 0 * 9/5 + 32
# c_to_f(100) should be 100 * 9/5 + 32
```

- **Body**: copy the template's body in place of `c_to_f`'s `...`, and fill it
  in with the part all the examples share, `* 9/5 + 32`.

  First we have:

```python skip
def c_to_f(celsius: float) -> float:
    """the temperature celsius (in degrees Celsius), in degrees Fahrenheit"""
    ...
    celsius
    ...
    return ...
```

  And then we complete it as:

```python
def c_to_f(celsius: float) -> float:
    """the temperature celsius (in degrees Celsius), in degrees Fahrenheit"""
    return celsius * 9/5 + 32
```

### Example: A Welcome

Every student who signs up for a course gets the same welcome, except for their
name and the course's (`"Welcome to " + "CS 2000" + ", " + "Ada" + "!"`,
`"Welcome to " + "Art History" + ", " + "Grace" + "!"`, ...). Step by step:

- **Data definition**: a sign-up has two parts, the student's name and the
  course's name, each a string (a `str`).

- **Template**: a string has just one part of its own, so a sign-up's template
  is just the two parameters: a line for each part, with `...` before and after
  it, and then `return ...`
  ([numbers, strings, and images](/class/recipe#template-numbers)):

```python
def _signup_temp(name: str, course: str) -> ...:
    ...
    name
    ...
    course
    ...
    return ...
```

- **Signature** and **Docstring**, with `...` as the body:

```python
def welcome(name: str, course: str) -> str:
    """the message that welcomes name to course"""
    ...
```

- **Examples**, as comments for now:

```
# welcome("Ada", "CS 2000") should be "Welcome to " + "CS 2000" + ", " + "Ada" + "!"
# welcome("Grace", "Art History") should be "Welcome to " + "Art History" + ", " + "Grace" + "!"
```

- **Body**: copy the template's body, and fill it in with what the examples
  share, the parts in their order:

```python
def welcome(name: str, course: str) -> str:
    """the message that welcomes name to course"""
    return "Welcome to " + course + ", " + name + "!"
```

- Try: `welcome(2000, "Ada")` is a mistake. Where does PLL report it? Where
  would it be reported if the `def` line had no annotations? After the file
  runs, what happens if you enter `name` at the prompt, and why?
