## Notes (review before class)
### Functions from Similar Expressions

These draw the flags of Armenia and Austria: the same shape, in different
colors (`frame` draws a thin outline around an image):

```python
# Lines starting with # are comments, for human readers:
# Python ignores everything on a line after #.

# armenia
frame(above(rectangle(120, 30, "solid", "red"),
            above(rectangle(120, 30, "solid", "blue"),
                  rectangle(120, 30, "solid", "orange"))))

# austria
frame(above(rectangle(120, 30, "solid", "red"),
            above(rectangle(120, 30, "solid", "white"),
                  rectangle(120, 30, "solid", "red"))))
```

We'd like to write the shared part once and give just the colors, but Python
has no such operation (it's specific to our program):

```python error
# armenia
three_stripe_flag("red", "blue", "orange")

# austria
three_stripe_flag("red", "white", "red")
```

A **function** is an operation we add ourselves: it takes **parameters**, and
uses them to produce a result.

### Defining Functions

To make a function from expressions that differ in only a few values:

1. Write down at least two examples (the two flags).
2. Find the fixed parts (`120` by `30` rectangles, stacked with `above`) and
   the changing parts (the colors).
3. Name each changing part: these are the parameters (`top`, `middle`,
   `bottom`).
4. Rewrite the expression with those names in place of the changing parts.
5. Pick a suggestive name: `three_stripe_flag`.
6. Wrap it in the syntax for functions (`<...>` means "fill in"):

   ```
   def <function name>(<parameters>):
       return <the expression goes here>
   ```

```python
def three_stripe_flag(top, middle, bottom):
    return frame(above(rectangle(120, 30, "solid", top),
                       above(rectangle(120, 30, "solid", middle),
                             rectangle(120, 30, "solid", bottom))))
```

- The indented lines after `def` are the function's **body**; `return` says
  what value it produces.
- With practice, you won't need to start from several examples.

Giving values for the parameters is **calling** the function;
`three_stripe_flag("red", "blue", "orange")` is a **call**:

```python
armenia = three_stripe_flag("red", "blue", "orange")
austria = three_stripe_flag("red", "white", "red")
```

- If your file already defines `armenia`, PLL reports a reassignment: use
  another name, or comment out the earlier definition with `#`.

### Whitespace Matters

**Indentation** (pushing lines in from the left edge) is how Python knows which
lines belong to the body: in Python, **whitespace** (spaces, tabs, new lines)
carries meaning, where many languages use braces or `end`:

```python
def double(n):
    return n * 2
```

```python error
def double(n):
return n * 2
```

- The second is an error: after the `def` line, Python finds no indented body.
- Indent by **four spaces** (the editor does this when you press Enter after
  the `:`).
- Be **consistent**: lines in the same body need the same indentation. A tab
  (copied in from elsewhere) can look just like spaces, but isn't: let the
  editor insert spaces.
- For an indentation error, read down the left edge first: the _shape_ of the
  code is wrong.
- This applies to everything with a body: conditionals, loops, and more.

### How Functions Evaluate

- A function **definition** adds an entry to the directory, from the function's
  name to its code (and shows nothing). The body is _not_ evaluated yet.
- A **call** evaluates the body, with the call's values substituted for the
  parameters: `three_stripe_flag("red", "blue", "orange")` becomes exactly the
  Armenia expression above, and evaluates to its flag.
- Equivalently, the call adds `top`, `middle`, and `bottom` to a **local**
  directory, used only while the body runs and then removed: they can't be used
  outside the function (more on [Class 5](/class/5)).

### Signatures and Docstrings

`three_stripe_flag(50, "blue", "red")` substitutes `50` for `top`: at best, we
get an error about `rectangle` (confusing: the caller wrote no rectangles); at
worst, a wrong picture and no error. The complete definition fixes this, and
explains the function:

```python
def three_stripe_flag(top: str, middle: str, bottom: str) -> Image:
    """produce image of flag with three equal-height horizontal stripes"""
    return frame(above(rectangle(120, 30, "solid", top),
                       above(rectangle(120, 30, "solid", middle),
                             rectangle(120, 30, "solid", bottom))))
```

- The **signature** is the `def` line, now with **type annotations**: each
  parameter gets a colon and its type (so far: `int`, `float`, `str`, or
  `Image`), and the result's type goes after `->`, as in the documentation's
  contracts. Now PLL reports that `three_stripe_flag` expects `top` to be a
  string.
- Python runs functions without annotations, but our signatures always have
  them: errors are reported more precisely, and readers know how to use the
  function.
- A **docstring** is a short, human-language description of what the function
  does (not necessarily how): a string with three double quotes on each side,
  on the first line of the body. A name can't say everything (stacked stripes?
  equal heights?), so always write one, for any reader, including you in a few
  weeks.
- These are two steps of the **design recipe**: the order in which we design
  every function, from now on. For each function, first the **Signature**, with
  its types (work them out _first_: the rest of the function depends on them),
  then the **Docstring**. Two steps come before them, about the kind of data
  rather than one function (its **Data definition**, and its **Template**), and
  the rest come in the next few classes:

### Example: Moon Weight

Objects on the Moon weigh one-sixth of their Earth weight. We _expect_ to
compute this once per astronaut (`100 * 1/6`, `150 * 1/6`, `90 * 1/6`, ...),
and repeating it invites typos, so we write a function right away ("DRY":
"don't repeat yourself"), with fixed part `* 1/6` and the Earth weight as
parameter. Step by step:

- **Data definition**: an Earth weight is a number of pounds (a `float`). Until
  [Class 19](/class/19), data definitions are written in words, like this.

- **Template**: the outline that the kind of data gives the body of any function
  on it, written once, right after the data definition. A template is a function
  named for its kind of data, with `_` in front (it's an outline, not a function
  to call), and `-> ...`, since its result could be anything. An Earth weight is
  a number, which has just one part, so the template has a line for it, with
  `...` before and after it, since the body's code can go around it, and then
  `return ...` (templates have more to them from [Class 5](/class/5)):

  ```python
  def _earth_weight_temp(earth_weight: float) -> ...:
      ...
      earth_weight
      ...
      return ...
  ```

- **Signature** and **Docstring** of this function, with `...` as the body. The
  file already runs: PLL says `moon_weight` isn't written yet, and calling it
  gives back `None`:

  ```python
  def moon_weight(earth_weight: float) -> float:
      """Compute weight on moon from weight on earth"""
      ...
  ```

- **Examples**: the calculations above say what the function should give:
  `moon_weight(100)` should be `100 * 1/6`, and `moon_weight(150)` should be
  `150 * 1/6`. (From [Class 5](/class/5), we write examples as tests.)

- **Body**: copy the template's body in place of `moon_weight`'s `...`, and fill
  it in with the part all the examples share, `* 1/6`:

  ```python
  def moon_weight(earth_weight: float) -> float:
      """Compute weight on moon from weight on earth"""
      return earth_weight * 1/6
  ```

### Example: Cost of Pens

Each pen costs 25 cents, plus 2 cents per character of the message printed on
it (counting spaces):

```python
# ordering 3 pens that say "wow"
3 * (0.25 + len("wow")*0.02)

# ordering 10 pens that say "smile"
10 * (0.25 + len("smile")*0.02)
```

```python
def pen_cost(num_pens: int, message: str) -> float:
    """total cost for pens, each 25 cents
    plus 2 cents per message character"""
    return num_pens * (0.25 + len(message)*0.02)
```

- `len` gives the number of characters in a string (including spaces and
  punctuation).
- _Two_ things change, so there are two parameters. The number of pens is
  whole (`int`); the cost has cents (`float`, written with a decimal _point_:
  `0,02` doesn't work).
- A docstring can continue onto another line.

## Class Exercise (40 mins)

1. `def` with cakes
   - Your goal is to draw an image of a three layer cake. Each cake consists of
     three equally sized rectangular layers, and the only difference is the color
     (or "flavor") of each layer. You can choose the colors!
   - Now, draw another cake with different flavors (i.e., colors). Notice what is
     different, and what is the same.
   - Define a new function, `three_layer_cake` that takes as arguments the three
     parts that change: the color of the top, middle, and bottom colors.
   - Be sure to give it a Signature (with types) and a Docstring.
   - Now use this new function to rewrite both of your past examples, and notice
     how much easier it is to read even though the behavior is the same: this is
     your second example of Design -- just like constant definitions can make
     expressions easier to read, by splitting large expressions into smaller parts
     or giving meaning to numbers, functions give names to repeated computations.
2. `def` with t-shirt printing
   - Your next task is to write a function to calculate the cost of printing a t-shirt, which can\
   have a message written on it. Each shirt costs `$5.00` plus an extra `$0.10` per
   letter printed on it.
   - First, write an expression for 4 t-shirts with the message "Go Team!".
   - Now make another expression, this time for 7 t-shirts with the message "Hello World".
   - Are there numbers that should be definitions? So-called "magic numbers"
     that aren't obvious what they mean are always good candidates for creating
     definitions -- do that now (there should be two!).
   - Now, look at the two expressions, and figure out what changes between the two,
     and write a function, `tshirt_cost`, that takes as arguments the parts that
     change.
   - Start with the Signature -- think about what type the arguments should
     be, and write `...` for the body. Next write down a Docstring. Finally,
     write the expression for the Body!
     Be sure to only include the part that changes, so that once you rewrite your
     original expressions to use your new function, the only repeated part is the
     name of the function!

## Wrap-up (10 mins)

- Functions allow us to not repeat ourselves; more importantly, **they are our first, and in this class, primary, example of a mechanism for abstraction** -- i.e., building a re-usable piece of a program, that has internals that are not visible to other parts of the program. **Abstraction is one of, if not the most, important ideas in computer science.**
- A function's Signature, with its types, clarifies and communicates what kind of input each parameter expects and the kind of output the function will return.
- Docstrings communicate what the function does in a clear, simple way.
- These serve both as a guide to others, but more importantly, as a guide to
  YOU! As thinking through the inputs / outputs **before** writing the function,
  and describing what the function should do, helps you figure out how to
  implement it.
- In the [design recipe](/class/recipe), they are the first steps for each
  function: the **Signature** (with `...` as the body, so the file runs) and the
  **Docstring**. They come after the steps about the kind of data, its **Data
  definition** and its **Template**, which are written once for all the
  functions on it.
- Template of the day: [numbers, strings, and images](/class/recipe#template-numbers),
  whose template is just the parameters.
