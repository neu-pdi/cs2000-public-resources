## Notes (review before class)
### Examples for Table-Producing Functions

Today is about the **Examples** step, for a function that makes a table:

<DesignRecipe focus="Examples" />

Its examples compare the function's result with the table you expect. For
`apply_discounts`, from [Class 9](/class/9), whose Signature and Docstring we
have:

- **Simplify the input table**: a small one, with just the columns the function
  uses, and enough variety in them. `apply_discounts` only uses `price`:

  ```python
  test_prices = table(["price"], [[50], [120], [80], [40]])
  ```

- **Write computations in the expected table**, rather than doing them by hand:
  `80 * 0.8`, not `64.0`, says where the number came from. The expected table
  goes right in the test, without a name (the input table can be made in the
  test, too):

  ```python
  def test_apply_discounts():
      assert apply_discounts(test_prices) == table(
          ["price"], [[50 * 0.8], [120], [80 * 0.8], [40 * 0.8]]
      )
  ```

- **Build the expected table from rows of an existing one**: `t.columns()` is
  the list of `t`'s column names, and `table` accepts `dict` rows, like those
  from `row`. Keeping only the discounted rows of `prices` (the scarf, the hat
  and the gloves) should give its first, third and fourth rows:

  ```python
  discounted = table(prices.columns(), [prices.row(0), prices.row(2), prices.row(3)])
  ```

- **Cover the helper's cases**: `discount_price` has two cases (under 100, and
  not), so the test table needs prices in both, and 100 itself, at the edge
  between them. `test_prices` is missing that edge, as the next section shows.
  The helper's examples are its own, in `test_discount_price`; the table
  function's examples check that it uses the helper on the right column, and
  handles every case the helper does.

### Checking Table Examples

Starting with HW 3, the autograder runs against your _tests_, not just your
_code_. It is the check from [Class 5](/class/5): each homework gives you an
`#examplar` line, so you can run the same check in the editor before you
submit. Try it on `discount_price` and `apply_discounts`, with the tests above,
by adding this line under the `#level` line:

```python skip
#examplar https://raw.githubusercontent.com/neu-pdi/cs2000-public-resources/refs/heads/python/static/examplar/class10-apply-discounts.json
```

Each run adds a card for each function:

```text
examplar: apply_discounts
  Against correct implementations: your test passes.
  Against buggy implementations: caught 2 of 3 - missed #3.
examplar: discount_price
  Against correct implementations: your test passes.
  Against buggy implementations: caught all 2.
```

- "Against correct implementations" means we take your tests and run them on
  implementations that work. A test that fails there expects the wrong answer.
  If you had read the problem as taking 20 _dollars_ off, and written
  `assert discount_price(50) == 50 - 20`, the card would say:

  ```text
  examplar: discount_price
    Against correct implementations: your test expects the wrong answer:
      test_discount_price
    Against buggy implementations: waiting until all your tests of discount_price pass.
  ```

  Fix the test first: a wrong example makes everything after it unreliable.
- "Against buggy implementations" means we run your tests on implementations
  with bugs we know about (we put them in!), and the goal is that at least one
  of your tests _fails_ on each. That means your tests are thorough enough to
  tell the buggy one from a correct one. These tests pass on the correct
  implementations, so they aren't _wrong_ (don't remove them!).
  `test_discount_price` checks 100, so it catches both buggy helpers, but
  `test_apply_discounts` misses a buggy `apply_discounts`: one that doesn't
  use the helper the way we think. Before class: what row, added to
  `test_prices`, would catch it?
- The card never says what a bug was: working out what your tests don't cover
  is the exercise. With several bugs, think about which cases of the data your
  tests leave out: each interval, each edge between them, zero, and for a table,
  rows of each kind.
- It works before the Body is written: with `...` as both bodies, the card is
  the same, since it runs your tests against our implementations, not yours. So
  check your Examples first, then write the Body.

### `lambda`: Functions without Names

Why not skip a helper like `is_high_value` ([Class 8](/class/8))?

```python error
orders.filter(r["amount"] >= 8)
```

- This is a `NameError`: `r` isn't defined. Arguments are evaluated _before_ a
  function (or method) runs, so `r["amount"] >= 8` is evaluated before `filter`
  starts. In `is_high_value`, `r` is a parameter, so the body waits until `r`
  has a value.
- **`lambda`** makes a temporary function, without a name: `lambda r:` means "a
  function that takes `r`", and the expression after the colon is what it
  returns:

```python
orders.filter(lambda r: r["amount"] >= 8)
```

- Same result as `orders.filter(is_high_value)`: `filter` calls whatever
  function it's given through its own parameter (say, `keep(row)`). Only
  `is_high_value` gets an entry in the directory.
- A `lambda`'s body is one expression: no `return`, type annotations, or `if`.
  Use it for simple functions given to `filter`, `transform_column`, or
  `add_column`; write anything more as a named function, with the full design
  process. (Many, though not all, languages have `lambda`.)
- So a `lambda` can stand in for the local helper in a
  [table template](/class/recipe#template-tables) (`keep`, `compute`, or
  `change`), when the helper's whole design would be one line. It has no
  Signature, Docstring, or Examples of its own, so the table function's examples
  are what check it:

```python
def discounted_rows(t: Table) -> Table:
    """the rows of t whose price gets the discount"""
    return t.filter(lambda r: r["price"] < 100)

def test_discounted_rows():
    assert discounted_rows(prices) == discounted
```

- `discount_price` has an `if`, and tests of its own, so it is a named function;
  `discounted_rows`'s helper is one comparison, so a `lambda` will do.
- Try: add a 10% tip to the amount of each of the coffee cart's orders, with a
  `lambda`.

### Charts

Table methods also make charts ([Tables](/pll/tables) lists them all).
**`freq_bar_chart`** draws a bar for each different value in a column, as tall
as the number of rows with that value:

```python
sale = table(["price"], [[50], [120], [80], [40], [50], [80], [80]])
apply_discounts(sale).freq_bar_chart("price")  # bars for 40.0 (two), 120, 64.0 (three), and 32.0
```

- Try: if the discount changed to "20% off under 100, 30% off at 200 or more",
  which examples would change first, and which template would `discount_price`
  fill in?
