## Notes (review before class)
### Examples for Table-Producing Functions

Today is about the **Examples** step, for a function that makes a table:

<DesignRecipe focus="Examples" />

Its examples compare the function's result with the table you expect. For
`give_raises`, from [Class 9](/class/9), whose Signature and Docstring we have:

- **Simplify the input table**: a small one, with just the columns the function
  uses, and enough variety in them:

  ```python
  wages_test = table(["hourly-wage"], [[15], [20], [18], [18]])
  ```

- **Write computations in the expected table**, rather than doing them by hand.
  The expected table goes right in the test, without a name (the input table can
  be made in the test, too):

  ```python
  def test_give_raises():
      assert give_raises(wages_test) == table(
          ["hourly-wage"], [[15 * 1.1], [20], [18 * 1.1], [18 * 1.1]]
      )
  ```

- **Build the expected table from rows of an existing one**: `t.columns()` is
  the list of `t`'s column names, and `table` accepts `dict` rows, like those
  from `row`. Filtering `employees` to those working exactly 40 hours should
  give its first and fourth rows:

  ```python
  emps_at_40 = table(employees.columns(), [employees.row(0), employees.row(3)])
  ```

- **Cover the helper's cases**: `new_rate` has two cases (under 20, and not),
  so `wages_test` has wages in both, and one, 20, at the edge between them. The
  helper's examples are its own, in `test_new_rate`: the table function's
  examples check that it uses the helper on the right column.

### `lambda`: Functions without Names

Why not skip a helper like `below_1k` ([Class 8](/class/8))?

```python error
shuttle.filter(r["riders"] < 1000)
```

- This is a `NameError`: `r` isn't defined. Arguments are evaluated _before_ a
  function (or method) runs, so `r["riders"] < 1000` is evaluated before
  `filter` starts. In `below_1k`, `r` is a parameter, so the body waits until
  `r` has a value.
- **`lambda`** makes a temporary function, without a name: `lambda r:` means "a
  function that takes `r`", and the expression after the colon is what it
  returns:

```python
shuttle.filter(lambda r: r["riders"] < 1000)
```

- Same result as `shuttle.filter(below_1k)`: `filter` calls whatever function
  it's given through its own parameter (say, `keep(row)`). Only `below_1k` gets
  an entry in the directory.
- A `lambda`'s body is one expression: no `return`, type annotations, or `if`.
  Use it for simple functions given to `filter`, `transform_column`, or
  `add_column`; write anything more as a named function, with the full design
  process. (Many, though not all, languages have `lambda`.)
- So a `lambda` is a short way to fill in the helper's place in the
  [table template](/class/recipe#template-tables), when the helper's whole
  design would be one line. It has no Signature, Docstring, or Examples of its
  own, so the table function's examples are what check it.
- Try: add 10 riders to each row of `shuttle`, with a `lambda`.

### Charts

Table methods also make charts ([Tables](/pll/tables) lists them all).
**`freq_bar_chart`** draws a bar for each different value in a column, as tall
as the number of rows with that value:

```python
employees.freq_bar_chart("hourly-wage")  # bars for 15, 18 (twice as tall), and 20
```

## Announcement -- tests for your tests (10 mins)

- Starting with HW3, the autograder runs against your _tests_, not just your
  _code_. It is the check from [Class 5](/class/5): each homework gives you an
  `#examplar` line, so you can run the same check in the editor before you
  submit.
- Try it on the Recap program below, by adding this line under its `#level`
  line:

  ```python skip
  #examplar https://raw.githubusercontent.com/neu-pdi/cs2000-public-resources/refs/heads/main/static/examplar/class10-apply-discounts.json
  ```

  Each run adds a card for each function:

  ```text
  examplar: apply_discounts
    Against correct implementations: your test passes.
    Against buggy implementations: caught 2 of 3 - missed 3.
  examplar: discount_price
    Against correct implementations: your test passes.
    Against buggy implementations: caught 1 of 2 - missed 1.
  ```

- "Against correct implementations" means we take your tests and run them on
  implementations that work. A test that fails there expects the wrong answer.
  If you had read the problem as taking 20 _dollars_ off, and written
  `assert discount_price(50) == 50 - 20`, the card would say:

  ```text
  examplar: discount_price
    Against correct implementations: your test expects the wrong answer:
      test_discount_price
    Against buggy implementations: waiting until all your tests of discount_price pass.
  ```

  Fix the test first: a wrong example makes everything after it unreliable.
- "Against buggy implementations" means we run your tests on implementations
  with bugs we know about (we put them in!), and the goal is that at least one
  of your tests _fails_ on each. That means your tests are thorough enough to
  tell the buggy one from a correct one. The Recap's tests pass on the correct
  implementations, so they aren't _wrong_ (don't remove them!), but they miss a
  buggy `apply_discounts` and a buggy `discount_price`. Before class: what input,
  missing from both, would catch them?
- The card never says what a bug was: working out what your tests don't cover
  is the exercise. With several bugs, think about which cases of the data your
  tests leave out: each interval, each edge between them, zero, and for a table,
  rows of each kind.
- It works before the Body is written: with `...` as both bodies, the card is
  the same, since it runs your tests against our implementations, not yours. So
  check your Examples first, then write the Body.

## Recap (15 mins)

A store takes 20% off every price under 100. Read through the program:

```python
prices = table(
    ["price"],
    [[50], [120], [80], [40], [50], [80], [80]],
)

def discount_price(price: float) -> float:
    """reduces price by 20%, if it is below 100"""
    if price < 100:
        return price * 0.8
    else:
        return price

def test_discount_price():
    assert discount_price(50) == 50 * 0.8
    assert discount_price(120) == 120

def apply_discounts(t: Table) -> Table:
    """transforms 'price' column by reducing 20%, if value is below 100"""
    return t.transform_column("price", discount_price)

def test_apply_discounts():
    test_table = table(["price"], [[50], [120], [80], [40]])
    assert apply_discounts(test_table) == table(
        ["price"], [[50 * 0.8], [120], [80 * 0.8], [40 * 0.8]]
    )

def discounted_rows(t: Table) -> Table:
    """the rows of t whose 'price' gets the discount"""
    return t.filter(lambda r: r["price"] < 100)

def test_discounted_rows():
    test_table = table(["price"], [[50], [120], [80]])
    assert discounted_rows(test_table) == table(["price"], [[50], [80]])

apply_discounts(prices).freq_bar_chart("price")
```

- Why is `discount_price` a named function, while `discounted_rows` uses a
  `lambda`?
- In `test_apply_discounts`, why write `80 * 0.8` rather than `64.0`? Which row
  of its `test_table` checks the `else` of `discount_price`?
- How many bars does the chart have, and which value's bar is tallest?
- Which shape of the table template does each of `apply_discounts` and
  `discounted_rows` use, and what decided the helper's Signature?
- If the discount changed to "20% off under 100, 30% off at 200 or more", which
  examples would change first, and which template would `discount_price` fill
  in?
