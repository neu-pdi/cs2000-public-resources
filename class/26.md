## Notes (review before class)
### Mutable Data

A library program keeps a record of each book, with how many copies are on its
shelves. The fields of a dataclass can be changed, by putting a field access on
the left of an `=`:

```python
@dataclass
class LibraryBook:
    id: int
    title: str
    copies: int

kindred = LibraryBook(205, "Kindred", 3)
kindred.copies = kindred.copies - 1
```

- **Mutable** data can be changed; **immutable** data, all we've used until now,
  cannot.
- The last line changes the _existing_ record: `kindred.copies` is now `2`.
  `LibraryBook(kindred.id, kindred.title, kindred.copies - 1)` would make a
  _new_ record instead.
- Every dataclass field can be changed, so it's up to you not to change one that
  shouldn't (like the `id`).
- Setting a name and setting a field both use `=`, but they mean very different
  things (compare rules 2 and 3 in The Heap, below).

### State

A test written right after making the record fails, because PLL runs the whole
file first, and only then calls the test functions:

```python error
kindred = LibraryBook(205, "Kindred", 3)

def test_copies():
    assert kindred.copies == 3

kindred.copies = kindred.copies - 1
```

- The test passes if it expects `2`, but then fails if the last line is removed:
  it is only _sometimes_ true.
- **State**: the values of the defined names at some point as the program runs.
  There is a state in which `kindred.copies` is `3`, and a later one in which
  it is `2`.
- Not just tests: from now on, every instruction runs in some state, and the
  same code can give different answers in different states.

### Testing Functions that Mutate

A function that mutates its input often returns nothing (`None`), so the
recipe changes a little ([data that changes](/class/recipe#template-mutation)):

<DesignRecipe focus="Docstring, Examples, Template" />

- **Data definition**: `LibraryBook`, above.
- **Template**: the field template from [Class 20](/class/20), ending by setting
  each field that changes (on the left of an `=`), instead of `return ...`:

```python
def _library_book_temp(b: LibraryBook) -> None:
    ...
    b.id
    ...
    b.title
    ...
    b.copies
    ...
    b.copies = ...
```

- **Signature**: the result type is `None`.
- **Docstring**: says what changes, since that is the function's whole job.
- **Examples**: a test checks the _effect_ of calling it, in parts (Setup,
  Call, Check, explained after the recipe):

```python
def test_check_out():
    # Setup
    book = LibraryBook(205, "Kindred", 3)

    # Call
    check_out(book)

    # Check
    assert book.copies == 2
```

- **Body**: copy the template's body into `check_out`. One copy fewer is on the
  shelves, and nothing else changes, so the other fields' lines go:

```python
def check_out(b: LibraryBook) -> None:
    """records that one copy of b has been checked out"""
    b.copies = b.copies - 1
```

A test for a function that uses mutation has three or four parts:

1. **Setup**: set up the values to give the function.
2. **Call**: call the function.
3. **Check**: check that the call had the desired effect.
4. **Teardown**: restore data to their expected state.

- `test_check_out` needs no Teardown, since it made its own record. Checking
  `check_out(kindred)` instead would depend on whatever `kindred.copies` was
  when the test ran (and change it); a test that changes data used elsewhere
  must undo its changes.
- Setup may also need to reset existing data (which other code may have
  mutated) to the values the test expects.
- Try: write a test for this function:

```python
def add_copies(b: LibraryBook, n: int) -> None:
    """adds n copies of b to the shelves"""
    b.copies = b.copies + n
```

### Aliasing

The library also has displays, each with a theme and the book it features.
Continuing the program, `kindred` (with 2 copies left) is featured on two
displays, and a reader checks out the copy from the Staff Picks display:

```python
@dataclass
class Display:
    theme: str
    book: LibraryBook

dune = LibraryBook(302, "Dune", 4)
staff_picks = Display("Staff Picks", kindred)
new_arrivals = Display("New Arrivals", kindred)

staff_picks.book.copies = staff_picks.book.copies - 1
```

- `staff_picks.book.copies` is now `1`, and so is `new_arrivals.book.copies`,
  even though the change was made through `staff_picks.book`, not
  `new_arrivals.book`.
- **Aliases**: different names for the exact same datum. Here `kindred`,
  `staff_picks.book`, and `new_arrivals.book` are aliases.
- Without mutation, sharing didn't _matter_. With it, a change through one alias
  is seen through all of them, so always be on the alert for aliases.

### Why the Directory Isn't Enough

Values in the directory can't contain names (Python replaces names with their
values when it evaluates expressions), so after the checkout the directory
would be:

```
kindred       LibraryBook(205, "Kindred", 1)
dune          LibraryBook(302, "Dune", 4)
staff_picks   Display("Staff Picks", LibraryBook(205, "Kindred", 1))
new_arrivals  Display("New Arrivals", LibraryBook(205, "Kindred", 1))
```

- Nothing here says why the checkout changed three numbers of copies but not
  `dune`'s. With mutation _and_ aliasing, mapping names to values breaks down:
  _it doesn't capture the aliases_.
- `Display("Staff Picks", kindred)` would show the sharing. Names can't go in
  values, but one term, reused wherever a value is shared, is the right idea:
  it's what the computer does.

### The Heap

- The computer's **memory** is a large number of slots, each labeled with an
  **address**, the way a street address picks out one building. Python stores
  its data in a portion of memory called the **heap**.
- A constructor puts the new data in a slot in the heap, and the directory gets
  the _address_ of that slot, not the value.
- We write addresses as `@` and four digits. The first (`@1001`) is arbitrary;
  later data get the next addresses, in order.
- `Display("Staff Picks", kindred)` looks up `kindred` and gets an address,
  `@1001`, so the `Display` in the heap contains that address.

The same program, after the checkout, as a directory and heap:

```
Directory            Heap
kindred       @1001  @1001  LibraryBook(205, "Kindred", 1)
dune          @1002  @1002  LibraryBook(302, "Dune", 4)
staff_picks   @1003  @1003  Display("Staff Picks", @1001)
new_arrivals  @1004  @1004  Display("New Arrivals", @1001)
```

- `kindred`, `staff_picks.book`, and `new_arrivals.book` all lead to `@1001`:
  that makes them aliases. `dune`'s address appears nowhere else.

Three rules for how running a program changes the directory and the heap:

1. Constructing a new piece of structured data puts it at the next address in
   the heap.
2. Associating a name with a piece of structured data maps the name, in the
   directory, to the address of that data.
3. Modifying a field of structured data modifies the data in the heap.

- The checkout (rule 3) changed only the `LibraryBook` at `@1001`, which all
  three names lead to.
- `featured = kindred` doesn't change the heap at all (rule 2): it maps
  `featured` to `@1001`, making it one more alias.
- Try: write three expressions, each starting from a different name in the
  directory, that give the number of copies at `@1001`. Would
  `staff_picks.book.copies = new_arrivals.book.copies - 1` check out another
  copy? Is it a good way to write it?

### Basic Data and the Heap

Basic data (numbers, strings, ...) don't go in the heap. Continuing the program:

```python
@dataclass
class Shelf:
    label: str
    row: int

n = 4
section = "Fiction"
shelf1 = Shelf("Poetry", 11)
shelf2 = Shelf(section, 10 + n)
```

```
Directory              Heap
n        4             @1005  Shelf("Poetry", 11)
section  "Fiction"     @1006  Shelf("Fiction", 14)
shelf1   @1005
shelf2   @1006
```

- The heap is there so that a change to a field is seen through every alias.
  Basic data have no fields, so (though real implementations vary) think of them
  as living right in the directory.
- Structured data have an identity (an address) and parts; basic data can't be
  broken down.
- Strings do have characters, but nothing in Python changes the characters of a
  string (`+` and the like make new strings), so we treat them as basic data.

### Equality

In a new file (after the dataclasses), with two checkpoints:

```python
b1 = LibraryBook(410, "Beloved", 5)
b2 = LibraryBook(410, "Beloved", 5)
b3 = LibraryBook(410, "Beloved", 2)
b4 = b2
# checkpoint 1
b2.copies = 8
# checkpoint 2
```

At checkpoint 1:

```
Directory     Heap
b1  @1001     @1001  LibraryBook(410, "Beloved", 5)
b2  @1002     @1002  LibraryBook(410, "Beloved", 5)
b3  @1003     @1003  LibraryBook(410, "Beloved", 2)
b4  @1002
```

- `b3` has a different number of copies: it isn't equal to the others.
- `b1` and `b2` have the same contents, but different addresses. At checkpoint
  2, `@1002` holds `LibraryBook(410, "Beloved", 8)`, so their contents differ.
- `b2` and `b4` are aliases, so they change in lockstep: both now show `8`.

There are two kinds of equality, with an operator for each:

- **Structural equality**, `==`: do the values have the same contents (do they
  look the same when displayed)?
- **Reference equality**, `is`: are they at the same address (are the names
  aliases, for what is really only one value)?

```python
b1 == b2  # True at checkpoint 1, but False at checkpoint 2
b2 == b4  # True at both
b1 is b2  # False at both
b2 is b4  # True at both
```

- Mutation is why `b1 == b2` stopped being true, which seems to break a basic
  idea of "equality": values that are `==` now may not be later.
- `==` is more accepting, so it is usually the right default. Use `is` when you
  need to know whether two expressions evaluate to the same address.

Try: in another new file, predict each answer, then draw the directory and heap
to check:

```python

copy2 = copy1
copy3 = LibraryBook(101, "The Curious Incident", 5)

```

- What are `copy1.copies`, `copy2.copies`, and `copy3.copies`?
- What are `copy1 == copy3`, `copy1 is copy2`, and `picks.book is copy3`? Which
  of them would change if the last line were deleted?
