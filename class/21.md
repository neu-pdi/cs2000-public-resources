## Notes (review before class)
### Conditional Data

- **Conditional data**: a type with several kinds of values, called
  **variants**, each with its own details. It's an "or": a washing machine is
  idle _or_ washing _or_ drying; a payment is in cash _or_ by card _or_ by
  check.
- Sometimes we care which variant we have (what the machine's screen should
  show), sometimes not (counting payments).

### Defining Conditional Data

One dataclass per variant, then a name for the type that is any of them:

```python
@dataclass
class Idle:
    pass

@dataclass
class Washing:
    pass

@dataclass
class Drying:
    pass

MachineState = Idle | Washing | Drying
```

- Each `|` ("or", as in `float | str` in [Class 12](/class/12)) adds a variant.
- A variant with no fields has the body `pass` ("nothing here"). Making one
  still takes `()`: `Idle()`.

Variants can have fields. A payment system records how each payment was made:
in cash, by credit card (with its number and expiration date), or by check
(with the bank account, routing number, and check number):

```python
@dataclass
class Cash:
    pass

@dataclass
class Credit:
    card_number: str
    expiry: str

@dataclass
class Checking:
    bank_account: str
    routing: str
    check_number: int

PaymentMethod = Cash | Credit | Checking

payment_1 = Cash()
payment_2 = Credit("1111-2222-3333-4444", "09/26")
payment_3 = Checking("987654321", "111", 55)
```

- _One_ type, `PaymentMethod`, with _three_ constructors, `Cash`, `Credit`, and
  `Checking`.
- The data definition's examples include at least one of each variant, so that
  every function on `PaymentMethod` has one to test.
- Annotate an example with its variant (`payment_2: Credit`) or the whole type
  (`payment_2: PaymentMethod`, losing the distinction).
- Structured data (like `BookRecord`, [Class 20](/class/20)) is the case with
  one variant.
- Python's built-in **`None`** means "no value"; `str | None` is "a string, or
  `None`" ([Class 25](/class/25) uses it).

### Telling Variants Apart: `match`

`payment_2.expiry` is fine, since `payment_2` is a `Credit`; but for any
`PaymentMethod` `p`, `p.expiry` is an error when `p` is `Cash`. Instead,
**`match`** has a `case` for each variant:

```python
def display(s: MachineState) -> str:
    """what the washing machine's screen shows in state s"""
    match s:
        case Idle():
            return "Ready"
        case Washing():
            return "Washing..."
        case Drying():
            return "Drying..."
```

Try: leave out the `()` in `case Idle():`. Then leave out the `Drying` case,
and try both `display(Washing())` and `display(Drying())`.

### Fields in a `case`

A `case` can list names for the variant's fields, in order; while that case
runs, they are in the directory (no `.` needed). That gives the **template** for
conditional data: a `match` with one `case` per variant, naming each variant's
fields ([templates for conditional data](/class/recipe#template-variants)). It's
the interval template from [Class 5](/class/5) again, one branch per case of the
data, but now the cases come from the data definition, not from numbers.

<DesignRecipe focus="Data definition, Examples, Template" />

- **Data definition**: `PaymentMethod`, and its examples `payment_1`,
  `payment_2`, and `payment_3`, above.
- **Template**: one `case` per variant, with a line for each of its fields:

```python
def _payment_method_temp(p: PaymentMethod) -> ...:
    match p:
        case Cash():
            return ...
        case Credit(cn, exp):
            ...
            cn
            ...
            exp
            ...
            return ...
        case Checking(acc, rout, num):
            ...
            acc
            ...
            rout
            ...
            num
            ...
            return ...
```

- **Signature** and **Docstring**:

```python
def display_payment(p: PaymentMethod) -> str:
    """describes how p was paid, for a receipt"""
    ...
```

- **Examples**: tests, at least one per variant:

```python
def test_display_payment():
    assert display_payment(payment_1) == "Paid in cash"
    assert display_payment(payment_2) == "Paid by credit card expiring on 09/26"
    assert display_payment(payment_3) == "Paid by check from account 987654321"
```

- **Body**: copy the template's body into `display_payment`, and fill in each
  case from its example:

```python
def display_payment(p: PaymentMethod) -> str:
    """describes how p was paid, for a receipt"""
    match p:
        case Cash():
            return "Paid in cash"
        case Credit(cn, exp):
            return "Paid by credit card expiring on " + exp
        case Checking(acc, rout, num):
            return "Paid by check from account " + acc
```

- The names needn't match the fields': fields get long names; cases, short ones.
- `display_payment(payment_2)`: `payment_2` is
  `Credit("1111-2222-3333-4444", "09/26")`, so the second case matches, with
  `cn` as `"1111-2222-3333-4444"` and `exp` as `"09/26"`; it returns
  `"Paid by credit card expiring on 09/26"`.
- The `Credit` and `Checking` cases name fields their bodies don't use (`cn`,
  `rout`, `num`): the template lists every field, and the body uses what it
  needs.
- Try: what does `display_payment(Checking("24680", "135", 7))` return, and
  which names does its `case` add to the directory? To also accept gift cards,
  each with a card number and a balance, what would you add, and where? Which
  step of the recipe changes first?

**Location tags** (the last four go together). A location tag is a small device
that nearby phones detect, and report to the tag's owner, so that a lost bag or
set of keys can be found.

```python
# A TagId is a str: a tag's unique identifier.
# A Time is an int: the number of seconds since Jan 1, 2025.

@dataclass
class OwnTagEncounter:
    tagid: str
    time: int

@dataclass
class OtherTagEncounter:
    tagid: str
    time: int

# An Encounter is a record of your phone seeing a tag: an OwnTagEncounter if
# the tag is yours, and an OtherTagEncounter if it isn't.
Encounter = OwnTagEncounter | OtherTagEncounter

encounter_1 = OwnTagEncounter("t1", 10)
encounter_2 = OwnTagEncounter("t1", 20)
encounter_3 = OtherTagEncounter("t2", 30)
```

1. Write `_encounter_temp`. Then design `own_encounters`, which takes a
  `list[Encounter]`, and gives just its `OwnTagEncounter`s.
1. Design `tag_activity_count`, which takes a tag's id and a `list[Encounter]`,
  and gives how many times that tag was seen.
1. Design `last_encounter`, which takes a tag's id and a `list[Encounter]`, and
  gives the latest time that the tag was seen (as an `OwnTagEncounter` or an
  `OtherTagEncounter`), or -1 if it never was.
