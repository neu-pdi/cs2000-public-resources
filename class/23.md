## Notes (review before class)
### Lists as Recursive Data

`match` tells apart variants of conditional data ([Class 21](/class/21)), and
empty and non-empty lists ([Class 22](/class/22)): lists are conditional data,
built into Python. Here is a list of our own, a stack of pancakes: it is either
just the `Plate`, or a `Pancake` on top of a smaller stack. (Try, before reading
on: what fields should `Pancake` have, and of what types?)

```python
@dataclass
class Plate:
    pass

@dataclass
class Pancake:
    flavor: str
    below: "Stack"

Stack = Plate | Pancake
```

- `Pancake` has the two parts of a non-empty list: its own `flavor`, a `str`,
  and the stack `below` it, the rest, so a `Stack`.
- `Stack` isn't defined until after the two classes, so inside them its name is
  written in quotes.
- `below` has the very type being defined: a data definition with a field of
  its own type is **recursive data**.
- This works because every stack starts from the `Plate()`, which doesn't refer
  to `Stack`; each `Pancake` goes on top. Making a stack of plain, then banana,
  then blueberry on top (each `below` a whole stack):

```python
Plate()
Pancake("plain", Plate())
Pancake("banana", Pancake("plain", Plate()))
Pancake("blueberry", Pancake("banana", Pancake("plain", Plate())))
```

- Recursive data is **arbitrarily sized**: a `Pancake` can go on top of any
  stack, so functions must handle stacks of any height.

### A Function over Recursive Data

`has_blueberry` says whether a stack has a blueberry pancake anywhere in it.
The template comes first, right after the data definition: an outline of any
function on a `Stack`, named for the data, as templates have been since
[Class 4](/class/4): a `match` on the variants, with a line for each of a
variant's fields where its answer goes:

```python
def _stack_temp(s: Stack) -> ...:
    match s:
        case Plate():
            return ...
        case Pancake(flavor, below):
            ...
            flavor
            ...
            below
            ...
            return ...
```

Then `has_blueberry`'s Signature, Docstring, and Examples:

```python
def has_blueberry(s: Stack) -> bool:
    """whether any pancake in the stack s is blueberry"""
    ...

def test_has_blueberry():
    assert not has_blueberry(Plate())
    assert has_blueberry(Pancake("blueberry", Plate()))
    assert has_blueberry(Pancake("plain", Pancake("blueberry", Plate())))
    assert has_blueberry(Pancake("plain", Pancake("banana", Pancake("blueberry", Pancake("plain", Plate())))))
    assert not has_blueberry(Pancake("plain", Pancake("banana", Pancake("chocolate", Pancake("plain", Plate())))))
```



- With only the first two tests (the empty plate, and a single blueberry
  pancake), the card says `caught 2 of 5 - missed #1, #4, #5`. Which of the
  other three tests catch them? What do those stacks have that the first two
  don't?

  examples are right and thorough.

Then copy the template's body into `has_blueberry`, and fill it in:

- `Plate()`: no pancakes, so the answer is `False`.
- `Pancake(flavor, below)`: if `flavor` is `"blueberry"`, the answer is `True`;
  otherwise, it is whether the stack `below` has a blueberry pancake.
- `below` is a `Stack`, so we could `match` on it, then on what's below _that_,
  ...; but any number of copies fails on a stack one pancake taller.
- Instead, call the function whose job is exactly that: `has_blueberry(below)`.
  All the tests pass:

```python
def has_blueberry(s: Stack) -> bool:
    """whether any pancake in the stack s is blueberry"""
    match s:
        case Plate():
            return False
        case Pancake(flavor, below):
            if flavor == "blueberry":
                return True
            else:
                return has_blueberry(below)
```

- Read `has_blueberry(below)` by its Docstring: whether any pancake in the
  stack below is blueberry. Then the `else` says: the top isn't blueberry, so
  the stack has one exactly when the stack below does. That's all it takes to
  see that the body is right; there's no need to follow the calls one inside
  another.
- The function does something with the non-recursive part (checks `flavor`),
  and combines it with the result of the same function on the recursive part
  (`below`).

### A Template for Recursive Data

In [Class 22](/class/22), working through examples gave functions that call
themselves on the rest. The same structure comes from _the shape of the data_:
break it into variants (`match`), pull out each variant's fields, and call the
function on any recursive fields (fields of the same type). For `Stack`, the
outline above, with the recursive call in place of `below`:

```python
def _stack_temp(s: Stack) -> ...:
    match s:
        case Plate():
            return ...
        case Pancake(flavor, below):
            ...
            flavor
            ...
            _stack_temp(below)
            ...
            return ...
```

- A **template**, like every template since [Class 4](/class/4): the outline of
  _any_ function on a `Stack` (hence its name, which is the data's). Every data
  definition has one.
- To write a specific function, copy the template's body into it, rename the
  recursive call, and fill in the `...`s: what does the recursive call return,
  by its Docstring, and how do you combine it with the non-recursive parts?
- Examples ([Class 22](/class/22)) and the template lead to the same function,
  but the template scales to complicated data definitions (there will be
  _many_), where writing out examples by hand is tedious.

**Strategy: Writing a Template for Recursive Data.** Given a recursive data
definition:

1. Write its Signature: the data's name, with `_` in front and `_temp` at the
   end, taking the data, with `...` as its result type.
2. Use `match` to split the input into its variants.
3. In each case, put each of its fields on a line of its own, with `...` before
   and after each, and `return ...` at the end.
4. In place of each field of the type being defined, put a call of the template
   itself on it.

### Another Function on Stacks

The design recipe, for counting the blueberry pancakes in a stack. The data
definition's examples extend each other, and so do the tests' inputs:

```python
one_blue = Pancake("plain", Pancake("blueberry", Plate()))
two_blue = Pancake("blueberry", one_blue)

def blueberries(s: Stack) -> int:
    """how many of the pancakes in the stack s are blueberry"""
    match s:
        case Plate():
            return 0
        case Pancake(flavor, below):
            if flavor == "blueberry":
                return blueberries(below) + 1
            else:
                return blueberries(below)

def test_blueberries():
    assert blueberries(Plate()) == 0
    assert blueberries(Pancake("plain", Plate())) == 0
    assert blueberries(Pancake("blueberry", Plate())) == 1
    assert blueberries(one_blue) == 1
    assert blueberries(two_blue) == 2
```

- Line `blueberries` up against `_stack_temp`: what did each `...` become?
- `two_blue` is `one_blue` with a blueberry pancake on top, and its answer is
  one more: that difference is the `+ 1` in the body.
- Which test would fail if `return blueberries(below) + 1` were `return 1`?

### Every Template So Far

The rule behind this template is the one behind each template since
[Class 5](/class/5): **one part of the body for each part of the data**.
Recursive data is that rule once more, plus a recursive call on each field of
the type being defined:

| Data | The template | From |
| --- | --- | --- |
| a number split into intervals | an `if` branch per interval | [Class 5](/class/5) |
| a row | a line for each column: `r["col"]` | [Class 8](/class/8) |
| a table, made into a new one | fewer rows (`filter`), a new column (`add_column`), or a changed column (`transform_column`) | [Class 9](/class/9) |
| a fixed set of strings | an `if` branch per value, and an `else` | [Class 11](/class/11) |
| a list, with built-ins | fewer elements (`filter`), each one changed (`map`), or one value (`sum`) | [Class 14](/class/14) |
| a list, with a loop | a `for`, combining, building, or checking | [Class 16](/class/16) |
| a dataclass | a line for each field: `s.field` | [Class 20](/class/20) |
| a union | a `case` per variant, naming its fields | [Class 21](/class/21) |
| recursive data | a `case` per variant, naming its fields, and a recursive call on each field of its own type | today |

Each is on the [Design Recipe](/class/recipe#templates) page.

### The Design Recipe

The steps are the same as since [Class 4](/class/4), for recursive data too:

<DesignRecipe focus="Data definition, Template" />

- **Data definition**: recursive, with examples that extend each other (as
  `two_blue` extends `one_blue`, above).
- **Template**: from the data definition, with the strategy above, once for all
  the functions on it.
- **Signature**: the name is needed for the recursive calls, and the types guide
  the body.
- **Docstring**: what the function gives for any list, not only the examples.
- **Examples**: tests with _concrete_ data, at least one per variant, including
  inputs that extend other inputs. Where one input extends another, the
  difference in outputs becomes the body, as in [Class 22](/class/22).
- **Body**: copy the template's body, and fill it in, using your examples.
- **Test and revise**: run the examples, to check the function behaves as you
  expect. They were about input-output behavior; now add tests that focus on
  the implementation's details.
