### Computing New Columns

Lifting computes a whole column at once, e.g. each order's price before
discounts:

```python
TICKET_PRICE = 10.0
events["total"] = events["numtix"] * TICKET_PRICE
```

A mask and `.loc` update just some rows, e.g. 10% off with the `"birthday"`
code:

```python
bday_mask = events["discount"] == "birthday"
events.loc[bday_mask, "total"] = events["total"] * 0.90
```

- The same notation adds a column or updates one (unlike PLL's `add_column`
  and `transform_column`): pandas creates the column if there is none by that
  name.

### Applying a Function

When lifting isn't enough, **`apply`** calls a function (a `lambda` or a named
one) on each value of a Series, or, with `axis=1`, on each row of a DataFrame:

```python
events["valid_email"] = events["email"].apply(lambda e: "@" in e)
events["contact"] = events.apply(lambda r: r["name"] + " <" + r["email"] + ">", axis=1)
```

- A Series' `apply` passes single values, like `transform_column`.
- With `axis=1`, the function gets a whole row, so a column can be computed (or
  recomputed) from several of its cells, which `transform_column` can't do.
- So, as for PLL's table template, which job it is decides the helper's
  Signature: a value for a Series' `apply`, a row for `axis=1`. A named helper
  gets the whole recipe.

### Sorting

```python
events.sort_values("numtix")                   # fewest tickets first
events.sort_values("numtix", ascending=False)  # most tickets first
```

- Like PLL's `order_by`: it makes a new DataFrame (`events` doesn't change), in
  which each row keeps its label.

### Aggregating and Grouping

```python
events["numtix"].sum()    # total number of tickets sold
events["numtix"].mean()   # average number of tickets per order
```

To summarize one column for each value of another (a spreadsheet's "pivot
table"), use **`groupby`**, rather than filtering to each value and summing:

```python
events.groupby("discount").count()           # how many orders had each code
events.groupby("discount")["numtix"].sum()   # tickets sold with each code
```

- `groupby` takes the column whose values group the rows, and returns a
  `GroupBy`: select a column of it, and an operation on it is done per group.
- The second line is a Series labeled by discount code: 14 tickets with no code
  (`""`), 2 with `"birthday"`, 8 with `"student"`.
- The pandas documentation lists many more `GroupBy` operations (means, other
  statistics, ...).

## Recap (15 mins)

We continue with the restaurant orders from [Class 26](/class/26): `orders` is
loaded from the CSV file, and `first_orders` is its first three rows, made by
hand. `orders` is:

```
         date    dish  quantity order_type
0  2023-07-01   Pasta         2    dine-in
1  2023-07-01   Salad         1    takeout
2  2023-07-02  Burger         3    dine-in
3  2023-07-02   Pasta         2    dine-in
4  2023-07-03   Steak         1    takeout
```

Here is more PLL table work, done in pandas, with the PLL version in the
comments. Its two functions are designed with the same recipe as PLL table
functions, since the recipe doesn't depend on the library:

<DesignRecipe />

- `order_total`:
  - **Data definition**: a row of `orders`, a `pd.Series`, with `date`,
    `dish`, `quantity`, and `order_type`.
  - **Signature** and **Docstring**: from a `pd.Series` to a `float`, the
    order's price.
  - **Examples**: tests on rows of `first_orders`, the small DataFrame from
    [Class 26](/class/26), with prices worked out by hand.
  - **Template**: the row template, with the columns:
    `... r["date"] ... r["dish"] ... r["quantity"] ... r["order_type"] ...`.
  - **Body**: the price only needs `quantity` and `dish`.
- `takeout_only`: from a `pd.DataFrame` to a `pd.DataFrame`. Its answer has
  fewer rows, so it's the `filter` shape of the table template, done the pandas
  way, with a mask.

```python
PRICES = {"Pasta": 12.0, "Salad": 8.0, "Burger": 10.0, "Steak": 25.0}

def order_total(r: pd.Series) -> float:
    """the price of order r: its quantity times its dish's price"""
    return r["quantity"] * PRICES[r["dish"]]

def takeout_only(t: pd.DataFrame) -> pd.DataFrame:
    """the takeout orders in t"""
    # PLL: t.filter(lambda r: r["order_type"] == "takeout")
    return t[t["order_type"] == "takeout"]

def test_order_total():
    assert order_total(first_orders.iloc[0]) == 24.0   # 2 Pasta
    assert order_total(first_orders.iloc[1]) == 8.0    # 1 Salad

def test_takeout_only():
    assert len(takeout_only(first_orders)) == 1
    assert takeout_only(first_orders).iloc[0]["dish"] == "Salad"

# PLL: orders.order_by("quantity", ascending=False)
by_quantity = orders.sort_values("quantity", ascending=False)

# PLL: orders.add_column("total", order_total)
orders["total"] = orders.apply(order_total, axis=1)

# PLL: orders.transform_column("total", lambda price: price * 0.9)
orders["total"] = orders["total"].apply(lambda price: price * 0.9)

# PLL: filter to each order type, then sum each one's totals
sales = orders.groupby("order_type")["total"].sum()
```

- What is `order_total(orders.iloc[4])`? What is `sales["takeout"]`?
- What are `by_quantity.iloc[0]["dish"]` and `by_quantity.loc[0]["dish"]`? Does
  `by_quantity` have a `total` column?
- Why does `orders.apply(order_total, axis=1)` need `axis=1`, while
  `orders["total"].apply(...)` doesn't? Which `apply` could be written with
  lifting instead?
- Why test `takeout_only` on `first_orders`, rather than on `orders`? What would
  a test on `orders` have to change, after the last lines run?

## Wrap-up (5 mins)

- Pandas provides the same table operations you learned with PLL tables: filtering with boolean conditions, sorting by columns, adding new columns with computations, and transforming existing columns.
- The syntax is different (boolean masks vs functions, `.sort_values()` vs `.order_by()`), but the concepts and capabilities are the same.
- Template of the day: none for pandas, but the
  [table template](/class/recipe#template-tables) still decides what the answer
  is, and the recipe's steps are the same with any library.
