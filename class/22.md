## Notes (review before class)
### Any Number of Pancakes

A dataclass has a fixed number of fields ([Class 20](/class/20)). A stack of
two pancakes could be a dataclass with two flavor fields, and a stack of three
another, with three; but a stack can have any number of pancakes, and no fixed
number of fields holds them all. Python's lists hold any number of values
([Class 13](/class/13)), but they are built in. Today: how to define data of any
size ourselves, from nothing but dataclasses and unions.

A stack of pancakes is a pancake on top of a stack: the top pancake's flavor,
and the stack below it. (Try, before reading on: what fields does `Pancake`
need, and of what types?)

```python skip
@dataclass
class Pancake:
    flavor: str
    below: Pancake
```

- `below` has the very type being defined.
- Now try to make an example. `Pancake("plain", ...)` needs a stack below it,
  which needs a stack below _that_, and so on: there's no way to start.

### Self-Referential Data

The way to start is conditional data ([Class 21](/class/21)): a stack is either
just the `Plate`, or a `Pancake` on top of a smaller stack.

```python
@dataclass
class Plate:
    pass

@dataclass
class Pancake:
    flavor: str
    below: Stack

Stack = Plate | Pancake
```

- `Pancake` has its own `flavor`, a `str`, and the stack `below` it, a `Stack`.
- `below` has the type being defined, `Stack`: a data definition with a field of
  its own type is **self-referential data** (also called **recursive data**).
- Every stack starts from the `Plate()`, which doesn't refer to `Stack`, and each
  `Pancake` goes on top. A stack of plain, then banana, then blueberry on top
  (each `below` a whole stack):

```python
Plate()
Pancake("plain", Plate())
Pancake("banana", Pancake("plain", Plate()))
Pancake("blueberry", Pancake("banana", Pancake("plain", Plate())))
```

- How many pancakes does each of these have? How would you make a stack of 79?
- Self-referential data is **arbitrarily sized**: a `Pancake` can go on top of
  any stack, so a function on stacks must handle stacks of any height.

### A Template That Refers to Itself

The template comes from the data, as every template has since
[Class 4](/class/4): a `match` on the variants, with a line for each of a
variant's fields. One rule is new: a field of the type being defined gets a call
of the template itself.

```python
def _stack_temp(s: Stack) -> ...:
    match s:
        case Plate():
            return ...
        case Pancake():
            ...
            s.flavor
            ...
            _stack_temp(s.below)
            ...
            return ...
```

- The data refers to itself, so the template does, and so will every function
  on a `Stack`.
- It's the outline of _any_ function on a `Stack` (hence its name, the data's).
  To write a specific function, copy the template's body into it, rename the
  recursive call, and fill in the `...`s.

**Strategy: Writing a Template for Self-Referential Data.** Given a
self-referential data definition:

1. Write its Signature: the data's name, with `_` in front and `_temp` at the
   end, taking the data, with `...` as its result type.
2. Use `match` to split the input into its variants.
3. In each case, put each of its fields on a line of its own, read with the `.`
   (as `s.flavor`), with `...` before and after each, and `return ...` at the
   end.
4. In place of each field of the type being defined, put a call of the template
   itself on it.

### A Function on Stacks

`has_blueberry` says whether a stack has a blueberry pancake anywhere in it.
Its Signature, Docstring, and Examples:

```python
def has_blueberry(s: Stack) -> bool:
    """whether any pancake in the stack s is blueberry"""
    ...

def test_has_blueberry_of_an_empty_stack():
    assert not has_blueberry(Plate())

def test_has_blueberry_of_one_blueberry_pancake():
    assert has_blueberry(Pancake("blueberry", Plate()))

def test_has_blueberry_under_a_plain_pancake():
    assert has_blueberry(Pancake("plain", Pancake("blueberry", Plate())))

def test_has_blueberry_near_the_bottom_of_a_deep_stack():
    assert has_blueberry(Pancake("plain", Pancake("banana", Pancake("blueberry", Pancake("plain", Plate())))))

def test_has_blueberry_not_in_a_deep_stack():
    assert not has_blueberry(Pancake("plain", Pancake("banana", Pancake("chocolate", Pancake("plain", Plate())))))
```

Then copy the template's body into `has_blueberry`, and fill it in:

- `Plate()`: no pancakes, so the answer is `False`.
- A `Pancake`: if `s.flavor` is `"blueberry"`, the answer is `True`; otherwise,
  it is whether the stack `s.below` has a blueberry pancake.
- That is exactly what `has_blueberry(s.below)` says, by its Docstring, so the
  template's recursive call, renamed, is the answer. All the tests pass:

```python
def has_blueberry(s: Stack) -> bool:
    """whether any pancake in the stack s is blueberry"""
    match s:
        case Plate():
            return False
        case Pancake():
            if s.flavor == "blueberry":
                return True
            else:
                return has_blueberry(s.below)
```

- Read `has_blueberry(s.below)` by its Docstring: whether any pancake in the
  stack below is blueberry. Then the `else` says: the top isn't blueberry, so
  the stack has one exactly when the stack below does. That's all it takes to
  see that the body is right; there's no need to follow the calls one inside
  another.
- The function does something with the part that isn't self-referential
  (checks `s.flavor`), and combines it with the result of the same function on
  the part that is (`s.below`).

### Another Function on Stacks

The design recipe, for counting the blueberry pancakes in a stack. The data
definition's examples extend each other, and so do the tests' inputs:

```python
ONE_BLUE = Pancake("plain", Pancake("blueberry", Plate()))
TWO_BLUE = Pancake("blueberry", ONE_BLUE)

def blueberries(s: Stack) -> int:
    """how many of the pancakes in the stack s are blueberry"""
    match s:
        case Plate():
            return 0
        case Pancake():
            if s.flavor == "blueberry":
                return blueberries(s.below) + 1
            else:
                return blueberries(s.below)

def test_blueberries_of_an_empty_stack():
    assert blueberries(Plate()) == 0

def test_blueberries_of_a_plain_pancake():
    assert blueberries(Pancake("plain", Plate())) == 0

def test_blueberries_of_one_blueberry_pancake():
    assert blueberries(Pancake("blueberry", Plate())) == 1

def test_blueberries_of_one_blue():
    assert blueberries(ONE_BLUE) == 1

def test_blueberries_of_two_blue():
    assert blueberries(TWO_BLUE) == 2
```

- Line `blueberries` up against `_stack_temp`: what did each `...` become?
- `TWO_BLUE` is `ONE_BLUE` with a blueberry pancake on top, and its answer is
  one more: that difference is the `+ 1` in the body.
- Which test would fail if `return blueberries(s.below) + 1` were `return 1`?

### Lists Are Self-Referential Too

Python's lists have the same shape as stacks. A list is either:

- **empty**, `[]`, like the `Plate()`; or
- **non-empty**: a **first** element, on top of the **rest**, which is itself a
  list, like a `Pancake` on the stack `below` it.

A cart's orders, as numbers of boxes, `[2, 4, 1]`, have first `2` and rest
`[4, 1]`; that has first `4` and rest `[1]`; that has first `1` and rest `[]`.
Built that way, one element at a time, on top of the rest:

```python
def test_building_lists():
    assert [2, 4, 1] == [2] + ([4] + ([1] + []))
```

A list has no fields to read with the `.`, so `match` takes it apart instead,
naming its first element and the rest:

```python skip
match lst:
    case []:
        ...
    case [f, *r]:
        ...  # can use f and r here
```

- If the list is empty, Python runs the code under `case []:`. Otherwise, it
  adds `f` (the first element) and `r` (the rest) to the program directory, and
  runs the code under `case [f, *r]:`.
- The `*` makes `r` the list of _all_ the remaining elements, not a single one.

So a list's template is the stack's, with `[]` for the plate, and `f` and `r` in
place of a pancake's `s.flavor` and `s.below`:

```python
def _list_temp(lst: list) -> ...:
    match lst:
        case []:
            return ...
        case [f, *r]:
            ...
            f
            ...
            _list_temp(r)
            ...
            return ...
```

Two functions on orders, from it. Any names will do in a `case`, and names that
fit the problem help: for orders, `boxes` (the first order's) and `others`:

```python
def count_orders(orders: list[int]) -> int:
    """the number of orders in orders"""
    match orders:
        case []:
            return 0
        case [boxes, *others]:
            return 1 + count_orders(others)

def total_boxes(orders: list[int]) -> int:
    """the total number of boxes in orders"""
    match orders:
        case []:
            return 0
        case [boxes, *others]:
            return boxes + total_boxes(others)

def test_count_orders_of_no_orders():
    assert count_orders([]) == 0

def test_count_orders_of_one_order():
    assert count_orders([1]) == 1

def test_count_orders_of_two_orders():
    assert count_orders([4, 1]) == 2

def test_count_orders_of_three_orders():
    assert count_orders([2, 4, 1]) == 3

def test_total_boxes_of_no_orders():
    assert total_boxes([]) == 0

def test_total_boxes_of_one_order():
    assert total_boxes([1]) == 1

def test_total_boxes_of_two_orders():
    assert total_boxes([4, 1]) == 5

def test_total_boxes_of_three_orders():
    assert total_boxes([2, 4, 1]) == 7
```

- `count_orders(others)` is trusted to do what its Docstring says, the number of
  orders in `others`, so the body reads "1, plus the number of the other
  orders".
- The two are nearly the same: the structure of the data gives the structure of
  the program. Next class: the whole design recipe on lists, for harder
  functions.
