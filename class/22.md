## Notes (review before class)
### Lists as Recursive Data

`match` tells apart variants of conditional data ([Class 20](/class/20)), and
empty and non-empty lists ([Class 21](/class/21)): lists are conditional data,
built into Python. Our own version: a `NumList` (list of numbers) is either an
`NlEmpty` or an `NlLink`. (Try, before reading on: what fields should `NlLink`
have, and of what types?)

```python
@dataclass
class NlEmpty:
    pass

@dataclass
class NlLink:
    first: float
    rest: "NumList"

NumList = NlEmpty | NlLink
```

- `NlLink` has the two parts of a non-empty list: `first`, a `float`, and `rest`,
  a list of numbers, so a `NumList`.
- `NumList` isn't defined until after the two classes, so inside them its name
  is written in quotes.
- `rest` has the very type being defined: a data definition with a field of its
  own type is **recursive data**.
- This works because building a `NumList` starts from `NlEmpty()`, which doesn't
  refer to `NumList`; `NlLink` adds numbers to the front. Building 2, 7, 3 (each
  `rest` a valid `NumList`):

```python
NlEmpty()
NlLink(3, NlEmpty())
NlLink(7, NlLink(3, NlEmpty()))
NlLink(2, NlLink(7, NlLink(3, NlEmpty())))
```

- Recursive data is **arbitrarily sized**: `NlLink` makes any `NumList` larger,
  so functions must handle any length, like
  `NlLink(1, NlLink(2, ... NlLink(8, NlEmpty()) ...))`.

### A Function over Recursive Data

`contains_3` returns whether a `NumList` contains `3`:

```python
def contains_3(nl: NumList) -> bool:
    """returns True if nl contains 3, False otherwise"""
    ...

def test_contains_3():
    assert not contains_3(NlEmpty())
    assert contains_3(NlLink(3, NlEmpty()))
    assert contains_3(NlLink(1, NlLink(3, NlEmpty())))
    assert contains_3(NlLink(1, NlLink(2, NlLink(3, NlLink(4, NlEmpty())))))
    assert not contains_3(NlLink(1, NlLink(2, NlLink(5, NlLink(4, NlEmpty())))))
```

Start with an outline of any function on a `NumList`, named for the data, as
templates have been since [Class 4](/class/4): a `match` on the variants, with a
line for each of a variant's fields where its answer goes:

```python
def _num_list_temp(nl: NumList) -> ...:
    match nl:
        case NlEmpty():
            return ...
        case NlLink(first, rest):
            ...
            first
            ...
            rest
            ...
            return ...
```

- `NlEmpty()`: the answer is `False`.
- `NlLink(first, rest)`: if `first` is `3`, the answer is `True`; otherwise, it is
  whether `rest` contains `3`.
- `rest` is a `NumList`, so we could `match` on it, then on _its_ rest, ...; but
  any number of copies fails on a list one element longer.
- Instead, call the function whose job is exactly that: `contains_3(rest)`. All
  the tests pass:

```python
def contains_3(nl: NumList) -> bool:
    """returns True if nl contains 3, False otherwise"""
    match nl:
        case NlEmpty():
            return False
        case NlLink(first, rest):
            if first == 3:
                return True
            else:
                return contains_3(rest)
```

Stepping through `contains_3(NlLink(1, NlLink(3, NlEmpty())))`:

1. Substitute the argument for `nl`. The `NlLink` case matches: `first` is `1`,
   `rest` is `NlLink(3, NlEmpty())`.
2. `1 == 3` is `False`, so it runs `contains_3(NlLink(3, NlEmpty()))`: an
   ordinary call, on the `rest`, which could be a test on its own.
3. There, `first` is `3`, so it returns `True`, and so does the original call.

The function does something with the non-recursive part (checks `first`), and
combines it with the result of the same function on the recursive part (`rest`).

### A Template for Recursive Data

On [Class 21](/class/21), substitution across examples gave a function that calls
itself on the rest. The same structure comes from _the shape of the data_: break
it into variants (`match`), pull out each variant's fields, and call the function
on any recursive fields (fields of the same type). For `NumList`, the outline
above, with the recursive call in place of `rest`:

```python
def _num_list_temp(nl: NumList) -> ...:
    match nl:
        case NlEmpty():
            return ...
        case NlLink(first, rest):
            ...
            first
            ...
            _num_list_temp(rest)
            ...
            return ...
```

- A **template**, like every template since [Class 4](/class/4): the outline
  of _any_ function on a `NumList` (hence its name, which is the data's). Every
  data definition has one.
- To write a specific function, copy the template's body into it, rename the
  recursive call, and fill in the `...`s: what does the recursive call return,
  and how do you combine it with the non-recursive parts?
- Examples (Class 21) and the template lead to the same function, but the
  template scales to complicated data definitions (there will be _many_), where
  writing examples out by hand is tedious.

**Strategy: Writing a Template for Recursive Data.** Given a recursive data
definition:

1. Write its Signature: the data's name, with `_` in front and `_temp` at the
   end, taking the data, with `...` as its result type.
2. Use `match` to break the recursive-data input into its variants.
3. In each case, put each of its fields on a line of its own, with `...` before
   and after each, and `return ...` at the end.
4. Call the template itself on any recursive fields, in place of their lines.

### Every Template So Far

The rule behind this template is the one behind each template since
[Class 5](/class/5): **one part of the body for each part of the data**.
Recursive data is that rule once more, plus a recursive call on each field of
the type being defined:

| Data | The template | From |
| --- | --- | --- |
| a number split into intervals | an `if` branch per interval | [Class 5](/class/5) |
| a row | a line for each column: `r["col"]` | [Class 8](/class/8) |
| a table, made into a new one | fewer rows (`filter`), a new column (`add_column`), or a changed column (`transform_column`) | [Class 9](/class/9) |
| a fixed set of strings | an `if` branch per value, and an `else` | [Class 11](/class/11) |
| a list, with built-ins | fewer elements (`filter`), each one changed (`map`), or one value (`sum`) | [Class 14](/class/14) |
| a list, with a loop | a `for`, combining, building, or checking | [Class 15](/class/15) |
| a dataclass | a line for each field: `s.field` | [Class 19](/class/19) |
| a union | a `case` per variant, naming its fields | [Class 20](/class/20) |
| recursive data | a `case` per variant, naming its fields, and a recursive call on each field of its own type | today |

Each is on the [Design Recipe](/class/recipe#templates) page.

### The Design Recipe

The steps are the same as since [Class 4](/class/4), for recursive data too:

<DesignRecipe focus="Data definition, Template" />

- **Data definition**: recursive, with examples that extend each other (as
  `two_7s` extends `one_7`, in the Recap).
- **Signature**: the name is needed for the recursive calls, and the types guide
  the body.
- **Docstring**: what the function gives for any list, not only the examples.
- **Examples**: tests with _concrete_ data, at least one per variant, including
  inputs that extend other inputs. Where one input extends another, the difference in
  outputs becomes the body, as in [Class 21](/class/21).
- **Template**: from the data definition, with the strategy above.
- **Body**: fill in the template, using your examples.
- **Test and revise**: run the examples, to check the function behaves as you
  expect. They were about input-output behavior; now add tests that focus on
  the implementation's details.

## Recap (15 mins)

The design recipe, applied to counting the `7`s in a `NumList`: the data
definition and examples, the template, and the function written from it, with
its tests:

```python
@dataclass
class NlEmpty:
    pass

@dataclass
class NlLink:
    first: float
    rest: "NumList"

NumList = NlEmpty | NlLink

one_7 = NlLink(0, NlLink(7, NlEmpty()))
two_7s = NlLink(7, one_7)

def _num_list_temp(nl: NumList) -> ...:
    match nl:
        case NlEmpty():
            return ...
        case NlLink(first, rest):
            ...
            first
            ...
            _num_list_temp(rest)
            ...
            return ...

def num_7s(nl: NumList) -> int:
    """counts how many times 7 appears in nl"""
    match nl:
        case NlEmpty():
            return 0
        case NlLink(first, rest):
            if first == 7:
                return num_7s(rest) + 1
            else:
                return num_7s(rest)

def test_num_7s():
    assert num_7s(NlEmpty()) == 0
    assert num_7s(NlLink(0, NlEmpty())) == 0
    assert num_7s(NlLink(7, NlEmpty())) == 1
    assert num_7s(one_7) == 1
    assert num_7s(two_7s) == 2
```

- Line `num_7s` up against the template: what did each `...` become?
- What is the first recursive call that `num_7s(two_7s)` makes, and what does it
  return?
- Which test would fail if `return num_7s(rest) + 1` were `return 1`?
- `one_7` and `two_7s` come from which step of the recipe? Which examples use
  them, and why is it useful that one extends the other?

## Wrap-up (5 mins)

- Data has structure, which can be used to guide how we implement functions.
- We can write function templates based on that structure, which is a helpful
  starting point.
- Template of the day: [recursive data](/class/recipe#template-recursive): a
  `case` per variant, naming its fields, and a recursive call on each field of
  its own type.
