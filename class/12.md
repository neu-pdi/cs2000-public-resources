## Notes (review before class)
### Task Plans

- A **task plan** breaks a problem into steps (sub-tasks) you know how to
  carry out, with a built-in function or one of your own: a to-do list for the
  program, as bullets, as a diagram of the data's transformations, or both.
- We made one for the promo-code chart in [Class 11](/class/11): we started
  from the chart we wanted, found a function that draws it, and then made the
  data fit that function.

**Strategy: Creating a Task Plan**

1. Make up a small example input, and work out the output you want for it by
   hand: big enough to show what matters, small enough to do on paper (4 to 6
   rows of a table).
2. List the functions (ones you know, or from the documentation) that might
   help get from the input to the output. For a step from a table to a table,
   ask which shape of the [table template](/class/recipe#template-tables) it is:
   fewer rows, a new column, or a changed column.
3. Put them in order, drawing the example's data after each step, with the
   operation on the arrow between.
4. Repeat step 3 for any step you can't yet write as code.

The promo-code chart's plan, on paper:

```
 Name     Boxes   Promo Code
 "Ines"   2       "BAKE10"
 "Dev"    5       "bake10"
 "Mo"     3       " "
 "Ruth"   4       "Friend"
               |
               |  using transform_column
               v
 Name     Boxes   Promo Code
 "Ines"   2       "BAKE10"
 "Dev"    5       "BAKE10"
 "Mo"     3       "none"
 "Ruth"   4       "FRIEND"
               |
               |  using freq_bar_chart
               v
 bars: BAKE10 2, none 1, FRIEND 1
```

- Each arrow is one template: "using `transform_column`" is the changed-column
  shape of the table template ([Class 9](/class/9)), and `freq_bar_chart`
  summarizes a column.
- Each helper an arrow needs (here, `cell_to_promo_code`) goes on a **wish
  list**: write its Signature, with `...`, and its Docstring as soon as the plan
  needs it, so the plan's code runs; then design each one with the rest of the
  recipe.
- To turn a plan into code, write each step, passing its output to the next.
- A plan can also work on the same table in two ways, then combine the
  results. How many more boxes does a delivery order have than a pickup order,
  on average?

```
 Name     Boxes   Delivery
 "Ines"   2       "pickup"
 "Dev"    5       "delivery"
 "Mo"     3       "pickup"
 "Ruth"   4       "delivery"
      |                          |
      |  filter: delivery        |  filter: pickup
      v                          v
 "Dev" 5, "Ruth" 4          "Ines" 2, "Mo" 3
      |                          |
      |  mean of Boxes           |  mean of Boxes
      v                          v
     4.5                        2.5
        \                       /
         '---->  4.5 - 2.5  <---'
```

- Try: plan how to find which item (cookies, brownies, or lemon bars) sold the
  most boxes.
- **When you aren't sure how to start, don't start with code: plan until you
  understand the problem.** Starting with code only feels faster.

### Mixed Types

A column in a `table(...)` may mix types. In this weather log, the second day's
temperature was typed as a string:

```python
weather_data = table(
    ["date", "temperature", "precipitation"],
    [
        ["2025-01-01", 62, 0.1],
        ["2025-01-02", "45", 3],
        ["2025-01-03", 28, 0.2],
        ["2025-01-04", 55, -1],
        ["2025-01-05", 90, 0],
    ],
)
```

A function normalizing the column must accept both types:

- `isinstance(v, str)` is `True` if `v` is a string.
- The annotation `float | str` means "a `float` or a `str`" (`|` means "or").
- Convert the strings with a helper like `string_to_int` ([Class 11](/class/11)),
  here with `float`, for decimals. The data definition has one case per type,
  so the template has one branch per type, and the examples check each:

```python
def string_to_number(s: str, default: float) -> float:
    """converts s to a number, or produces default if s does not represent a number"""
    try:
        return float(s)
    except ValueError:
        return default

def normalize_temp(v: float | str) -> float:
    """given a number or a string that represents a number, converts to a number"""
    if isinstance(v, str):
        return string_to_number(v, 0)
    else:
        return v

def test_normalize_temp():
    assert normalize_temp(10) == 10
    assert normalize_temp("13") == 13

fixed_weather = weather_data.transform_column("temperature", normalize_temp)
```

- Try: if the second day's temperature were `"forty-five"`, what would
  `normalize_temp` give? Is that right? (`precipitation` has a problem too: a
  negative amount of rain.)

### Binning

Clean data may still need preparing: charting small, medium, and large orders
needs a size label for each order.

- **Binning** reduces values (like numbers of boxes) to a few categories, the
  **bins** (small/medium/large; morning/afternoon/evening; cold/mild/hot).
- Write a function that computes a value's bin, with the recipe:

<DesignRecipe focus="Template" />

- **Data definition**: a number of boxes, in three bins: small (1 or 2),
  medium (3 to 5), and large (6 or more).
- **Template**: the interval template from [Class 5](/class/5): one branch per
  bin, with the conditions from the edges
  ([templates for intervals](/class/recipe#template-intervals)):

```python
def _boxes_temp(boxes: int) -> ...:
    if boxes >= 6:
        ...
        boxes
        ...
        return ...
    elif boxes >= 3:
        ...
        boxes
        ...
        return ...
    else:
        ...
        boxes
        ...
        return ...
```

- **Signature** and **Docstring**: from an `int` to a `str`, as below.
- **Examples**: a test in each bin, and at each edge: 2 (small), 3 and 5 (the
  edges of medium), and 6 (the edge of large):

```python
def test_order_size_label():
    assert order_size_label(2) == "small"
    assert order_size_label(3) == "medium"
    assert order_size_label(5) == "medium"
    assert order_size_label(6) == "large"
```

- **Body**: copy the template's body into `order_size_label`. Each branch gives
  its bin's label, which doesn't need `boxes` itself:

```python
def order_size_label(boxes: int) -> str:
    """categorizes a number of boxes as a small, medium, or large order"""
    if boxes >= 6:
        return "large"
    elif boxes >= 3:
        return "medium"
    else:
        return "small"
```

- Then add a column of bins with it (`order_size_data`, below). It takes a
  number, not a row, so it's easy to test; a `lambda` passes it each row's value.

### Splitting Columns

- `s.split(sep)` splits `s` around `sep` into a **list** of the pieces (lists:
  [Class 13](/class/13)): `"Priya Raman".split(" ")` is `["Priya", "Raman"]`.
- Get a piece by its position, from 0, in square brackets:
  `"Priya Raman".split(" ")[1]` is `"Raman"`. `len` works on lists, too.
- To sort the orders by family name, we might replace `Name` with `given-name`
  and `family-name` columns (`add_column`, then `select_columns` to drop
  `Name`). But look at the bake sale's names: `"Kiran"` is one name, `"Ana Paula
  Lima"` has two given names, and `"Tomás García López"` has two family names.
  Some people write their family name first, and many names aren't written in
  the Latin alphabet at all.
- How people's names work depends on culture and context. A program may
  reasonably serve only some people, but finding out later that it can't
  represent people it needs to is costly. So before choosing a table's columns,
  ask what they assume about the people (or things) they describe, and who
  those assumptions leave out. (For many more examples, search "falsehoods
  programmers believe about names".)

### Managing and Naming Tables

- Keep the original file and the corrected copy (to see what people typed, or
  to try other fixes), and keep cleaned data separate from loaded data (table
  operations make new tables).
- Name the loaded table, the cleaned table, and the important variations, not
  every intermediate table. Naming them the same way in every project saves
  confusion:

```python
bake_raw = load_table("bake-sale.csv")

cleaned_bake_data = (
    bake_raw.transform_column("Boxes", int)
    .transform_column("Promo Code", cell_to_promo_code)
)

order_size_data = cleaned_bake_data.add_column("order-size", lambda r: order_size_label(r["Boxes"]))
```

- `transform_column` produces a table, so we can call it on its own result; the
  parentheses let each step have its own line. (`cell_to_promo_code`:
  [Class 11](/class/11).)
- For a huge dataset, save the cleaned table to a file (**Save CSV**, on a table
  in the interactions panel), and load only that.

### Visualizations and Plots

The right plot depends on the question, and on the kinds of variables
(columns):

- **Quantitative**: numbers that it makes sense to compute with, with equal
  steps between values (amounts, counts, measurements).
- **Categorical**: one of a set of values, which can be counted but not
  computed with (perhaps ordered, like "small", "medium", "large").
- Names, numbers of boxes, zip codes, order sizes: which kind is each?

Plots (table methods; see [Tables](/pll/tables)):

- `scatter_plot`: relates two quantitative variables.
- `freq_bar_chart`: how often each categorical value appears.
- `histogram`: how quantitative values fall into equal-size intervals.
- `pie_chart`: each categorical value's share of a total.

Try: which chart shows the most used promo code? Whether bigger orders tend to
be delivered? Orders per delivery option? For the last:

```python
cleaned_bake_data.freq_bar_chart("Delivery")
```

- Bars: `pickup` (5), `delivery` (3), `Delivery` (1), and `delivry` (1): the
  chain above didn't normalize `Delivery`. Add `normalize_delivery`
  ([Class 11](/class/11)'s Try) to it.
- So plots also check data: **don't trust a dataset until you've checked that
  its values make sense.** When a dataset is too big to read, plots and
  summaries are how you find its errors.

### Summary: Managing a Data Analysis

1. Before looking: what values should each column hold, and how could they go
   wrong, given how the data were collected?
2. Look for problems (read, chart, `filter`), and fix them: mistakes at the
   source, if you control it, and interpretations in code.
3. Keep the raw data, and name the cleaned table (or save it as a file).
4. Prepare the data for each question (new columns, bins), naming one table
   per question.
5. Answer each question with the statistic or plot that suits it and its
   variables, and keep track of which file and code produced each result.

The same steps come before any **machine learning**, which makes predictions
from a dataset with programs other people wrote. A model learns a dataset's
errors and gaps along with everything else, so who the data represents, and
what it was collected for, matter as much as the code (the hiring case,
[Class 6](/class/6)).
