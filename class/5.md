## Notes (review before class)
### Tests

Keep the examples a function was written from ([Class 4](/class/4)), since
**software evolves**: a function may stop matching them, on purpose or by
mistake.

```python
def c_to_f(celsius: float) -> float:
    """the temperature celsius (in degrees Celsius), in degrees Fahrenheit"""
    return celsius * 9/5 + 32

def test_c_to_f():
    assert c_to_f(0) == 0 * 9/5 + 32
    assert c_to_f(100) == 100 * 9/5 + 32
    assert c_to_f(37) == 37 * 9/5 + 32
```

- A **test function**'s name starts with `test_`; it goes right after the
  function it checks.
- Each **`assert`** checks that the expression after it is `True`; `==` checks
  that two values are equal.
- PLL runs the tests _every time you run the file_, and reports failures. A
  test function stops at its first failing `assert`.
- Try: change the body to `return celsius * 5/9 + 32` (a common mix-up) and
  run the file, to see what a failing test looks like. Then fix it, break a
  test instead, and compare.

### Writing Good Tests

These tests check `c_to_f` better:

```python
def test_c_to_f():
    assert c_to_f(0) == 32      # water freezes
    assert c_to_f(100) == 212   # water boils
    assert c_to_f(-40) == -40   # the two scales meet
    assert c_to_f(37) == 98.6   # body temperature
```

- Each answer is something known _without_ the formula. Tests that just repeat
  the body catch little: if the formula were wrong, the test would be wrong the
  same way.
- `-40` is a negative input: unusual, but valid. Look for the special inputs a
  kind of data allows (zero, negatives, an empty string). (Ignore nonsensical
  ones, like a temperature below absolute zero, for now.)
- The right of `==` just has to evaluate to the expected answer, written in
  some meaningful way: `32`, or `0 * 9/5 + 32`.
- **Never run the function to get a test's answer!** If a wrong body produces
  the answers, the tests can't catch it.
- Working **on concrete values** first checks that you understand the problem:
  if you can't write examples, you probably can't write the function.

Tests are the **Examples** step of the [design recipe](/class/recipe), and they
come _before_ the body. Today adds them, and more to the **Template** step, to
the Signature and Docstring from [Class 4](/class/4):

### Conditionals

`choose_hat` picks a hat for the weather: a sun hat when it's 80 degrees
Fahrenheit or above, and no hat otherwise. Its input is a temperature, so the
**Data definition** (in words, as in [Class 4](/class/4)) is: the weather is a
number of degrees Fahrenheit, in two intervals, below 80, and 80 or above.

The **Template** step comes next: the outline that the kind of data gives the
body of any function on it, before solving any particular problem. Its rule is
that **the body has one part for each part of the data**. The weather is a
number split into two intervals, so the template has one case per interval,
with the question taken from the edge between them
([templates for intervals](/class/recipe#template-intervals)). As in
[Class 4](/class/4), it's a function named for the kind of data, with each part
on a line of its own, `...` before and after it, and `return ...` at the end of
each case. An **`if` statement** asks a question about the input:

```python
def _weather_temp(temp_in_f: float) -> ...:
    if temp_in_f < 80:
        ...
        temp_in_f
        ...
        return ...
    else:
        ...
        temp_in_f
        ...
        return ...
```

- If the answer to the question (`temp_in_f < 80`) is true, Python runs the code
  under the `if`; if false, the code under `else` (the **else clause**).
- The `if` and `else` lines end with a colon; each case is indented under its
  line.

### Choosing Test Inputs

Now for `choose_hat` itself: its **Signature** and **Docstring**, with `...` as
the body, so the file runs:

```python
def choose_hat(temp_in_f: float) -> str:
    """the hat to wear at temp_in_f degrees Fahrenheit: a sun hat at 80 or
    above, otherwise none"""
    ...
```

Then the **Examples**, with carefully chosen inputs:

```python
def test_choose_hat():
    assert choose_hat(80) == "sun hat"
    assert choose_hat(79.5) == "no hat"
    assert choose_hat(50) == "no hat"
    assert choose_hat(95) == "sun hat"
```

- `80` is **at the boundary** between the answers; `79.5` is **just under** it.
  Boundaries are a common source of **bugs** (mistakes that make a program
  misbehave).
- **Whole and decimal numbers**, and examples for **each answer**.
- `"sun hat"` and `"no hat"` appear only in the answers: which one _depends_ on
  the input.
- Run the file now: the tests run, and fail, since the body is still `...` (PLL
  says that `choose_hat` is not written yet). That is expected at this step;
  but thinking through the examples before we write the body prevents us from
  falling into the trap of writing the wrong body and then having our tests
  match.

### Writing the Body

For the **Body**, copy the template's body into `choose_hat`, and fill in each
case using the examples (each line that only says `temp_in_f` goes, once the
case uses it, or when it doesn't need it):

```python
def choose_hat(temp_in_f: float) -> str:
    """the hat to wear at temp_in_f degrees Fahrenheit: a sun hat at 80 or
    above, otherwise none"""
    if temp_in_f < 80:
        return "no hat"
    else:
        return "sun hat"
```

- Run the file again (**Test and revise**): the tests that failed against `...`
  now pass.

<Aside title="Indentation Nests">

- _Two_ levels of indentation: `if` and `else` are in the body (indented
  once), and each case is indented again. Same rule as [Class 4](/class/4).
- `else` must line up with its `if`, or Python can't tell which `if` it goes
  with:

```python error
    if temp_in_f < 80:
        return "no hat"
        else:
            return "sun hat"
```

- When a conditional misbehaves, check each line's level before doubting the
  question.
- For now, wrong indentation usually causes an error, which tells you about
  itself. Later, once code does several things in order, a line at the wrong
  level can run happily and quietly do the wrong thing.

</Aside>

### Booleans

`79.5 < 80` is `True` and `95 < 80` is `False`: the only two values of the type
**`bool`** (for _Boolean_, after George Boole). (`temp_in_f < 80` at the prompt
is an error: `temp_in_f` only exists inside `choose_hat`.)

```python
2 + 2 == 4          # True
"Hat" == "hat"      # False
"apple" < "banana"  # True
"cap" < "car"       # True
"b" >= "Z"          # True
"Z" < "a"           # True
```

- `==` checks equality (unlike `=`, which associates a name with a value).
- Strings are **case-sensitive**.
- `<`, `>=`, etc. order strings alphabetically, letter by letter, following
  **ASCII**, an old convention: every uppercase letter comes before every
  lowercase one (letters outside ASCII are far more complicated).
- Any two values can be compared: `"5" == 5` is `False`, not an error, so
  comparing a number with a string by mistake quietly gives nonsense.
- A `bool` input has two cases, `True` and `False`, so its template is an `if`
  with an `else`: one case for each.
- Most kinds of data have operations producing booleans; `in` checks whether
  one string appears inside another:

```python
hat = "sun hat"
"sun" in hat  # True
"Sun" in hat  # False (note the capital S)
```

**`and`**, **`or`**, and **`not`** combine booleans (a picnic if it's warm _and_
dry; stay in if it's raining _or_ snowing; a walk if it's _not_ dark):

```python
(80 >= 80) and (95 < 80)  # False
(80 >= 80) or (95 < 80)   # True
not (95 < 80)             # True
```

### Asking Multiple Questions

For a third answer (a winter hat, below 50), **`elif`** ("else if") adds a
question:

```python
def choose_hat(temp_in_f: float) -> str:
    """the hat to wear at temp_in_f degrees Fahrenheit: a winter hat below 50,
    a sun hat at 80 or above, otherwise none"""
    if temp_in_f < 50:
        return "winter hat"
    elif temp_in_f < 80:
        return "no hat"
    else:
        return "sun hat"
```

- Python asks the questions in order, and runs the code for the first that is
  `True` (or `else`, if none are). Any number of `elif`s is allowed.
- "Between 50 and 80" is implicit: `temp_in_f < 80` is only asked if
  `temp_in_f < 50` was `False`. `elif (temp_in_f >= 50) and (temp_in_f < 80):`
  makes it explicit (comparisons happen before `and`, so the parentheses just
  make the order clear).
- Both versions are correct. A winter hat changes the data (three intervals
  now), so go back through the steps in order: the data definition, and a third
  case in its template; then the docstring, then examples for the new interval
  and its edge (like `assert choose_hat(49) == "winter hat"`, beside
  `choose_hat(50)`), and only then the body.
- A redundant condition like `temp_in_f >= 50` shows readers which case it
  covers, and keeps a mistake in an earlier question (now, or after a later
  change) from _silently_ giving surprising output.

Try: write `free_entry`, which takes a visitor's age and whether they are a
student, and decides whether a museum lets them in for free: `True` for anyone
under 12, anyone 65 or older, and any student. Write it once with `if`, once
with only boolean operations.

**Who a rule leaves out.** `free_entry` decides with two facts about a person.
Real systems deciding who sees a job ad, gets a loan, or is flagged for a
closer look do the same with more data, and the choice of data matters: this
rule charges a 40-year-old who can't afford a ticket, and lets in a wealthy
student for free. Ask _what data should represent people_, and _who a rule
treats unfairly_: decisions based on it can be inaccurate, and harmful.

### Evaluating by Reducing Expressions

Substitution ([Class 4](/class/4)) works with `if` too, step by step, as in
algebra. A garage charges nothing for the first hour, then \$3 an hour, but
never more than \$20:

```python
def parking_fee(hours: float) -> float:
    """the fee for parking hours: the first hour free, then $3 an hour, up to $20"""
    if hours <= 1:
        return 0
    elif (hours - 1) * 3 <= 20:
        return (hours - 1) * 3
    else:
        return 20
```

```
    parking_fee(5)
=>  if 5 <= 1:
        return 0
    elif (5 - 1) * 3 <= 20:
        return (5 - 1) * 3
    else:
        return 20
=>  if False:
        return 0
    elif (5 - 1) * 3 <= 20:
        return (5 - 1) * 3
    else:
        return 20
=>  if (5 - 1) * 3 <= 20:
        return (5 - 1) * 3
    else:
        return 20
=>  if 12 <= 20:
        return (5 - 1) * 3
    else:
        return 20
=>  if True:
        return (5 - 1) * 3
    else:
        return 20
=>  return (5 - 1) * 3
=>  return 12
```

- `5` replaces `hours`; a `False` question's case is dropped and the next
  question tried; a `True` one's case is all that's left.
- This is the best way to think about how Python evaluates, and to work
  through a program by hand or in your head.

### Composing Functions

A forecast in Celsius needs a hat too: send `c_to_f`'s output into
`choose_hat`. We **compose** the functions, directly, or by naming the
intermediate result:

```python
choose_hat(c_to_f(28))
```

```python
temp = c_to_f(28)
choose_hat(temp)
```

- Both give `"sun hat"`: a function's inputs are evaluated before the call, so
  `82.4` is substituted for `temp_in_f` either way.
- The second also stores `82.4` in the directory as `temp`: more steps, but
  some find it easier to read.
- A function's body can compose functions too: a function that needs another's
  result calls it (a **helper**), rather than repeating its code.

#### Local Names and the Directory

A name defined in a body can make it more readable:

```python
def choose_hat_c(temp_in_c: float) -> str:
    """the hat to wear at temp_in_c degrees Celsius"""
    fahrenheit = c_to_f(temp_in_c)
    return choose_hat(fahrenheit)
```

`hat = choose_hat_c(28)` now makes two directory entries, `fahrenheit` (inside
the body of `choose_hat_c`) and `hat`, but using `fahrenheit` afterwards is a
`NameError`:

```python error
hat = choose_hat_c(28)
very_hot = fahrenheit > 90
```

- Entries made inside a function are **local** (private) to its body: each
  call gets a local directory that other code can't see (a library function's
  body may not even be visible).
- A body can use its local names (`fahrenheit`) and the **global** directory
  (`c_to_f`, `choose_hat`), but never another call's local names: `choose_hat`
  can't see `fahrenheit`, only its own `temp_in_f`.
- When a call finishes, its local directory disappears.

### Debugging with print

**Debugging** is finding and removing bugs. **`print`** shows values while code
runs: any number of them, separated by commas, shown with spaces between (so a
label can go before a value):

```python
print("fahrenheit:", c_to_f(28), "hat:", choose_hat_c(28))
```

- This shows `fahrenheit: 82.4 hat: sun hat`.
- A `print` in a body shows values each time the function runs; what's printed
  during a test is shown with that test's results.
- To see a question's answer, either name it (`warm = temp_in_f < 80`, a local
  name) and print `warm`, or print the expression itself
  (`print("warm:", temp_in_f < 80)`), adding no name.
