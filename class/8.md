### Functions over Rows

Now that we can isolate rows, we can write functions that ask questions about
them. In the [Class 7](/class/7) reading, we checked whether the `shuttle` row for
March had at least 1000 riders; to do that for any row, let's write
`cleared_1k`. Rows are `dict`s, so that is the type of its input, and its body
compares the `"riders"` cell to 1000:

```python
def cleared_1k(r: dict) -> bool:
    """determine whether given row has at least 1000 riders"""
    return r["riders"] >= 1000

def test_cleared_1k():
    assert cleared_1k(shuttle.row(2))
    assert not cleared_1k(shuttle.row(3))
```

Both tests share the `shuttle.row(...)` part. Would it have been better to have
`cleared_1k` take just the row position, as in `cleared_1k(2)`? What are the
benefits and limitations? Taking a row is more flexible: it works with a row
from _any_ table with a `"riders"` column (one with more columns, or for a
different year), while taking a position would fix which table it works with.

Try writing `is_winter`, which takes a row with a `"month"` column and returns
whether its month is `"Jan"`, `"Feb"`, or `"Mar"`; and `low_winter`, which takes
a row with `"month"` and `"riders"` columns and returns whether it is a winter
row with fewer than 1050 riders. Then take one of your tests, and show how the
program directory evolves as you evaluate it.

### Finding Rows

Extracting rows by position isn't always convenient: a table might have
thousands of rows, and we might not know where the ones we want are. To find a
row with fewer than 1000 riders, with what we've seen so far, we might try:

```python
if shuttle.row(0)["riders"] < 1000:
    shuttle.row(0)
elif shuttle.row(1)["riders"] < 1000:
    shuttle.row(1)
elif shuttle.row(2)["riders"] < 1000:
    shuttle.row(2)
elif shuttle.row(3)["riders"] < 1000:
    shuttle.row(3)
else:
    ...  # not clear what to do here
```

What limitations do you see? With thousands of rows, this would be painful to
write; only the row positions change; it isn't clear what to do if no rows
match; and if several match, we might want _all_ of them.

It is, however, the _spirit_ of what we want: go through the rows one at a
time, identifying those that match some criterion. We just don't want to check
each row by hand, and we don't have to: a table can do that, if we say what the
criterion is. As before, we write it as a function that takes a row and returns
a boolean (since it was the question in our `if`):

```python
def below_1k(r: dict) -> bool:
    """determine whether row has fewer than 1000 riders"""
    return r["riders"] < 1000

def test_below_1k():
    assert not below_1k(shuttle.row(2))
    assert below_1k(shuttle.row(3))
```

The table method `filter` is given the criterion, and, roughly like our `if`,
calls it on each row, one at a time:

```python
shuttle.filter(below_1k)
```

If you run this, you'll see that `filter` produces a _table_ of the matching
rows, not a row by itself. This is handy when several rows match:
`shuttle.filter(is_winter)`, with your `is_winter`, gives a table of the three
winter rows, which we can name as usual:

```python

```

### Ordering Rows

A new question: _which winter month had the fewest riders?_ Can we answer it
with `filter`? Why or why not?

`filter` checks each row independently of the others, but this question
requires _comparing across rows_. Tools for analyzing data let us _sort_ a
table's rows by one column, which helps here: we can sort the winter rows from
fewest to most riders, then look at the first row. First, let's sort:

```python
winter.order_by("riders", ascending=True)
```

`order_by` takes the column to sort on, and whether to sort in increasing order
(`ascending=False` sorts from largest to smallest). It creates a new sorted
table (`Feb`, then `Mar`, then `Jan`), without modifying `winter`.

Now, try writing the code to extract the name of the winter month with the
fewest riders. Here are two ways:

```python
winter.order_by("riders", ascending=True).row(0)["month"]
```

```python
sorted_winter = winter.order_by("riders", ascending=True)
least_row = sorted_winter.row(0)
least_row["month"]
```

Which do you prefer, and why? How does each affect the program directory?

This combined several operations: finding rows (`filter`), ordering them
(`order_by`), extracting a row (`row`), and then a cell (square brackets). This
is typical of how we'll work with tables: combining operations to compute a
result, much as we did with images.

## Recap (15 mins)

- Consider we have the following table:
  ```python
  orders = table(
      ["time", "amount"],
      [
          ["08:00", 10.50],
          ["09:30", 5.75],
          ["10:15", 8.00],
          ["11:00", 3.95],
          ["14:00", 4.95],
          ["16:45", 7.95],
      ],
  )
  ```
- Let's say we want to find orders that are "high-value" (e.g., amount >= 8).
- To do this, we want to create a _new_ table with rows that satisfy this. With
  a small table, we could do this manually, i.e.,:
  ```python
  high_value_orders = table(
      ["time", "amount"],
      [
          ["08:00", 10.50],
          ["10:15", 8.00],
      ],
  )
  ```
  But if we have hundreds or thousands of orders, this is impractical.
- Better is to design a function that checks if an order is high-value, and then
  use a table operation, `filter`, to create a new table that contains only
  rows that satisfy the function. Rows are values of type `dict` (we'll learn
  more about these later in the semester), so that is the type annotation we use for them:
  ```python
  def is_high_value(r: dict) -> bool:
      """returns whether the amount column is >= 8"""
      return r["amount"] >= 8.0

  def test_is_high_value():
      assert is_high_value(orders.row(2))
      assert not is_high_value(orders.row(3))
  ```
  Note that since `is_high_value` returns a boolean, we can `assert` its result
  directly, or `assert not` to check that it is `False`.
- Now we can use `is_high_value` with a table operation, `filter` to construct a new table:
  ```python
  new_high_orders = orders.filter(is_high_value)
  ```
  Note that we write `is_high_value`, without parentheses after it: we are not calling
  the function, we are giving it to `filter`, which will call it on each row.
  This constructs the same table as we did by hand:
  ```python
  def test_new_high_orders():
      assert new_high_orders == high_value_orders
  ```
  But this approach will work on tables that have hundreds, thousands, or even millions of rows.
- Another built in operation on tables is `order_by`. This takes a column name,
  and whether the rows should be ordered in ascending (`ascending=True`) or descending (`ascending=False`)
  order by the given column. We can use this to sort by amount:
  ```python
  orders.order_by("amount", ascending=True)
  ```
