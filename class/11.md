### Messy Data

- Data collected by someone else often has missing or incorrect entries:
  **clean** it before analysis, so the analysis is reliable.
- Example: a student club took preorders for its bake sale with an online form,
  which saved what people typed as a CSV file:

### Loading Data

Open https://raw.githubusercontent.com/neu-pdi/cs2000-public-resources/refs/heads/python/static/support/bake-sale-orig.csv in a new tab, and copy its contents into a new file,
`bake-sale-orig.csv`, in your `cs2000-scratch` repository. `load_table`
([Class 7](/class/7)) takes a web address, or, as here, the name of a file in
the same folder as your program:

```python
bake_orig = load_table("bake-sale-orig.csv")
```

- Column names come from the file's first line.
- **Every cell is loaded as a string**, even `"2"`, so `load_table` sees no
  problem with `"three"`. It shows up once we use the column as numbers.

### Fixing the Source, or Fixing in Code

- Well-formed data doesn't mix types in a column. `three` is a person's slip,
  and a program that dropped every value of the wrong type would lose orders
  that were only typed oddly. So fix it where it is, before loading.
- Fix **mistakes** (`three`, typos) in the source, rather than complicating the
  analysis. Make **interpretations** ("a blank code means no code") in code,
  where they are visible, since a later analysis may need the distinction.
- Many errors of the same kind (say, dates written several ways)? A function
  fixes them more reliably than editing by hand, which is slow and adds its own
  mistakes.
- Clean a _copy_, and keep the original: you may want to see what people
  actually typed, and the form may send more orders. Copy `bake-sale-orig.csv`
  to `bake-sale.csv`, and in the copy, replace `three` with `3`.

### Missing Entries

`table(...)` needs a value for every cell, but spreadsheet cells can be empty:

```python
bake_raw = load_table("bake-sale.csv")

bake_raw.row(1)["Promo Code"]  # -> ''
bake_raw.row(5)["Promo Code"]  # -> ' '
```

- An empty cell (Marcus's) holds the empty string, `""`.
- A cell that _looks_ empty may not be: Sam's holds a space, since Python keeps
  a cell's actual content.
- And how is Kiran's `"none"` different from Marcus's `""`?

### Converting Columns

Convert columns after loading, with `transform_column`. `int` (or `float`)
converts a string of digits to a number, with an error (a `ValueError`) if it
can't:

```python
bake_data = bake_raw.transform_column("Boxes", int)
```

- Rule of thumb: on loading, convert numeric columns with `transform_column`,
  so missing or malformed data is handled explicitly, not silently. (On
  `bake_orig`, this stops at Lina's `"three"`, saying so.)
- Leave string columns (names, emails, codes, zip codes) unconverted. Zip codes
  use digits, but aren't numbers (what is a zip code times 3?), and their
  leading 0 matters: `int("02115")` is `2115`. They are identifiers (more on
  [Class 12](/class/12)).

### Default Values

- No default for a missing number suits every use. `0` boxes might do for an
  order the club cancelled, but `0` is no one's age, and a missing exam score
  of `0` would quietly pull down a course grade. So `int` reports an error.
- When a default _is_ appropriate, a helper can choose it with `try` / `except`,
  like `earnings_to_number` ([Class 9](/class/9)); with `float`, it would
  convert decimals:

```python
def string_to_int(s: str, default: int) -> int:
    """converts s to a whole number, or produces default if s does not represent one"""
    try:
        return int(s)
    except ValueError:
        return default

def test_string_to_int():
    assert string_to_int("3", 0) == 3
    assert string_to_int("three", 0) == 0
    assert string_to_int("", 0) == 0
```

- With `transform_column`, supply the default with a `lambda`:
  `lambda s: string_to_int(s, 0)`.

### Normalizing Data

- **Normalization**: making a collection of data (such as a column) share
  structure and formatting.
- Question: how many orders used each promo code? `freq_bar_chart`
  ([Class 10](/class/10)) draws a bar for each value in a column, as tall as its
  number of rows.
- **Examples** first, for the whole analysis: what chart do we _want_? That
  means choosing how to standardize codes and handle missing values. We choose
  `BAKE10` (3), `FRIEND` (2), and `none` (5), so every cell must hold one of
  those: put `"none"` in blank cells, and upper-case the rest.

That needs a helper for `transform_column`, from a cell to its new value. Its
new step is the template for a string with a few known values:

- **Data definition**: a promo code cell is a string: a code (in any
  capitalization), `"none"`, or blank (`""`).
- **Template**: a string that is one of a fixed set of values has one branch per
  value, and an `else` for anything else, which here is the codes
  ([templates for a fixed set of strings](/class/recipe#template-strings)):

```python
def _promo_code_temp(s: str) -> ...:
    if s == "":
        return ...
    elif s == "none":
        return ...
    else:
        ...
        s
        ...
        return ...
```

- **Signature** and **Docstring**: from `str` to `str`, with the docstring below.
- **Examples**: a test for each kind of value in the data definition, and for
  two capitalizations of a code:

```python
def test_cell_to_promo_code():
    assert cell_to_promo_code("") == "none"
    assert cell_to_promo_code("none") == "none"
    assert cell_to_promo_code("bake10") == "BAKE10"
    assert cell_to_promo_code("Bake10") == "BAKE10"
```

- **Body**: copy the template's body into `cell_to_promo_code`. The blank and
  `"none"` branches give the same answer, so they share one, with `or`:

```python
def cell_to_promo_code(s: str) -> str:
    """upper-cases a promo code, and turns blank cells and none into none"""
    if s == "" or s == "none":
        return "none"
    else:
        return s.upper()
```

- **Test and revise**: a missing example is other capitalizations of `"none"`
  (unless the data can't have them). This test fails:

```python error
    assert cell_to_promo_code("None") == "none"
```

- Fix: normalize the input, too: `s == "" or s.lower() == "none"`. Then:

```python
promo_fixed = bake_data.transform_column("Promo Code", cell_to_promo_code)
promo_fixed.freq_bar_chart("Promo Code")
```

### An Error Model

To catch cases like `" "`, ask _how the data were collected_, and so which
errors are plausible: an **error model**, which helps you write programs that
hold up.

- These codes were typed into a text box, which allows any slip: swapped or
  missing letters, an extra space, any capitalization, random junk. A **drop-down
  menu** of the valid codes would have allowed none of them: when people choose
  from fixed options, let them choose.
- A program could fix swapped or missing letters, since it knows the valid
  codes. But what to do with junk (`"BAKE100"`? `"free"`?) is a question for the
  club, not for the programmer: it's _policy_.
- Best of all is to prevent bad data where it's entered.
- Experience with a kind of data teaches you which errors to expect. Thinking
  about how input could go wrong, accidentally or on purpose, is also how
  security work starts.
- Try: make `cell_to_promo_code` also turn strings of only spaces into
  `"none"`. Which step do you go back to first? (Hint: `s.replace(" ", "")`
  removes the spaces from `s`.)

### Finding Errors with Programs

Programs can find data that needs correcting, even when they can't fix it. A
rough check of an email address: it has an `@`, and no spaces.

```python
def is_email(s: str) -> bool:
    """a rough check of whether s is an email address: it has an @, and no spaces"""
    return "@" in s and not (" " in s)

bake_data.filter(lambda r: not is_email(r["Email"]))  # Sam's row
```

- The `filter` gives the rows to look at and correct: here, only Sam's
  `"sam.r at mail.com"`.
- But Lina's `"lina@mailcom"` passes: a check only finds the errors it looks
  for. What would `is_email` also have to check, to catch it?
