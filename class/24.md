### River Data in a Table

A watershed survey records each river: its length, in kilometers, and the two
rivers that join to form it, at its upstream end (`""` where a river begins at
a spring instead):

```python
rivers = table(
    ["name", "length", "left-fork", "right-fork"],
    [
        ["Main River", 40, "North Fork", "South Fork"],
        ["North Fork", 22, "Cedar Creek", "Pine Run"],
        ["South Fork", 18, "", ""],
        ["Cedar Creek", 9, "Birch Brook", "Elk Creek"],
        ["Pine Run", 7, "", "Fern Brook"],
        ["Birch Brook", 4, "", ""],
        ["Elk Creek", 5, "", ""],
        ["Fern Brook", 3, "", ""],
    ],
)
```

- Questions: which rivers join to form a river? Which are two levels
  upstream? Does a stream flow, eventually, into the Main River? How long is
  the whole network?
- Try: plan how to list the rivers two levels upstream of a river (names are
  unique). Ours: find the rivers that join to form it, then the rivers that
  form _them_, with a helper, `forks_of`.

### Forks, and Forks of Forks, from a Table

```python
import pytest

def forks_of(river_table: Table, river: str) -> list[str]:
    """the names of the rivers that join to form river"""
    matches = river_table.filter(lambda r: r["name"] == river)
    if matches.length() > 0:
        river_row = matches.row(0)
        names = [river_row["left-fork"], river_row["right-fork"]]
        return list(filter(lambda n: n != "", names))
    else:
        raise ValueError("No such river " + river)

def test_forks_of():
    assert forks_of(rivers, "Main River") == ["North Fork", "South Fork"]
    assert forks_of(rivers, "Pine Run") == ["Fern Brook"]
    assert forks_of(rivers, "South Fork") == []
    with pytest.raises(ValueError):
        forks_of(rivers, "Amazon")
```

- `""` isn't a river's name, and would break later computations, so we filter
  it out.
- `"South Fork"` (it begins at springs) gets `[]`. `"Amazon"` (not in the
  table) is a different case, and any list could be mistaken for river names,
  so it's an error: `raise ValueError(...)` stops the program with a
  **`ValueError`** (as `float` causes for a non-number string) and our message.
- `with pytest.raises(ValueError):` checks that the code under it causes that
  error (see [Tests](/pll/testing)).
- Test rivers with only one fork (`"Pine Run"`), or none (`"South Fork"`), too.

Two levels upstream are the forks' forks:

```python
def two_up(river_table: Table, river: str) -> list[str]:
    """the rivers two levels upstream of river"""
    flist = forks_of(river_table, river)
    if len(flist) == 2:
        return forks_of(river_table, flist[0]) + forks_of(river_table, flist[1])
    elif len(flist) == 1:
        return forks_of(river_table, flist[0])
    else:
        return []

def test_two_up():
    assert two_up(rivers, "Main River") == ["Cedar Creek", "Pine Run"]
    assert two_up(rivers, "North Fork") == ["Birch Brook", "Elk Creek", "Fern Brook"]
    assert two_up(rivers, "South Fork") == []
    with pytest.raises(ValueError):
        two_up(rivers, "Amazon")
```

- Gotcha: with fewer than two forks, `flist[1]` (or `flist[0]`) is an error,
  so we check `len(flist)` first.

### River Trees

Finding _everything_ upstream this way needs to repeat to any depth (how many
levels are there?), and filters the table again and again. Instead, link each
river directly to the rivers that form it. In data: a fork is a river, not a
`str` (which leaves us back at the table), and the place where a river begins
at a spring needs its own variant:

```python
@dataclass
class Spring:
    pass

@dataclass
class River:
    name: str
    length: float
    left: "RiverTree"
    right: "RiverTree"

RiverTree = Spring | River
```

- A **tree** holds hierarchical data: items with sub-items (a river's forks).
- `RiverTree` is a **binary tree**: conditional data, like a list, with a base
  case (`Spring`), but its recursive case has _two_ fields of its own type
  (in quotes, as in [Class 23](/class/23)).

```python
main_tree = River("Main River", 40,
                  River("North Fork", 22,
                        River("Cedar Creek", 9,
                              River("Birch Brook", 4, Spring(), Spring()),
                              River("Elk Creek", 5, Spring(), Spring())),
                        River("Pine Run", 7,
                              Spring(),
                              River("Fern Brook", 3, Spring(), Spring()))),
                  River("South Fork", 18, Spring(), Spring()))

north_tree = main_tree.left
```

- Nesting shows the structure. Naming the smaller trees first (`elk_tree`,
  then `cedar_tree = River("Cedar Creek", 9, birch_tree, elk_tree)`, ...) gives
  more examples, but hides it; field access digs them out instead.
- `main_tree` and `north_tree`, with `Spring()`, are the **Data definition**'s
  examples: the Examples of every function on `RiverTree` use them.

The forks come from fields, not filtering:

```python
def forks_of_tree(t: RiverTree) -> list[str]:
    """the names of the rivers that join to form the river at the top of t"""
    match t:
        case Spring():
            return []
        case River(n, l, left, right):
            return [left.name, right.name]
```

- Gotcha: this fails if a fork is `Spring()`, which has no `name`: try
  `forks_of_tree(north_tree.right)`, Pine Run.
- Two templates for one question. `forks_of` follows the table's templates: a
  `filter` for the river's row ([Class 8](/class/8)), then the row's columns.
  `forks_of_tree` follows the tree's: a `case` per variant, naming its fields.
  The shape of the data, not the question, gave each its outline, and in the
  tree the forks are fields, so there's nothing to search for.

### Recursive Functions on Trees: `in_network`

Is a river in a network? With the recipe:

<DesignRecipe focus="Examples, Template" />

- **Data definition**: `RiverTree`, and its examples, `main_tree` and
  `north_tree`, above.
- **Template** (as for stacks in [Class 23](/class/23)): a `case` per variant,
  naming its pieces, and a recursive call on each piece of the same type
  ([templates for recursive data](/class/recipe#template-recursive)):

```python
def _river_tree_temp(t: RiverTree) -> ...:
    match t:
        case Spring():
            return ...
        case River(n, l, left, right):
            ...
            n
            ...
            l
            ...
            _river_tree_temp(left)
            ...
            _river_tree_temp(right)
            ...
            return ...
```

- **Signature** and **Docstring**:

```python
def in_network(t: RiverTree, river: str) -> bool:
    """whether river is in the network t"""
    ...
```

- **Examples**: tests, with the data definition's examples as inputs, covering
  both variants:

```python
def test_in_network():
    assert in_network(main_tree, "Main River")
    assert in_network(main_tree, "Elk Creek")
    assert not in_network(north_tree, "South Fork")
    assert not in_network(Spring(), "Elk Creek")
```

- **Body**: copy the template's body into `in_network`. Its recursive calls
  become `in_network(left, river)` and `in_network(right, river)`, since
  `in_network` also takes the river it looks for. Then fill in the `...`s (`l`
  isn't needed, so its line goes):

```python
def in_network(t: RiverTree, river: str) -> bool:
    """whether river is in the network t"""
    match t:
        case Spring():
            return False
        case River(n, l, left, right):
            # n is the same as t.name, and left is the same as t.left
            return river == n or in_network(left, river) or in_network(right, river)
```

- A `Spring()` has no rivers: `False`.
- A `River`: it's this river, or it's in the network of the left fork, or of the
  right fork. Read each recursive call by the Docstring: `in_network(left,
  river)` is whether `river` is anywhere in the left fork's network. That's all
  it takes to see that the body is right.

**Family trees.** In some families -- maybe including yours -- people want to be
able to understand how they're related to others in their family. Family trees
can be useful for that purpose. They represent familial relationships in certain
ways. For example, a node might represent an ancestor, and a child represents
... well, a child or a descendant.

Often, but not always, family trees show both (a) legally-recognized
relationships and (b) relationships in which the children are directly
genetically related to their parents. That means that people who don't meet both
conditions (a) and (b) might not be included in a family tree.

Deciding whom to put in a family tree has emotional and psychological
consequences; it also reflects political and legal stakes. For example:
determining citizenship (who can apply for residency or citizenship based on
family relationships?), finances (whose debts are you responsible for paying?),
medical decision-making authority (what decisions can someone make on someone
else's behalf?), and inheritance (who will automatically inherit if there is no
will?) all depend on definitions of who counts as "family" or "relatives". And
in many places, ideas about what a family is, and about which **familial
relations** should be openly acknowledged and documented, are changing.
