## Notes (review before class)

### Recursion That Follows the Data

Every recursive function so far has followed its data. A list is empty, or a
first element and the rest; a river tree ([Class 25](/class/25)) is a spring, or
a river with two trees flowing into it. The template makes a recursive call on
each part of the same kind (the rest, each subtree), and the function uses what
that call gives for that part. This is **structural recursion**: the structure
of the data gives the function its shape.

The template also says why the function ends. Each recursive call gets a part
of its input, which is smaller, and the data has an end: every list ends with
`[]`, and every path down a tree ends at a spring. So a function written from
the template ends, whatever its body does with the answers.

### Recursion That Follows an Idea

Some problems are solved more easily by a smaller problem that isn't a part of
the data at all, but is made from it, by an idea about the problem. That's
**generative recursion**: each call generates a new problem for the next.

The **greatest common divisor** of two whole numbers is the largest number that
divides both: for 36 and 81, it's 9 (36 is 4 × 9, and 81 is 9 × 9), so the
fraction 36/81 is 4/9 in lowest terms. One way to find it is to try every
number, starting from the smaller of the two and counting down, until one
divides both:

```python
def divisor_from(a: int, b: int, d: int) -> int:
    """the largest whole number from d down to 1 that divides both a and b,
    where d is at least 1"""
    if a % d == 0 and b % d == 0:
        return d
    else:
        return divisor_from(a, b, d - 1)

def slow_gcd(a: int, b: int) -> int:
    """the greatest common divisor of a and b, two whole numbers above 0"""
    return divisor_from(a, b, min(a, b))

def test_slow_gcd_with_no_common_divisor():
    assert slow_gcd(6, 5) == 1

def test_slow_gcd_of_36_and_81():
    assert slow_gcd(36, 81) == 9
```

- `%` is the remainder after dividing ([Class 18](/class/18)), so `a % d == 0`
  when `d` divides `a`.
- It steps down one number at a time, as the list template steps through a list
  one element at a time. For 1,000,000 and 999,999, which have no common divisor
  but 1, that's 999,999 calls: far too many for PLL, which stops any recursion
  that goes thousands of calls deep.

Euclid had a better idea, over 2,000 years ago: `a` and `b` have the same common
divisors as `b` and `a % b`. (A number that divides `a` and `b` also divides
what's left of `a` after taking away `b` as many times as it fits, and the other
way around.) And when `b` is `0`, the answer is `a`, since every number divides
`0`. So each step can jump to a much smaller problem:

```python
def gcd(a: int, b: int) -> int:
    """the greatest common divisor of a and b, two whole numbers that aren't
    both 0. It ends because b is smaller in each recursive call, since a % b
    is less than b, and it is never less than 0."""
    if b == 0:
        return a
    else:
        return gcd(b, a % b)

def test_gcd_with_no_common_divisor():
    assert gcd(6, 5) == 1

def test_gcd_with_a_common_divisor():
    assert gcd(6, 4) == 2

def test_gcd_when_one_divides_the_other():
    assert gcd(27, 81) == 27

def test_gcd_of_36_and_81():
    assert gcd(36, 81) == 9

def test_gcd_with_a_zero():
    assert gcd(5, 0) == 5
```

- The smaller problem, `gcd(b, a % b)`, isn't a part of `a` or `b`. It comes
  from Euclid's idea: nothing in the data suggests it, and nothing in the data
  promises that it ends.
- So the Docstring says why it ends: its **termination statement**. Here, `b`
  gets smaller at every call (from 36 and 81, `b` goes 81, 36, 9, 0), and a
  whole number can't keep getting smaller without going below 0, which `a % b`
  never does. So `b` reaches 0. For 1,000,000 and 999,999, that takes three
  calls.
- When `a` is the smaller one, the first step swaps them: `36 % 81` is `36`.

### Chunks

To print a long list 4 to a line, or to put photos 6 to a page, the list is
split into **chunks**: `chunks([1, 2, 3, 4, 5, 6, 7], 3)` is
`[[1, 2, 3], [4, 5, 6], [7]]`.

From the list template, the recursive call would give the chunks of the rest,
`[2, 3, 4, 5, 6, 7]`: `[[2, 3, 4], [5, 6, 7]]`. That doesn't help: every chunk in
it starts one place off from ours, and fixing it means taking it all apart.

The idea: the first chunk is the first `n` elements, and the other chunks are
the chunks of what's left after them. A list can be cut up like a string
([Class 11](/class/11)'s Practice): `lst[:n]` is its first `n` elements (or all
of them, if it has fewer), and `lst[n:]` is everything after them. Leaving out
the start of a slice means from the beginning, and leaving out the end means to
the end.

```python
def chunks[T](lst: list[T], n: int) -> list[list[T]]:
    """the elements of lst, in order, in lists of n (the last may have fewer),
    where n is at least 1. It ends because each recursive call's list is
    shorter: lst[n:] leaves out at least one element, since n is at least 1."""
    if lst == []:
        return []
    else:
        return [lst[:n]] + chunks(lst[n:], n)

def test_chunks_of_an_empty_list():
    assert chunks([], 3) == []

def test_chunks_that_come_out_even():
    assert chunks(["a", "b", "c", "d"], 2) == [["a", "b"], ["c", "d"]]

def test_chunks_with_a_short_last_one():
    assert chunks([1, 2, 3, 4, 5, 6, 7], 3) == [[1, 2, 3], [4, 5, 6], [7]]

def test_chunks_bigger_than_the_list():
    assert chunks([1, 2], 5) == [[1, 2]]
```

- The question in the `if` is whether the problem is **trivial**: so simple
  that it's answered directly. An empty list has no chunks.
- The termination statement needs `n` to be at least 1, so the Docstring says
  so. With `n` as `0`, `lst[0:]` is all of `lst`: the recursive call gets the
  same problem again, and again, forever. PLL stops it:

```
RecursionError: `chunks` kept calling itself and never stopped.
```

### Designing with Generative Recursion

The recipe's steps are the same. What changes is the Template step: since the
smaller problems don't come from the data, there's no template from the data.
Instead, there are four questions about the problem, answered before the Body:

1. **What's trivial?** Which problems can be answered directly, without
   recursion? (For `gcd`, `b` is `0`; for `chunks`, the list is empty.)
2. **How do you make smaller problems?** This is the idea: a new problem, or
   several, made from the input, and closer to trivial. (`b` and `a % b`; what's
   left after the first `n` elements.)
3. **How do you combine their answers?** (For `gcd`, the smaller problem's
   answer is the answer; for `chunks`, the first chunk goes in front of the
   others.)
4. **Why does it end?** The termination statement, in the Docstring: what gets
   smaller at each call, and why it can't keep getting smaller forever.

Every generative function has the same outline:

```python
def _generative_temp(p: ...) -> ...:
    if ...:
        return ...
    else:
        ...
        _generative_temp(...)
        ...
        _generative_temp(...)
        ...
        return ...
```

The `if` asks whether `p` is trivial, and its branch answers it directly.
Otherwise, the `...` in each recursive call is a smaller problem made from `p`,
and the lines around the calls combine their answers. There can be one
recursive call, as in `gcd` and `chunks`, or more.

| | Structural recursion | Generative recursion |
| --- | --- | --- |
| The smaller problem | a part of the data: the rest, a subtree | made from the data, by an idea |
| Where the function's shape comes from | the data's template | the four questions |
| Why it ends | the parts get smaller, and the data has an end | its termination statement says why |

Use generative recursion when the template's recursive call doesn't help, as
for `chunks`, or when following the data is too slow, as for `slow_gcd`.
Otherwise, follow the data: the template gives the function its shape, and
promises that it ends.

## Live

A worksheet, with your neighbor's sheet different from yours. Each side has a
problem that needs an idea, given in words. You answer the four questions,
then write the function, with its termination statement in the Docstring.
Then you explain yours to your neighbor, who checks it against an example, and
says what would happen on an input that your termination statement rules out.

1. Nobody has been able to write a termination statement for this function. Try
  it on a few numbers: does it always end?

   ```python
   def collatz_steps(n: int) -> int:
       """how many steps it takes to get from n to 1, where each step halves
       an even number, and turns an odd one into 3 × n + 1"""
       if n == 1:
           return 0
       elif n % 2 == 0:
           return 1 + collatz_steps(n // 2)
       else:
           return 1 + collatz_steps(3 * n + 1)
   ```

   Whether it ends for every whole number above 0 is a famous unsolved problem,
   the Collatz conjecture: it has been checked for every number up to
   enormous ones, but no one knows why it should always end.
