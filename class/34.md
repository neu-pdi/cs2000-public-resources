## Notes (review before class)

### Sorting by Inserting

[Class 23](/class/23)'s Practice sorted a list with `insert_sorted`, from the
list template: sort the rest, then put the first number in its place.

```python
def insert_sorted(n: float, lst: list[float]) -> list[float]:
    """lst, in order smallest first, with n added in its place"""
    match lst:
        case []:
            return [n]
        case [f, *r]:
            if n <= f:
                return [n] + lst
            else:
                return [f] + insert_sorted(n, r)

def sort_numbers(lst: list[float]) -> list[float]:
    """lst, in order, smallest first"""
    match lst:
        case []:
            return []
        case [f, *r]:
            return insert_sorted(f, sort_numbers(r))

def test_sort_numbers_of_an_empty_list():
    assert sort_numbers([]) == []

def test_sort_numbers_of_three_numbers():
    assert sort_numbers([9, 2, 5]) == [2, 5, 9]

def test_sort_numbers_with_a_repeat():
    assert sort_numbers([8, 6, 7, 5, 3, 0, 9, 6]) == [0, 3, 5, 6, 6, 7, 8, 9]
```

This is **insertion sort**. How much work does it do? Each `insert_sorted`
compares its number with the sorted rest, one at a time, until it finds the
number's place. For numbers in a random order, that's about halfway along, on
average, so sorting `n` numbers takes about `n × n / 4` comparisons: about
2,500 for 100 numbers, 250,000 for 1,000, and 25,000,000 for 10,000. Twice as
many numbers take four times the work.

The waste is in comparing each number with every number smaller than it, one by
one, on its way to its place.

### Sorting by Splitting

An idea, called **quicksort**: take the first number, the **pivot**, and split
the rest into the numbers no bigger than it and the numbers bigger than it.
Sort each part, and the whole list is the sorted smaller part, then the pivot,
then the sorted bigger part. The four questions of
[generative recursion](/class/33#designing-with-generative-recursion):

1. **What's trivial?** An empty list, which is already sorted.
2. **How do you make smaller problems?** The two parts, made from the rest by
   `filter` ([Class 14](/class/14)): new lists, not parts of the data.
3. **How do you combine their answers?** The sorted smaller part, then the
   pivot, then the sorted bigger part. That's in order, since everything in the
   first is no bigger than the pivot, and everything in the last is bigger.
4. **Why does it end?** Each recursive call's list is made from the rest, which
   leaves out the pivot, so it's shorter than the list the call was given.

```python
def quick_sort(lst: list[float]) -> list[float]:
    """lst, in order, smallest first. It ends because each recursive call's
    list is made from the rest, without the pivot, so it is shorter than lst."""
    match lst:
        case []:
            return []
        case [pivot, *rest]:
            smaller = list(filter(lambda x: x <= pivot, rest))
            bigger = list(filter(lambda x: x > pivot, rest))
            return quick_sort(smaller) + [pivot] + quick_sort(bigger)

def test_quick_sort_of_an_empty_list():
    assert quick_sort([]) == []

def test_quick_sort_of_three_numbers():
    assert quick_sort([9, 2, 5]) == [2, 5, 9]

def test_quick_sort_with_a_repeat():
    assert quick_sort([8, 6, 7, 5, 3, 0, 9, 6]) == [0, 3, 5, 6, 6, 7, 8, 9]

def test_quick_sort_of_a_list_in_order():
    assert quick_sort([1, 2, 3]) == [1, 2, 3]
```

- `match` names the pivot and the rest, as the list template does, but the
  recursive calls aren't on `rest`: they're on lists made from it. That's what
  makes it generative.
- `<=` on one side and `>` on the other put each number of the rest on exactly
  one side, repeats included. With `<` and `>`, a number equal to the pivot
  would be on neither side, and lost.
- How much work? The two filters compare each number of the rest with the
  pivot. When the pivots split their lists about in half, each half is sorted
  the same way, and a list can only be halved about 10 times before it's
  empty, for 1,000 numbers. In a random order, sorting 1,000 numbers takes
  about 22,000 comparisons, against insertion sort's 250,000.

### When Each Is Slow

The pivot doesn't always split its list in half. When the list is already in
order, each pivot is the smallest number in its list: `smaller` is always
empty, and `bigger` is all the rest. Each call takes off one number, as
insertion sort does, and compares every other number with it twice. For 1,000
numbers already in order, that's 999,000 comparisons.

For insertion sort, a list already in order is the best case: each first number
belongs in front of the sorted rest, so `insert_sorted` finds its place with one
comparison. For 1,000 numbers, that's 999 comparisons. In reverse order, it's
the worst case: each number goes to the end, past every number already sorted.

| | `sort_numbers` | `quick_sort` |
| --- | --- | --- |
| The smaller problem | the rest: a part of the data | two lists made from the rest, by comparing with the pivot |
| Combining the answers | `insert_sorted` puts the first number in its place | the smaller part, the pivot, and the bigger part, in that order |
| Why it ends | the template's promise: the rest is shorter | its termination statement |
| 1,000 numbers in a random order | about 250,000 comparisons | about 22,000 |
| 1,000 numbers already in order | 999 | 999,000 |

Neither is wrong, and both are worth knowing; they make different trades. Real
quicksorts choose their pivots more carefully (from the middle of the list, or
at random), so that a list in order isn't slow. Python's own `sorted` uses yet
another idea, and is fast for any list.
