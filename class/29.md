## Notes (review before class)
### Mutable Data

A library program keeps a record of each book, with how many copies are on its
shelves. The fields of a dataclass can be changed, by putting a field access on
the left of an `=`:

```python
@dataclass
class LibraryBook:
    id: int
    title: str
    copies: int

kindred = LibraryBook(205, "Kindred", 3)
kindred.copies = kindred.copies - 1
```

- **Mutable** data can be changed; **immutable** data, all we've used until now,
  cannot.
- The last line changes the _existing_ record: `kindred.copies` is now `2`.
  `LibraryBook(kindred.id, kindred.title, kindred.copies - 1)` would make a
  _new_ record instead.
- Every dataclass field can be changed, so it's up to you not to change one that
  shouldn't (like the `id`).
- Setting a name and setting a field both use `=`, but they mean very different
  things ([Class 30](/class/30)'s heap shows why).

### State

A test written right after making the record fails, because PLL runs the whole
file first, and only then calls the test functions:

```python error
kindred = LibraryBook(205, "Kindred", 3)

def test_copies():
    assert kindred.copies == 3

kindred.copies = kindred.copies - 1
```

- The test passes if it expects `2`, but then fails if the last line is removed:
  it is only _sometimes_ true.
- **State**: the values of the defined names at some point as the program runs.
  There is a state in which `kindred.copies` is `3`, and a later one in which
  it is `2`.
- Not just tests: from now on, every instruction runs in some state, and the
  same code can give different answers in different states.

### Testing Functions that Mutate

A function that mutates its input often returns nothing (`None`), so the
recipe changes a little ([data that changes](/class/recipe#template-mutation)):

<DesignRecipe focus="Docstring, Examples, Template" />

- **Data definition**: `LibraryBook`, above.
- **Template**: the field template from [Class 20](/class/20), ending by setting
  each field (on the left of an `=`), instead of `return ...`, since a function
  on this data might change any of them:

```python
def _library_book_temp(b: LibraryBook) -> None:
    ...
    b.id
    ...
    b.title
    ...
    b.copies
    ...
    b.id = ...
    b.title = ...
    b.copies = ...
```

- **Signature**: the result type is `None`.
- **Docstring**: says what changes, since that is the function's whole job.
- **Examples**: a test checks the _effect_ of calling it, in parts (Setup,
  Call, Check, explained after the recipe):

```python
def test_check_out():
    # Setup
    book = LibraryBook(205, "Kindred", 3)

    # Call
    check_out(book)

    # Check
    assert book.copies == 2
```

- **Body**: copy the template's body into `check_out`. One copy fewer is on the
  shelves, and nothing else changes, so the other fields' lines go:

```python
def check_out(b: LibraryBook) -> None:
    """records that one copy of b has been checked out"""
    b.copies = b.copies - 1
```

A test for a function that uses mutation has three or four parts:

1. **Setup**: set up the values to give the function.
2. **Call**: call the function.
3. **Check**: check that the call had the desired effect.
4. **Teardown**: restore data to their expected state.

- `test_check_out` needs no Teardown, since it made its own record. Checking
  `check_out(kindred)` instead would depend on whatever `kindred.copies` was
  when the test ran (and change it); a test that changes data used elsewhere
  must undo its changes.
- Setup may also need to reset existing data (which other code may have
  mutated) to the values the test expects.
- Try: write a test for this function:

```python
def add_copies(b: LibraryBook, n: int) -> None:
    """adds n copies of b to the shelves"""
    b.copies = b.copies + n
```

### Changing a List

Lists can be changed too. In a new file, the library card numbers of the readers
waiting for a book:

```python
holds = [1042, 1187]
holds.append(1203)
```

- `append` adds an element to the end of the _existing_ list: `holds` is now
  `[1042, 1187, 1203]`. `holds + [1203]` would make a _new_ list instead, and
  leave `holds` as it was.
- Assigning to a position (from 0) replaces the element there: after
  `holds[0] = 1099`, `holds` is `[1099, 1187, 1203]`.
- Like a function that changes a field, `append` gives back nothing (`None`): it
  is called for its effect.

A function that changes a list it's given follows the same recipe:

```python
def place_hold(waitlist: list[int], card: int) -> None:
    """adds card to the end of waitlist"""
    waitlist.append(card)

def test_place_hold():
    # Setup
    readers = [1042, 1187]

    # Call
    place_hold(readers, 1203)

    # Check
    assert readers == [1042, 1187, 1203]
```

- Try: write a second test for `place_hold`, whose Setup is an empty list.
