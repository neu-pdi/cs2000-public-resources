## Notes (review before class)
### The Editor

The interactions panel is for trying things out, one at a time. The **editor**,
above it, holds the program you keep: code saved in a file, which you can
organize as it grows.

### Naming Values

A **definition**, `NAME = EXPRESSION`, associates the value of `EXPRESSION` with
`NAME`. Put this in your file, click **PLL: Run Python File**, then enter `crown`
at the prompt:

```python
crown = triangle(50, "solid", "green")
```

- From then on, the name gives the _value_: after `trunk_height = 10 * 3`,
  `trunk_height` is `30`, not `10 * 3`.
- Using a name that isn't **bound** to a value, like `leaves`, is a `NameError`.
- Names (also called **identifiers**, or variables) can contain letters, digits,
  and underscores, but no spaces or dashes: join words with underscores, as in
  `trunk_height`.

### Names Versus Strings

- Quotes tell them apart: `green` is a name, `"green"` is a string. That's why
  `triangle(green, 50)` failed in [Class 2](/class/2): `green` was a name with no
  value.
- Entering a name looks up its value; entering a string just writes down data,
  like entering `3`. So a name that was never defined is an error, but any string
  is fine. `"dark green"` is data, while `dark green` is two names in a row, a
  syntax error.

### Expressions Versus Statements

```python
3 * 12
trunk_width = 4 + 6
rectangle(trunk_width, 30, "solid", "brown")
apple = circle(5, "solid", "red")
```

- **Expressions** (lines 1 and 3) produce values, which PLL shows when it runs
  the file. A name on its own, like `apple`, is an expression too.
- **Statements** give other instructions. So far, definitions (lines 2 and 4)
  are our only statements, and PLL shows nothing for them.

### The Program Directory

A definition adds an entry to Python's **directory**, which associates names
with values:

```python
size = 60
trunk_height = size / 2
```

- For `trunk_height`, Python looks up `size`, substitutes its value
  (`60 / 2`), and stores the _result_, `30.0`, not the expression. (This will
  matter when we use names to avoid repeating a computation.)
- Definitions are added in order. With these lines swapped, `size` isn't in the
  directory yet when `size / 2` needs it. PLL reports that `size` is defined
  after the line that uses it, and runs nothing.
- You can't see the directory, so write it down on paper to work out what a
  program does. Try: what appears when a file with `color = "green"` and then
  `"color"` runs, and how does each line use the directory?
- **Reassignment** (giving a name that has a value a new one, like a later
  `size = 90`) is allowed by Python, but at the `beginner` level PLL rules it
  out, as a common cause of bugs: it reports that `size` is already assigned,
  and doesn't run the file. So, for now, a name keeps its first value.

### The Run Button

**PLL: Run Python File** clears the directory (except Python's and PLL's
functions), then runs the file from the top. After a file with `size`,
`trunk_height`, and `trunk = rectangle(10, trunk_height, "solid", "brown")`,
the directory is:

| Name | Value |
| --- | --- |
| `circle`, `rectangle`, ... | PLL's functions |
| `size` | `60` |
| `trunk_height` | `30.0` |
| `trunk` | the brown rectangle image |

- Names used at the prompt are looked up there. But
  `above(triangle(size, "solid", "green"), trunk)` at the prompt adds nothing:
  neither the tree nor its crown has a name. A definition adds the tree (but not
  the crown alone):

<!-- python setup
trunk = rectangle(10, trunk_height, "solid", "brown")
-->

```python
tree = above(triangle(size, "solid", "green"), trunk)
```

- Running clears the directory, so a name defined only at the prompt is gone
  after the next run.

### Using Names to Build Images

A window of four blue panes, as one nested expression, is hard to read and
repeats itself:

```python
above(beside(rectangle(40, 40, "solid", "blue"), rectangle(40, 40, "solid", "blue")),
      beside(rectangle(40, 40, "solid", "blue"), rectangle(40, 40, "solid", "blue")))
```

Naming the parts is clearer:

```python
pane = rectangle(40, 40, "solid", "blue")
two_panes = beside(pane, pane)
window = above(two_panes, two_panes)
window
```

- The names say what each part is. The window has four panes, but its
  `rectangle` expression is written (and evaluated) once, so a gray window is one
  change.
- Running this file shows only the window: the definitions show nothing.
- Name the values used more than once, or that help a reader understand the
  program, not every value.
- Try: rewrite the two trees from [Class 2](/class/2), naming their parts, so
  that making both trunks gray is one change.

## Live

Partners trace short programs on paper, taking turns: one reads each line and
says what Python does with it, and the other keeps the directory, then they
switch. For each program, you write down what PLL shows and the directory
after each run. Then we check the trickiest ones together.

## Practice

1. **Define** an orange triangle with side length 35. Now evaluate the name (or identifier, or variable -- all of these are synonyms that programmers use for the same thing) (i.e., `orange_triangle`) in the interactions panel.

1. Define a side length and color (as two separate definitions), and then define a square using those names for the side length and color.

1. Now define a second version where you do not use the side length and color
  variables (or name, or identifier). Notice that when you evaluate both identifiers in the interactions,
  they are exactly the same, but the code is easier to read with the separate
  definitions.

1. Try defining a new side length with the _same name_, later in the
  file. Note what happens when you try to run it. Giving a name that already
  has a value a new one is called "reassignment". Python allows it, but at the
  `beginner` level, PLL rules it out (and will not run your file), since it is a common
  cause of bugs.

1. Now define an image that has a small yellow circle on top of a larger black
  rectangle. Try several different ways, using different number of definitions.
  See which is easiest to understand.

1. Go back to your previous examples and see if there are other definitions you
  can add. Did you make definitions for the radius of circles you made? The
  length of your orange triangle? Try changing the code to include all of those.

1. If you make a definition for the color of your orange triangle, what did you
  name it? If you want to change the color of the triangle, will you have to
  change the name of the definition (i.e., if you used `orange`, but wanted to
  make the triangle purple, you should probably change it to `purple = "purple"`)? If so, that's an indication that perhaps the definition was not
  helpful, or didn't have a good name. Having to change the definition name
  means you will also have to change the uses of the definition!

1. Now make a new image that puts two copies of your small yellow circle
  side-by-side on top of your black rectangle.

1. Now think of a simple flag or logo design. Sketch out a plan on paper and come up with names for different parts of the design. If you have time, make definitions for each part, and compose them together to make the final image.

1. Make a face from definitions. Define `head` (a large circle), `eye`, `nose`,
  and `mouth` (shapes of your choice), and then `face`: two eyes above the nose,
  above the mouth, all on the head. ([`overlay_align`](/pll/images) puts one
  image on another at an edge or corner, rather than at the center.) Then define
  `ear`, and make `face_with_ears`, with an ear on each side. With a definition,
  you draw the ear once, and use it twice.
